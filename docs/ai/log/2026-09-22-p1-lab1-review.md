## Problems found (not fixed yet — awaiting a decision)
1. **Concurrent vote changes by the same user corrupt counters or return 500** (`VoteService.CastOnceAsync`,
   Participant 2). Under Read Committed, N parallel change requests all read the same old `option_id`, so the old
   option gets −1 N times. Reproduced: 40 parallel changes on a fresh `allowVoteChange` poll → 23× **500**
   (`23514 ck_options_vote_count` — the counter would go negative); on poll #1 (large counts) the same race
   **silently** skewed per-option counters (e.g. 38 vs 50 real votes) while `SUM(vote_count) = COUNT(votes)` still
   held — which is why the SUM-based check in ADR 0014 / README bottleneck #1 did not catch it.
   Suggested fix: lock the vote row in the transaction (`SELECT ... FOR UPDATE`) or make the change conditional
   (`UPDATE votes SET option_id = @new WHERE id = @id AND option_id = @old`, 0 rows → re-read); update the two
   option rows in a fixed order (by id) to avoid deadlocks between opposite changes. Verify per option, not by SUM.
2. **Results cache not invalidated on publish and delete** (`PollService.PublishAsync` / `DeleteAsync`,
   Participant 1's code; breaks the rule "anything that changes a poll's status must invalidate").
   Reproduced: author views results of a draft → publishes → other users get **404** on results for up to 10 s
   (TTL); after deleting a draft the author still gets its results for up to 10 s.
3. **Npgsql pool (default max 100) = Postgres `max_connections` (100).** After the 100-thread test the backend held
   ~100 idle connections and even `psql` failed with `FATAL: sorry, too many clients already` until the backend
   restarted. With 2+ instances (labs 2–3) this fails outright. Suggested fix: `Maximum Pool Size` (~20–30) in the
   connection string and/or a higher `max_connections`; good concrete evidence for bottleneck #3.
4. **`/health` takes ~16 s to answer when the DB is down** (EF retries inside the check). Lab 3 load-balancer checks
   need an answer in 1–2 s → give the health check a short timeout.
5. Minor: a `GET /results` computed just before a vote commits can be cached right after the invalidation → stale
   for up to one TTL (10 s). Acceptable for lab 1; a lab 4 talking point.
