## 0. Шпаргалка за одну хвилину

- **Єдина точка входу — HAProxy** на `:8080`, статистика на `:8404/stats`. Backend-и (`backend-1..3`) портів не
  мають — лише `app-network` (ADR 0031). `backend-3` — профіль `scale`, HAProxy підхоплює його сам через Docker DNS.
- **Чому HAProxy, а не Nginx:** безкоштовні активні health checks по `/health`; у відкритому Nginx — лише пасивні.
- **Алгоритм** — `roundrobin` за замовчуванням, перемикання наживо: `bash scripts/lb-algorithm.sh leastconn`
  (м'який reload, 0 помилок під навантаженням). Для нашого профілю правильний — **Least Connections**.
- **Health checks:** активна `GET /health` кожні 2 с (`fall 2 rise 2`), пасивна `observe layer4` — вузол поза пулом
  за 0.3–1.2 с. 5xx від API **не** вважаються відмовою вузла — «пастка 503» (падіння Redis вимкнуло б увесь пул).
- **Повтори:** не вдалося з'єднатися — повтор на інший вузол для будь-якого методу; обрив після відправлення — лише
  GET (`be_api`) і голос (`be_vote`, ADR 0037: одна транзакція + `UNIQUE` → повтор безпечний, максимум 409).
- **Відмова вузла:** читання й голосування — 0 помилок у клієнта при `stop` і `kill`.
- **Scale-out:** на одній машині без лімітів CPU не видно (один backend сам тягне ≈ 5k rps); з `cpus: 1` на
  інстанс читання 1.5k → 2.8k → 3.2k rps, запис упирається в ≈ 250–300 rps.
- **Наступний bottleneck** — рядкові блокування гарячих `options.vote_count` (26–29 з ≈ 30 сесій PostgreSQL чекають
  на `Lock`), далі — бюджет з'єднань з БД (90 на 3 інстанси, ADR 0032).
- **SPOF** — сам HAProxy: Keepalived / VRRP (VIP), DNS Round Robin, керований хмарний LB.

## 1. Сценарій захисту (процедура методички — 4 пункти)

Сухий прогін (С-4, 2026-10-28, з холодного старту, кроки 0 → 3b) — ≈ 3 хв машинного часу: старт ≈ 30 с; розподіл
150 / 150; weighted 75.3 / 24.7; повільний вузол RR 297 rps (50 / 50) → LC 1757 rps (97.6 / 2.4); kill під час
читання — 0 помилок на 16 598 запитів; kill під час голосування — 0 помилок, вузол DOWN за 1.0 с; після демо
`haproxy.cfg` без змін. З поясненнями закладайте 15–20 хв.

Усі команди — з кореня репозиторію, у Git Bash. Перед захистом: Docker Desktop запущений, немає
`docker-compose.override.yml` (`ls docker-compose.override.yml` → «No such file»), відкрита сторінка
http://localhost:8404/stats.

### Крок 0. Холодний старт

```bash
docker compose down -v && docker compose up -d --build
curl -i http://localhost:8080/health        # X-Instance-ID чергується backend-1 / backend-2
curl http://localhost:8082/health           # connection refused — інстанси ззовні недоступні (2.2)
```

**Сказати:** одна команда, без ручних кроків; назовні лише балансувальник; поки backend-и застосовують міграції,
HAProxy кілька секунд віддає свій 503 — це очікувано.

### Крок 1. Демонстрація балансування — п. 1 процедури

```bash
python scripts/lb-distribution.py           # 300 GET → розподіл по X-Instance-ID + лічильники з /stats
docker compose --profile scale up -d        # + backend-3; через ~9 с він UP на сторінці статистики
python scripts/lb-distribution.py           # 33 / 33 / 33 %
```

**Сказати:** розподіл видно і в заголовку `X-Instance-ID`, і на сторінці статистики — числа збігаються.

### Крок 2. Live-переключення алгоритму — п. 2 процедури

```bash
python scripts/load.py --scenario mixed --threads 16 --duration 15 &   # потік запитів
bash scripts/lb-algorithm.sh leastconn      # під навантаженням — 0 помилок
bash scripts/lb-algorithm.sh weighted && python scripts/lb-distribution.py   # ≈ 75 / 25
bash scripts/lb-algorithm.sh roundrobin     # повернути як було (файл під Git)
```

Якщо попросять показати **різницю в поведінці** — повільний вузол (≈ 1 хв):

```bash
printf 'services:\n  backend-2:\n    environment:\n      Diagnostics__ArtificialDelayMs: 200\n' > docker-compose.override.yml
docker compose up -d backend-2
python scripts/load.py --scenario read --threads 32 --duration 10     # RR: 50 / 50, ≈ 300 rps
bash scripts/lb-algorithm.sh leastconn
python scripts/load.py --scenario read --threads 32 --duration 10     # LC: ≈ 97 / 3, ≈ 1.7–2k rps
bash scripts/lb-algorithm.sh roundrobin; rm docker-compose.override.yml; docker compose up -d backend-2
```

**Сказати:** Round Robin не бачить, що вузол повільний, і віддає йому половину запитів — половина клієнтів чекає
200 мс, швидкий вузол простоює. Least Connections бачить, що повільний вузол довше тримає з'єднання, і шле нові
запити на швидкий. p99 однаковий, бо 2.5 % запитів однаково йдуть на повільний вузол (> 1 %).

### Крок 3. Симуляція аварії — п. 3 процедури

```bash
python scripts/lb-failover.py --kill        # потік GET, kill backend-2 на 3-й с, start на 10-й
python scripts/kill-test.py                 # 800 голосів, kill backend-1 після 10 %
```

**Що побачимо:** `client saw 0 non-2xx` / `errors the client saw: 0`; вузол DOWN за ≈ 0.5 / 1 с; після `start` —
UP сам; у kill-test — рядків = користувачів, лічильники узгоджені, результати = БД.

**Сказати:** вузол виключає пасивна перевірка на першій же помилці з'єднання, запити «на льоту» HAProxy повторює на
живому вузлі. Для голосу це безпечно: на вбитому вузлі транзакція або закомічена цілком, або PostgreSQL її відкотить,
а повтор після коміту отримає 409 (`UNIQUE`). Подвійного голосу не буває.

## 2. Питання на захист

**Що таке Single Point of Failure у нашій схемі і як його усунути?** Один HAProxy: упав він — система недоступна,
хоч backend-и живі. Варіанти: два балансувальники + **Keepalived / VRRP** — спільна віртуальна IP, активний шле
heartbeat, при його падінні резервний забирає VIP за 1–3 с; **DNS Round Robin** — кілька A-записів, дешево, але DNS
кешується (TTL), health check-ів немає, клієнт не знає, що адреса мертва; **керований хмарний LB** у кількох зонах.
Після усунення SPOF балансувальника наступними SPOF лишаються PostgreSQL і Redis — один екземпляр кожного.

**Активні vs пасивні health checks?** Активні — HAProxy сам питає `/health` (виключає вузол без участі клієнтів,
повертає після `rise` вдалих). Пасивні — помилки на живих запитах (`observe layer4`): швидше, але перший запит
«платить» — тому повтори.

**Чому `/health` перевіряє БД, але не Redis?** Готовність = можна обслуговувати запити; без БД — не можна (усі
вузли виходять з пулу, клієнт за 3 мс отримує 503 замість 15 с очікування). Redis спільний: перевіряй його `/health`
— падіння Redis вимкнуло б усі вузли, навіть для запитів без Redis.

**Чому не реагуємо на 5xx («пастка 503»)?** 503 від нашого API — чесна відповідь «залежність недоступна», і її
віддають усі вузли одночасно. Якщо вважати це відмовою вузла, балансувальник вимкне весь пул і замінить нашу
ProblemDetails своєю сторінкою. Перевірено `redis-outage-check.py`.

**Чому повтор POST небезпечний, а голосу — ні?** Повтор `POST /api/polls` створить друге опитування. Голос —
одна транзакція (голос + `vote_count`) і `UNIQUE(poll_id, user_id)`: або голос є, або нема; повтор після коміту дає
409. Тому окрема секція `be_vote`. Ціна — клієнт інколи бачить 409 замість 201 для голосу, що пройшов.

**Чому в `be_vote` власні перевірки, а не `track`?** Заміряли: з `track` у секції немає пасивної перевірки, вбитий
вузол лишався в пулі ≈ 6 с, і голоси чекали по 2 с `timeout connect`; з власними — ≈ 1 с.

**Навіщо `option http-buffer-request`?** Повторити можна лише запит, який HAProxy тримає цілком. Без опції він
пересилав заголовки до приходу тіла, і повтор мовчки не відбувався (502 `SH--`).

**Чому IP Hash віддав усе одному вузлу?** Усі запити з хоста приходять у Docker-мережу з однієї адреси шлюзу — як
тисячі клієнтів за NAT. Нам sticky-прив'язка не потрібна: стану в інстансах немає (лаба 2).

**Чому scale-out спершу «не працював»?** Генератор (один процес Python, GIL) упирався в ≈ 1.8k rps, а контейнери
без лімітів CPU ділять ту саму машину: другий інстанс не додає заліза. З `cpus: 1` на інстанс видно приріст.

**Що стане bottleneck після масштабування backend?** Запис: блокування рядків `options.vote_count` у гарячому
опитуванні — транзакції на один рядок PostgreSQL виконує по черзі (Lock = 26–29 з ≈ 30). Далі — з'єднання: кожен
інстанс +30, `max_connections` = 100. Шляхи: кеш читань (лаба 4), шардований лічильник або пакетне оновлення,
PgBouncer.

**Скільки інстансів можна додати?** До трьох — пул 30 кожному (90 зі 100 з'єднань); для 4+ — `DB_MAX_POOL_SIZE =
floor(90 / N)` (ADR 0032).

## 3. Якщо щось пішло не так

| Симптом | Що робити |
|---|---|
| Одразу після `up` HAProxy віддає 503 | backend-и ще застосовують міграції — почекати кілька секунд, на `/stats` вони стануть UP |
| Усі запити повільні на +200 мс / дивний розподіл | лишився `docker-compose.override.yml` із затримкою: `rm docker-compose.override.yml && docker compose up -d` |
| `git status` показує зміни в `haproxy/haproxy.cfg` | після демо алгоритмів: `bash scripts/lb-algorithm.sh roundrobin` |
| `backend-3` у `MAINT (resolution)` | він не запущений: `docker compose --profile scale up -d` |
| Вбитий вузол не повертається сам | так і має бути після ручного `kill` / `stop`: `docker compose start backend-1` |
| `haproxy -c` у Git Bash: «Cannot open configuration file C:/Program Files/Git/...» | Git Bash переписує шлях: `MSYS_NO_PATHCONV=1 docker compose exec -T lb haproxy -c -f /usr/local/etc/haproxy/haproxy.cfg` |
