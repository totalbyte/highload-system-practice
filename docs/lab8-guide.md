## 0. Шпаргалка за одну хвилину

- **Об'єкт:** `GET /api/polls/{id}/results` гарячого опитування (лайв-дашборд). Кожен голос скидає його кеш (збільшує покоління), тож у нас stampede викликає **інвалідація**, а не TTL.
- **Чесно:** наш агрегат дешевий (1–2 мс з `vote_count`). Важкий агрегат імітує `RESULTS_LOAD_DELAY_MS=50` (`pg_sleep`), за замовчуванням 0 — як повільний вузол у лабі 3.
- **Звернення до БД рахує сам PostgreSQL:** `pg_stat_statements`, запит агрегату з тегом `-- results-load`.
- **Stampede (500 VU одночасно, агрегат + 50 мс):** без захисту **486 звернень** до БД на одне скидання ключа, p95 1.2 с.
- **Захист — два рівні:** single-flight на інстансі (лаба 4) → 2 звернення (по одному на інстанс); **+ distributed lock у Redis** (`SET … NX PX 1000`, token, Lua-звільнення) → **рівно 1**. Режим `Lock` — за замовчуванням.
- **Lock без deadlock:** lease 1 с (мертвий власник — читачі відповідають через 1 с), чекач не чекає довше 2 с, знімається лише свій lock.
- **Матриця (500 VU, потік інвалідацій, 3 повтори):** без захисту 124 звернення / 1075 RPS / p95 1.5 с → Lock 1.0 / 3420 RPS / p95 257 мс.
- **Avalanche:** 832 ключі з однаковим TTL — хвилі до 269 звернень/с кожні 10 с; TTL ± 20 % — пік 162 і рівно з третього циклу.
- **Penetration:** неіснуючі id — маркер `not-found` на 30 с; 100 % → **0.15 %** запитів до БД. Межа: унікальні id не ловить (потрібен Bloom filter).

## 1. Сценарій захисту (процедура методички — 4 пункти)

Команди — з кореня репозиторію, у Git Bash. Демо потребує k6, тож стек піднімається **з оверлеєм лаби 8**:

```bash
export MSYS_NO_PATHCONV=1
docker compose down -v && docker compose -f docker-compose.yml -f load-tests/docker-compose.loadtest-lab8.yml up -d --build   # ≈ 35 с
curl -s localhost:8080/health
```

`stampede.sh` / `penetration.sh` перезапускають backend-и з потрібними перемикачами й лишають їх так. Після демо —
`docker compose up -d` (звичайний стек, режими за замовчуванням).

### Крок 1. Live-демонстрація Cache Stampede — п. 1 процедури (≈ 1 хв)

Сказати: «Скидаю ключ гарячого опитування і одночасно пускаю 500 запитів; скільки разів агрегат читали з БД, рахує сам PostgreSQL».

```bash
RESULTS_LOAD_DELAY_MS=50 bash load-tests/stampede.sh None burst -e ROUNDS=1
```

Очікувано: `postgres: 480–500 DB loads`, `RESULT None burst … 480–500 per invalidation`, p95 1.2–1.4 с. Усе демо (кроки 1–3) з холодного старту — ≈ 3 хв. Пояснити: 500 VU
чекають спільного моменту, за 50 мс до нього k6 робить `INCR polling:results:gen:1` (так само, як голос), усі читачі
промахуються і кожен іде в Primary Shard A — це Thundering Herd: пул (2 × 30 з'єднань) вичерпано, решта в черзі.

Показати в самій БД (за бажанням):

```bash
docker compose exec -T postgres psql -U polling -d polling -c "SELECT calls, round(mean_exec_time::numeric, 1) AS ms FROM pg_stat_statements WHERE query LIKE '%results-load%'"
```

### Крок 2. Live-демонстрація захисту — п. 2 процедури (≈ 2 хв)

```bash
RESULTS_LOAD_DELAY_MS=50 bash load-tests/stampede.sh SingleFlight burst -e ROUNDS=1   # 2 — по одному на інстанс
RESULTS_LOAD_DELAY_MS=50 bash load-tests/stampede.sh Lock burst -e ROUNDS=1           # 1 — на весь кластер
```

Пояснити два рівні: single-flight об'єднує одночасні промахи одного інстансу (лаба 4), тому на двох інстансах — 2;
distributed lock у Redis узгоджує інстанси — 1. Показати діаграму послідовності в README (розділ 2.4).

Коректна обробка TTL / timeouts (критерій оцінювання):

```bash
python scripts/lock-check.py        # «мертвий» власник lock: усі 200 через ≈ 1 с, 1 звернення, ключів не лишилось
```

За бажанням — сплив lease посеред читання: `RESULTS_LOAD_DELAY_MS=1500 bash load-tests/stampede.sh Lock burst -e ROUNDS=1 -e PERIOD=5`
→ 2 звернення замість 1, 0 % помилок, у лозі `lease … expired` (`docker compose logs backend-1 | grep -i lease`).

Матрицю (2.7) показати з README: потік інвалідацій, 3 повтори — 124 → 2.2 → 1.0 звернення, RPS 1075 → 3765 → 3420.

### Крок 3. Демонстрація Negative Caching — п. 3 процедури (≈ 2 хв)

```bash
python scripts/negative-cache-check.py                             # 150 запитів до 9999999 → 1 звернення до БД; нове опитування не ховається
RESULTS_STAMPEDE_PROTECTION=None bash load-tests/penetration.sh false   # без жодного захисту: 100 % запитів до БД
bash load-tests/penetration.sh true                                # Lock + негативний кеш: ≈ 0.15 %
```

Пояснити: маркер `not-found` у тому самому ключі покоління, TTL 30 с ± 20 %; створення опитування збільшує покоління
свого id (id передбачувані — послідовність `poll_ids`), тож закешоване «немає» не сховає нове опитування. Межа:
`bash load-tests/penetration.sh true -e IDS=0` (новий id на кожен запит) — у БД так само 100 %, Redis росте на ключ на запит.

## 2. Теорія (п. 4 процедури)

### Чотири аномалії кешу

| Аномалія | Що відбувається | Скільки ключів | Наш приклад | Захист |
|---|---|---|---|---|
| **Cache Stampede** (dog-piling, «cache breakdown» для гарячого ключа) | ключ зник, і багато одночасних запитів промахуються та **кожен** перераховує те саме значення | один, гарячий | голос у гаряче опитування скидає покоління — всі глядачі промахуються разом | single-flight, distributed lock, SWR, XFetch |
| **Thundering Herd** | загальніше: багато очікувачів «прокидаються» одночасно на одну подію і разом б'ють у ресурс. Для кешу — це те, як stampede виглядає з боку **БД**: сплеск запитів і черга за з'єднаннями | — | 486 читань агрегату за мить, пул 2 × 30 вичерпано, p95 1.2 с | обмежити кількість тих, хто йде в ресурс (coalescing, lock), розкид у часі (jitter, backoff) |
| **Cache Avalanche** | **багато** ключів зникають одночасно: однаковий TTL у записів, зроблених разом, або рестарт / flush кешу | багато | 832 ключі, записані в одну секунду з TTL 10 с, — хвиля кожні 10 с | TTL jitter, прогрів, захист на рівні кожного ключа, кластер кешу (не втратити всі ключі разом) |
| **Cache Penetration** | запити до того, чого **немає ніде** — кеш ніколи не має значення, кожен запит іде в БД | неіснуючі | `GET /api/polls/9999999/results` | Negative Caching, Bloom filter, валідація / rate limiting |

Коротко: stampede — один ключ і багато запитів; avalanche — багато ключів разом; penetration — ключів немає взагалі;
thundering herd — назва самого удару по ресурсу, який дають перші два.

### Механізми координації

- **Single-flight / Request Coalescing** — у процесі: перший промах запускає читання, решта чекають той самий `Task`.
  Без мережевих викликів, але межа — інстанс: N інстансів → N читань.
- **Distributed Lock (`SET key token NX PX ttl`)** — один на кластер. Обов'язково: lease (інакше впалий власник —
  вічний lock), випадковий token і звільнення через Lua `if GET == token then DEL` (інакше після спливу lease знімеш
  чужий lock), обмеження часу очікування. Ціна — запити в Redis і очікування; чекачі опитують кеш (у нас кожні 10–20 мс)
  або підписуються на pub/sub.
- **Stale-While-Revalidate** — віддати старе значення, одного відправити оновлювати у фоні. Stampede зникає повністю,
  але застарілість = вік значення + час оновлення, і вона не обмежена інвалідацією. У нас ламає «після голосу бачу свій
  голос» — не реалізовано (ADR 0044). У HTTP — `Cache-Control: stale-while-revalidate=N`.
- **TTL Jitter** — `TTL = Base × (1 ± U·j)`: записи, зроблені разом, спливають у різний час. Розкид має бути симетричним
  і достатнім: ±20 % від 10 с — лише 4 с, тож перша хвиля лишається, а вирівнюють наступні цикли.
- **Negative Caching** — кешувати «немає» з коротким TTL. Пам'ять ≈ частота різних неіснуючих ключів × TTL; потрібна
  інвалідація при створенні сутності.

### Redlock

Алгоритм для lock на **N незалежних** Redis-майстрах (зазвичай 5), без реплікації між ними:
1. Клієнт запам'ятовує час і по черзі робить `SET key token NX PX ttl` на кожному вузлі з коротким таймаутом.
2. Lock узято, якщо вдалося на **більшості** (≥ N/2 + 1) і минуло менше за TTL; час дії = TTL − витрачене − запас на
   дрейф годинників.
3. Інакше — звільнити на всіх вузлах (тим самим Lua зі звіркою token).

Навіщо: один Redis із реплікою не дає безпеки — майстер міг віддати lock і впасти до реплікації, репліка стає майстром
без цього ключа, і lock бере другий клієнт. Критика (M. Kleppmann, 2016): пауза процесу (GC), стрибок годинника або
затримка мережі можуть зробити так, що клієнт вважає lock своїм, коли той уже сплив, — два власники. Для **correctness**
потрібен fencing token: монотонний номер, який перевіряє сам захищений ресурс і відкидає запис зі старим номером; Redlock
його не дає, тому для таких задач беруть консенсус (ZooKeeper, etcd). Для **efficiency** lock (не робити зайву роботу) —
як у нас — достатньо одного Redis: подвійний власник означає лише зайве читання БД. У нас fencing не потрібен ще й
тому, що запис у кеш ідемпотентний і прив'язаний до покоління.

### Bloom filter

Бітовий масив із m бітів і k хеш-функцій. Додати елемент — встановити k бітів; перевірити — якщо хоч один із k бітів 0,
елемента **точно немає**; якщо всі 1 — **можливо є**. Хибно-негативних відповідей немає, хибно-позитивні — з
імовірністю ≈ (1 − e^(−kn/m))^k; оптимальне k = (m/n)·ln 2. Приклад: 1 млн id з 1 % хибних спрацювань — ≈ 9.6 біта на
елемент (≈ 1.2 МБ), k = 7. Видаляти не вміє (для цього — counting Bloom або cuckoo filter). Проти penetration: фільтр
стоїть перед кешем — «точно немає» → 404 одразу, без кешу й БД; id додаються при створенні. У Redis — модуль RedisBloom
(`BF.ADD`, `BF.EXISTS`). Перевага над Negative Caching — ловить і **унікальні** неіснуючі id і займає фіксовану пам'ять.
У нас дешевша заміна: id послідовні, тож `id > last_value` послідовності `poll_ids` точно не існує; дірки (видалені
чернетки) ловить негативний кеш.

### XFetch (Probabilistic Early Expiration)

Vattani, Chierichetti, Lowenstein, 2015. Разом зі значенням зберігають `delta` — скільки тривав перерахунок — і момент
спливання `expiry`. При кожному читанні:

```
if now − delta · β · ln(rand()) ≥ expiry:   # ln(rand()) < 0, тож ліва частина «забігає вперед»
    перерахувати і записати заново (до того, як ключ сплив)
```

Імовірність дострокового оновлення росте, що ближче `expiry` і що дорожчий перерахунок (`delta`); β = 1 за
замовчуванням, β > 1 — раніше. Без lock і без координації: майже завжди оновлює **один** запит трохи раніше спливання.
Розрахований на stampede **через TTL**. У нас stampede дає інвалідація (покоління збільшується голосом, ключ стає
недосяжним миттєво) — XFetch тут нічого не змінить; для закритих опитувань (TTL 1 год) він міг би бути, але там
перерахунок дешевий і натовпу немає.

## 3. Питання на захист

**Чим stampede відрізняється від avalanche?** Stampede — один гарячий ключ, багато одночасних запитів до нього.
Avalanche — багато ключів зникають разом. Lock і single-flight проти avalanche не допомагають (на кожен ключ і так одне
читання, але всі ключі разом), допомагає розкид TTL.

**Чому дві копії захисту — single-flight і lock?** Single-flight безкоштовний (у процесі) і зрізає сотні промахів
інстансу до одного; lock узгоджує інстанси. Без single-flight кожен із сотень промахів сам опитував би Redis.

**Чому Lock не швидший за single-flight у матриці?** На двох інстансах 1 чи 2 читання для БД однаково; очікування lock
коштує запитів у Redis: −9 % RPS, зате −13 % p95. Виграш росте з кількістю інстансів — single-flight дає N читань,
lock — одне.

**Що буде, якщо власник lock впаде?** Lock — ключ із lease 1 с; він зникне сам, наступний візьме lock. Показано
`lock-check.py`: відповіді рівно через ≈ 1 с.

**Що буде, якщо читання довше за lease?** Lock візьме наступний і теж прочитає БД — зайве читання, не помилка; власник
не зніме чужий lock (Lua зі звіркою token). Виміряно: 1500 мс при lease 1 с — 2 читання, 0 помилок.

**Чому не просто `DEL` для звільнення?** Після спливу lease ключ уже може належати іншому. `DEL` зняв би чужий lock.

**Навіщо покоління в ключі lock?** Як і в single-flight: читання, що почалося після голосу, має покоління g + 1 і не
чекатиме читання, яке почалося до голосу (інакше побачило б агрегат без свого голосу).

**Чи не ламає Negative Caching нові опитування?** Id видає послідовність, наступний id передбачуваний. Тому створення
опитування збільшує його покоління, і закешоване «немає» стає недосяжним — `negative-cache-check.py`, крок 2.

**Скільки пам'яті з'їсть негативний кеш?** ≈ частота різних неіснуючих id × TTL × ~106 байт: 465 запитів/с × 30 с ≈
14 тис. ключів ≈ 1.5 МіБ. При атаці унікальними id він ще й не допомагає — потрібен Bloom filter або rate limiting.

**Чому TTL ± 20 %, а не + 20 %?** Методичка: `Base ± Random`. Симетричний розкид не збільшує середній TTL і розносить
ключі в обидва боки; за абсолютною величиною 4 с від 10 с — мало, тому перша хвиля лишається.

**Наскільки вірити числам?** Кількість звернень до БД стабільна між повторами. RPS і p95 одиночних прогонів
розходилися до 30–50 %, тому матриця — серія з трьома повторами, медіана [min–max]; різниця менше ~10 % не доведена.
Ноутбук на 8 потоків, закрита модель (coordinated omission занижує хвіст).

**Чому імітація затримки — чесно?** Методичка просить «коштовний за обчисленнями» об'єкт, а наш агрегат дешевий. Перемикач
за замовчуванням 0, у звіті є обидві серії: на справжньому агрегаті захист теж дає +50 % RPS.
