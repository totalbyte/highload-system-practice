## 0. Шпаргалка за одну хвилину

- **Що кешуємо:** лише `GET /api/polls/{id}/results` — лайв-дашборд, найчастіше читання; секунди застарілості
  прийнятні, а відповідь однакова для всіх. Список опитувань, `GET /polls/{id}`, `/me`, `/login`, `/health` — ні
  (README, «Вибір об'єкта кешування»).
- **Де:** один Redis у `app-network`, спільний для всіх інстансів. PostgreSQL — джерело правди, Redis — лише кеш:
  без збереження на диск (`--save ""`, ADR 0043).
- **Ключі:** `polling:results:v1:{pollId}:g{покоління}` + лічильник `polling:results:gen:{pollId}` (ADR 0041).
  `v1` — версія формату значення; хешу параметрів немає, бо параметрів немає.
- **Cache-Aside:** Lua-скрипт за один round-trip читає покоління і значення → HIT (без БД) або MISS → PostgreSQL →
  `SET … EX` під поколінням, прочитаним **до** запиту в БД.
- **Інвалідація:** голос, publish, close, delete після коміту роблять `INCR` покоління (+ `UNLINK` старого значення).
  Це закрило гонку лаби 2 («прочитали до коміту, записали після `DEL`»): `DEL` — застарілі читання в кожному прогоні,
  покоління — 0 із 60.
- **TTL:** `active` / `draft` — 10 с, `closed` — 1 год, + 0–20 % jitter проти Avalanche. TTL — страховка, а не
  механізм свіжості; довгий TTL — лише для даних, що вже не зміняться.
- **Метрики:** `X-Cache: HIT | MISS | BYPASS` у відповіді і `{HIT}` у лозі HAProxy; cold ≈ 3.8 мс, hot ≈ 2.0 мс (p50).
- **Fallback:** `docker stop redis` → 200 `BYPASS` з БД за десятки мс (у лабі 2 було 503 через 5 с); fail-fast
  клієнт; `/health` Redis не перевіряє — вузли лишаються в пулі.
- **Stampede:** кожен голос скидає кеш гарячого опитування → single-flight у процесі: 6.7–14.4 → ≈ 2 звернення до
  БД на інвалідацію (по одному на інстанс, ADR 0044).
- **Під навантаженням:** кеш — 2730 читань/с і 0 запитів у БД; Redis зупинено — 1355 читань/с, p95 ×2.4, 0 помилок.

## 1. Сценарій захисту (процедура методички — 4 пункти)

Сухий прогін (2026-11-02, з холодного старту, кроки 0 → 4 цими самими командами) — ≈ 75 с машинного часу: старт
22 с; `cache-demo.py` 7 с (MISS → HIT → голос → MISS → HIT → close → TTL ≈ 1 год → BYPASS → MISS → HIT);
`cache-race-check.py` 23 с, 0 з 60; `docker stop` → 200 BYPASS, `/health` Healthy; `redis-outage-check.py` 6 с;
stampede ≈ 2.2 звернення до БД на інвалідацію; cold / hot 4.2 / 2.1 мс (p50). З поясненнями закладайте 15–20 хв.

Усі команди — з кореня репозиторію, у Git Bash. Перед захистом: Docker Desktop запущений, немає
`docker-compose.override.yml`, вільні порти 8080, 8404 (HAProxy), 6379 (Redis — його читають `cache-demo.py`,
`cache-latency.py`, `cache-stampede-check.py`), 5433 (PostgreSQL), 5050 (pgAdmin).

### Крок 0. Холодний старт

```bash
docker compose down -v && docker compose up -d --build
curl -si http://localhost:8080/api/polls/1/results | grep -i -E "x-cache|x-instance"   # MISS; повторити — HIT
docker compose exec redis redis-cli CONFIG GET save                                       # порожньо — кеш без диска
```

**Сказати:** одна команда, без ручних кроків; Redis — окремий контейнер у тій самій мережі, усі інстанси ходять у
нього (2.2); API доступне лише через балансувальник — backend-и портів не публікують.

### Крок 1. Cache Hit / Miss — п. 1 процедури

```bash
python scripts/cache-demo.py --pause        # Enter перед кожним кроком; тут — блок «1. Cache Hit / Miss»
```

**Що побачимо:** перше читання — `MISS` (backend-1), друге і третє — `HIT`, причому на **іншому** інстансі;
праворуч — покоління і TTL ключа, прочитані прямо з Redis (`gen=1 TTL(g1)=10s`).

**Сказати:** при MISS backend прочитав PostgreSQL і поклав агрегат у Redis на 10–12 с; при HIT БД не зачіпалась.
Копію, покладену backend-1, одразу віддав backend-2 — кеш один на всі інстанси, affinity немає.

За бажанням — те саме вручну і в лозі балансувальника. Спершу прочитати опитування: демо в кроці 3 перезапускає
Redis, і після цього він порожній.

```bash
curl -si http://localhost:8080/api/polls/1/results | grep -i x-cache            # MISS (або HIT)
docker compose exec redis redis-cli GET polling:results:gen:1                  # покоління N; (nil) = 0
docker compose exec redis redis-cli --scan --pattern 'polling:results:v1:1:*'  # значення поточного покоління
docker compose exec redis redis-cli TTL polling:results:v1:1:g<N>              # 10–12 с
docker compose logs lb | grep results | tail -5                                # {MISS} / {HIT} поруч з інстансом і часом
```

### Крок 2. Інвалідація — п. 2 процедури

Той самий `cache-demo.py`, блок «2. Invalidation on a mutation».

**Що побачимо:** `POST vote` → 201 і `gen=2 TTL(g2)=no entry` → наступне читання `MISS` з `totalVotes=1` → `HIT`.
Далі `PATCH close` → `MISS` зі статусом `closed` і **TTL ≈ 3600–4300 с**.

**Сказати:** мутація після коміту в БД збільшує покоління; для нового покоління запису ще немає, тож наступне
читання гарантовано йде в БД і бачить зміну (2.5). Закрите опитування вже не зміниться — тому довгий TTL.

Якщо спитають «а гарантовано?» — показати доказ (≈ 20 с):

```bash
python scripts/cache-race-check.py          # 60 раундів × 8 одночасних голосів, 12 читачів → «0 of 60»
```

### Крок 3. Fallback — п. 3 процедури

Той самий `cache-demo.py`, блоки «3. Fallback» (скрипт сам робить `docker compose stop redis` / `start`). Або
буквально як у методичці:

```bash
docker stop polling-platform-redis-1
curl -si http://localhost:8080/api/polls/1/results | grep -i -E "HTTP|x-cache"   # 200, BYPASS
curl -s http://localhost:8080/health                                            # Healthy — вузли в пулі
docker start polling-platform-redis-1
```

**Що побачимо:** `BYPASS`, 200, мілісекунди; голос під час збою — 201, і наступне читання вже його бачить; після
`start` — кілька `BYPASS`, поки клієнт перепідключається (~2.5 с), далі `MISS` (`gen=0` — Redis порожній) → `HIT`.

**Сказати:** кеш лише прискорює, джерело правди — PostgreSQL, тому без Redis читаємо з БД (graceful degradation).
Fail-fast: поки з'єднання немає, команда Redis падає одразу, а не чекає 5 с. Під час збою нічого не пишемо в кеш, а
після рестарту Redis порожній — застаріле не «воскресає». Ціна — усе читання йде в БД (README: читань/с удвічі
менше, p95 ×2.4).

Повна автоматична перевірка — `python scripts/redis-outage-check.py` (≈ 6 с, `ALL CHECKS PASSED`).

## 2. Питання на захист

### Теорія з методички

**Cache Stampede / Thundering Herd — що це і чи є у вас?** Багато запитів одночасно промахуються по **одному**
ключу і кожен сам іде в БД рахувати те саме. Класично — коли популярний ключ сплив за TTL. У нас причина інша:
**кожен голос скидає кеш гарячого опитування** (нове покоління), і всі глядачі дашборду промахуються разом. Розмір
натовпу ≈ читань/с × час перерахунку; під піком перерахунок довшає (пул з'єднань зайнятий транзакціями голосів), натовп
росте і забирає ще більше з'єднань — петля зворотного зв'язку. Заміряли: 6.7–14.4 звернення до БД на інвалідацію,
до 98 зі 100. Рішення — **single-flight у процесі**: одночасні промахи інстансу по одному (опитування, покоління)
чекають одне спільне читання → ≈ 1 звернення на інстанс (ADR 0044).

**Які ще є способи і чому не вони?**

| Спосіб | Суть | Чому ні в нас |
|---|---|---|
| Розподілений lock (`SET … NX PX`) | один перерахунок на весь кластер, інші чекають | 1 замість 2–3 звернень ціною додаткових round-trip-ів, очікування в циклі і обробки падіння власника lock |
| Stale-while-revalidate | віддавати старе, поки один оновлює | виборець після 201 бачив би старий результат — ламає 2.5 |
| Probabilistic early expiration (XFetch) | оновлювати трохи раніше за TTL з імовірністю, що росте до кінця TTL | від stampede через TTL; у нас його спричиняє інвалідація |
| Debounce інвалідації | скидати не частіше ніж раз на N мс | теж ламає «наступне читання свіже» |

**Cache Avalanche — що це і як захищені?** Масовий одночасний промах по **багатьох** ключах: однаковий TTL у записів,
створених разом (після рестарту або холодного старту), або падіння всього шару кешу. Захист у нас:
- **jitter TTL** 0–20 % — спливання розтягується на 2 с (active) / 12 хв (closed);
- **fail-fast + fallback** — падіння Redis не «вішає» запити на 5 с, а переводить читання в БД; ціну виміряли:
  1355 проти 2730 читань/с, p95 ×2.4, 0 помилок;
- **single-flight** — після рестарту Redis кожне опитування перераховується один раз на інстанс, а не на кожного
  читача.
Далі (поза лабою): прогрів кешу після рестарту, rate limiting на БД, L1-кеш у процесі.

**LRU vs LFU, стратегії витіснення (eviction)?** Витіснення працює, коли Redis досягає `maxmemory`:
- **LRU** (Least Recently Used) — викидає те, до чого найдовше не зверталися. Добре для «свіжість важлива»; слабке
  місце — одноразовий прохід по багатьох ключах витісняє гарячі.
- **LFU** (Least Frequently Used) — викидає те, до чого зверталися найрідше. Тримає стабільно гарячі ключі; слабке
  місце — колись популярний ключ довго не витісняється (у Redis лічильник частоти логарифмічний і згасає з часом,
  `lfu-decay-time`), а новий ключ стартує з малим лічильником.
- Redis реалізує обидва **наближено**: вибирає кілька випадкових ключів (`maxmemory-samples`, 5) і витісняє гірший
  із них. Політики: `noeviction` (за замовчуванням — помилка запису), `allkeys-lru` / `allkeys-lfu`,
  `volatile-lru` / `volatile-lfu` (лише ключі з TTL), `volatile-ttl`, `*-random`.
- **Для нас — `volatile-lru`**, якщо колись ставити ліміт пам'яті. `volatile-*`, бо ключі без TTL — лічильники
  поколінь і ключі DataProtection — витісняти не можна. **LRU, а не LFU**, бо в нас ключ значення змінюється з
  кожним голосом: старе покоління, яке читали тисячі разів, після інвалідації не читає ніхто. LFU тримав би саме
  його (високий лічильник), а новий ключ поточного покоління витіснив би першим; LRU робить навпаки — правильно.
  Зараз `maxmemory` не задано: записи короткоживучі, пам'ять обмежує TTL.

**Expiration vs Invalidation?**
- **Expiration** — пасивне: запис зникає сам за TTL. Просто, без координації, але застарілість = до TTL.
- **Invalidation** — активне: запис змінюють або видаляють у момент зміни даних. Точно, але треба покрити **кожен**
  шлях запису і мати справу з гонками.
- У нас **інвалідація — основний механізм свіжості** (4 точки: vote, publish, close, delete), а **TTL — страховка**
  на випадок втраченої інвалідації (Redis «моргнув»). Тому TTL залежить від того, чи можуть дані змінитися: 10 с для
  активного, 1 год для закритого.

**Cache Penetration (бонус, якщо спитають).** Запити до ключів, яких немає ніде (неіснуючий id) — щоразу промах і
запит у БД. У нас 404 не кешується; захист — негативне кешування на кілька секунд або Bloom-фільтр існуючих id. Для
лаби не потрібно.

### Про наше рішення

**Чому саме `/results`, а не список опитувань?** Список залежить від користувача (автор бачить свої чернетки і
непублічні) і має багато параметрів — спільний запис годився б лише для анонімних; і це не піковий шлях. `/results`
однаковий для всіх, читається найчастіше, застарілість у секунди прийнятна. Критерій «кешувати лише відповідні
операції».

**Навіщо покоління, чому не `DEL`?** З `DEL` була гонка: читач прочитав БД **до** коміту голосу, голос зробив `DEL`,
читач поклав старий агрегат **після** `DEL` — застаріле до TTL, хоча виборець уже має 201. З поколінням читач пише
під покоління, яке прочитав до запиту в БД; якщо інвалідація встигла, запис ляже під старе покоління, яке ніхто не
читає. `cache-race-check.py`: `DEL` — 2–5 застарілих раундів із 60 у кожному з 5 прогонів, покоління — 0.

**Чому гонку важко зловити?** Один голос на раунд її не відтворює: кеш гарячий, читачі промахуються лише після `DEL`,
тобто вже після коміту. Потрібна **друга** інвалідація саме тоді, коли читач, що промахнувся після першої, ще між
читанням БД і записом у кеш, — тому в тесті пачки одночасних голосів за один варіант.

**Чому TTL різний за статусом?** Довгий TTL — лише для даних, що вже не зміняться: голосувати можна тільки в
`active`, із `closed` переходів немає. Запис, порахований поки опитування активне, лишається з 10 с, навіть якщо
його закрили мить потому, — тож при втраченій інвалідації застаріле живе ≤ 12 с.

**Чому cold vs hot різняться лише в 2 рази (3.8 vs 2.0 мс)?** Запит і так дешевий — денормалізований
`vote_count`, а ~1.5 мс з обох — HTTP, HAProxy, мережа Docker. Головна цінність не в latency одного запиту, а в тому,
що при HIT **немає звернення до БД**: під навантаженням 2730 читань/с — 0 запитів у PostgreSQL.

**Чому під час голосування лише 47 % HIT?** Кожен голос скидає кеш; при 116–250 голосах/с запис живе мілісекунди.
Частку попадань підняти можна лише ціною свіжості (debounce, stale-while-revalidate) або write-through оновленням
лічильника в кеші — інший, складніший патерн. Ми обрали свіжість, а промахи зробили дешевими: 930 промахів/с →
209 звернень до БД/с (≈ 2 на голос, single-flight).

**Чому Redis без збереження на диск?** Після `docker compose stop/start` Redis завантажував `dump.rdb` — і повертав
запис, інвалідацію якого пропустив, поки лежав (контрольний прогін: HIT з `totalVotes=0`, хоча голос у БД).
Кешу персистентність не потрібна: порожній після рестарту — значить свіжий.

**Чому `/health` не перевіряє Redis?** Без Redis інстанс повністю працездатний (fallback). Якби `/health` залежав від
Redis, його падіння вимкнуло б **увесь** пул — та сама «пастка 503», що в лабі 3.

**Чи не stateful single-flight (лаба 2)?** Ні: у ньому лише запити, що виконуються в цю мить. Падіння інстансу
нічого не губить, нічого не треба синхронізувати між інстансами — це об'єднання запитів, а не стан застосунку.

**Чому промах, що чекав спільного читання, теж `MISS`?** `X-Cache` каже, звідки дані: не з Redis. Скільки реально
було звернень до БД — видно з кількості різних `generatedAt` (`cache-stampede-check.py`).

**Яка модель узгодженості?** Для кожного клієнта: читання, що почалося **після** відповіді на мутацію, бачить цю
мутацію — на будь-якому інстансі (read-your-writes через покоління). Читання, **одночасні** з мутацією (між її
комітом і відповіддю), можуть отримати і старе, і нове значення — це звичайна паралельність, не застарілість.
Виняток — Redis втратив інвалідацію і не перезапускався: застаріле ≤ 12 с (ADR 0043).

## 3. Якщо щось пішло не так

| Симптом | Що робити |
|---|---|
| Одразу після `up` HAProxy віддає 503 | backend-и ще застосовують міграції — почекати кілька секунд (`/stats`: DOWN → UP) |
| Завжди `BYPASS` | Redis зупинений після демо: `docker compose start redis` (або `docker start polling-platform-redis-1`) |
| Після `start redis` ще кілька секунд `BYPASS` | нормально: клієнт перепідключається ~2.5 с; `cache-demo.py` і `redis-outage-check.py` чекають на це самі |
| `redis-cli GET polling:results:gen:1` → `(nil)`, `--scan` нічого не знаходить | Redis щойно перезапускався (демо, крок 3) і порожній: спершу прочитати `/api/polls/1/results` |
