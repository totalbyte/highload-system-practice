# Лабораторна 6: посібник до захисту — реплікація БД і розділення читання та запису

> Методичка — [`labs/Lab6 - Database Replication.md`](labs/Lab6%20-%20Database%20Replication.md), план — [`lab6/plan.md`](lab6/plan.md), усі числа — README, розділ
> «Лабораторна 6», і [`lab6/load-comparison.md`](lab6/load-comparison.md). Сторінка для викладача — [`about/lab6.md`](about/lab6.md). Рішення — ADR 0049–0053.

## 0. Шпаргалка за одну хвилину

- **Топологія:** `postgres` (Primary) + `postgres-replica`, асинхронна потокова реплікація WAL, слот `replica_1`, старт без ручних кроків (`pg_basebackup` на порожньому томі).
- **Маршрутизація:** у застосунку. Primary за замовчуванням, на репліку йде лише `ReadDb`: каталог і деталі. `X-DB-Node` показує реальний вузол.
- **Strict на Primary:** логін, `/me`, голос і перевірки перед ним, відповідь після запису, «мій голос», результати при промаху кешу.
- **Read-After-Write:** Session Sticky у Redis, 5 с після запису читання користувача на Primary.
- **Replica down:** читання на Primary, 0 помилок. **Primary down:** читання на репліці, записи й логін — 503 `Read-Only Mode`. `/health` = 503 лише коли лежать обидва.
- **Навантаження:** RPS не зростає; під записом p95 читання вдвічі менший до насичення (≈ 75 проти ≈ 146 мс), запис +40 %; ціна — до −25 % RPS чистого запису.
- **Межа:** вище насичення затримка реплікації до 29.5 с, причину не встановлено, TTL лишено 5 с свідомо.

## 1. Сценарій захисту (процедура методички — 4 пункти)

Команди — з кореня репозиторію, у Git Bash. Перед захистом: Docker Desktop запущений, немає `docker-compose.override.yml`, у `load-tests/docker-compose.loadtest*.yml` стек **не** піднятий.

```bash
docker compose down -v && docker compose up -d --build     # ≈ 20 с зібраними образами; показати, що ручних кроків немає
curl -s localhost:8080/health
```

### Крок 1. Демонстрація реплікації — п. 1 процедури (≈ 1 хв)

```bash
python scripts/replication-check.py --pause
```

**Показує:** хто Primary, а хто standby; `pg_stat_replication` зі `streaming | async`; сід на обох вузлах; INSERT, UPDATE, DELETE через API доходять до репліки; запис у репліку відхилено.

**Сказати:** міграції й сід виконуються лише на Primary, а на репліці з'являються через WAL. `replayed in 230–380 ms` — це не затримка реплікації, а переважно час `docker compose exec`; справжня — `lag` у `pg_stat_replication`, мілісекунди.

### Крок 2. Stale Read і Read-After-Write — п. 2 процедури (≈ 1 хв)

```bash
python scripts/rw-routing-check.py --pause     # необов'язково: хто на який вузол іде; чекає 11 с статистику PostgreSQL
python scripts/stale-read-demo.py --pause
```

**Показує:** сторонній читач отримує 404, автор бачить опитування з Primary на обох інстансах, після TTL автор знову читає з репліки; без захисту автор сам отримує 404; затримка понад TTL — межа механізму.

**Сказати:** власна затримка на одній машині — мілісекунди, тому вмикаю керовану через `recovery_min_apply_delay`. Позначка в Redis, бо backend-и stateless і наступний запит може потрапити на інший. Скрипт перестворює backend-и, це ≈ 15 с: так перемикається `STICKY_TTL_SECONDS`.

### Крок 3. Симуляція відмов — п. 3 процедури (≈ 1 хв)

```bash
python scripts/db-failure-check.py --pause
```

**Показує:** три сценарії під потоком читань каталогу. Відмова репліки — 0 помилок, далі на Primary. Відмова Primary — 0 помилок читання, запис і логін 503 за мілісекунди. Обидва — `/health` 503.

**Сказати:** перший запис чекає 4–8 с (монітор ще не знає про відмову, EF повторює, Docker DNS шукає зупинений контейнер), наступні відмовляють миттєво. Backend-и ніде не перезапускались. Під час паузи можна показати http://localhost:8404/stats: вузли лишаються UP. За бажанням відкрити http://localhost:8080 і проголосувати в браузері.

### Крок 4. Порівняння і теорія — п. 4 процедури

Показати README «Порівняння» або [`lab6/load-comparison.md`](lab6/load-comparison.md). Наживо серію не запускати (≈ 95 хв). Якщо попросять живий короткий прогін:

```bash
export MSYS_NO_PATHCONV=1 OVERLAY=load-tests/docker-compose.loadtest-8cpu.yml
docker compose -f docker-compose.yml -f $OVERLAY up -d
bash load-tests/run.sh scenario-a-read demo LEVELS=10,50 STEP=20 WARMUP=5     # ≈ 1 хв
docker compose up -d                                                          # назад без лімітів
```

**Важливо сказати самому**, не чекаючи питання: приросту RPS немає, і чому; де саме репліка корисна; як слот спотворив першу серію і як я це знайшов.

Після захисту, якщо демо щось лишило: `docker compose up -d`, і перевірити `SHOW recovery_min_apply_delay` на репліці.

## 2. Теорія (п. 4 процедури)

### Синхронна, асинхронна, напівсинхронна реплікація

| Режим | COMMIT чекає | Втрата даних при падінні Primary | Вартість |
|---|---|---|---|
| **Асинхронна** (у нас) | лише власний WAL | можлива: те, що ще не дійшло до репліки (RPO > 0) | найменша затримка; Stale Read можливий |
| **Синхронна** | підтвердження репліки; у PostgreSQL `synchronous_standby_names` + `synchronous_commit` = `on` (записано на диск), `remote_apply` (відтворено) | немає для підтверджених транзакцій (RPO = 0) | затримка кожного запису; без репліки записи зупиняються |
| **Напівсинхронна** | щонайменше одна репліка отримала запис, але могла ще не відтворити; при таймауті відкат до асинхронної | менша, але не нуль | компроміс. Термін із MySQL; у PostgreSQL близько до `remote_write` або кворуму `ANY 1 (...)` |

**Чому в нас асинхронна:** завдання вивчає затримку, а синхронна зробила б падіння однієї репліки зупинкою всіх голосів. Навіть `remote_apply` прибрав би Stale Read лише ціною затримки кожного голосу.

### Split-Brain

Дві ноди одночасно вважають себе Primary й приймають записи: дані розходяться, і автоматично їх не об'єднати (два різні голоси, два різні лічильники). Виникає, коли мережа розділила вузли, і другий підняли, бо перший «наче мертвий». Захист: кворум (призначення лише більшістю), **fencing / STONITH** (старий лідер примусово зупиняється), номери епох, за якими запис старого лідера відхиляється.

**У нас неможливо за побудовою:** репліка не підвищується сама, вона лише read-only. Ціна — записи стоять, доки Primary не повернеться.

### CAP

Коли мережа розділена (P), система обирає: узгодженість (C, відмовити) чи доступність (A, відповісти, можливо, застарілим). Вибір робиться не на всю систему, а на операцію.

**У нас при втраті Primary:** запис і логін обирають **C** (503), каталог і деталі — **A** (відповідь із можливо застарілих даних). Застереження: зупинка контейнера — не зовсім розділення мережі, бо вузол справді лежить. Монітор не відрізнить одне від іншого.

### PACELC

Розширення CAP: **P**artition → **A** чи **C**, **E**lse (нормальна робота) → **L**atency чи **C**onsistency. CAP мовчить про нормальну роботу, а там теж є вибір.

**У нас:** асинхронна реплікація — це **EL**: COMMIT не чекає репліку, отже низька затримка в обмін на можливий Stale Read. Sticky Routing точково повертає C для автора запису ціною навантаження на Primary: сценарій C показує цю ціну в цифрах.

### Вибір нового лідера, Raft

Щоб автоматично призначити Primary, вузли мають домовитися. **Raft:**
- **Терми:** час поділено на номери епох; у кожному не більше одного лідера.
- **Heartbeat:** лідер регулярно шле серцебиття; послідовник без нього після випадкового таймауту стає кандидатом. Випадковий — щоб кандидати рідше ділили голоси.
- **Вибори:** кандидат збирає голоси **більшості**; вузол голосує раз на терм і лише за кандидата, чий журнал не старіший за власний. Тому новий лідер має всі закомічені записи.
- **Коміт:** запис закомічено, коли його прийняла більшість.
- **Кількість вузлів:** 2f + 1 витримують відмову f. Тому двох вузлів, як у нас, замало: кожен із них не може сам зібрати більшість.

**Як це роблять із PostgreSQL:** сам він виборів не робить. Patroni зберігає стан лідера в etcd (там Raft), підвищує репліку через `pg_promote()`, а старий Primary повертається як репліка через `pg_rewind`. У нас цього немає: завдання вимагає Read-Only Mode, а асинхронне підвищення втратило б непереданий хвіст WAL.

## 3. Питання на захист

**Де масштабування читання, якщо RPS не зріс?** Одна репліка такого самого розміру його не дає: сумарна робота та сама, а Primary простоює на 1–4 % CPU. Щоб зросла пропускна здатність, потрібні кілька реплік або читання ще й із Primary. Користь однієї репліки — ізоляція: під записом p95 читання вдвічі менший, запис +40 %.

**Чому не проксі (Pgpool, PgBouncer)?** PgBouncer лише пул з'єднань, він не маршрутизує за змістом. Pgpool розбирає SQL, але не знає, що `SELECT` перед голосом має бути свіжим, а такий самий у каталозі — ні. Класифікація — бізнес-знання, тому вона в застосунку.

**Чому Primary за замовчуванням?** Помилка в класифікації має коштувати навантаження, а не застарілих даних.

**Чому результати при MISS не з репліки?** Застарілий агрегат потрапив би у спільний кеш для всіх до кінця TTL. Виміряно: 6–11 застарілих раундів із 60 навіть без штучної затримки, на Primary 0. А без Primary читаю з репліки, але не пишу в кеш.

**Чому Sticky, а не LSN?** Простіше: Redis уже є, один middleware. LSN точніший (немає TTL, який треба вгадати), але потребує читання позиції WAL після кожного запису, місця для її передачі й порівняння перед кожним читанням. Якщо затримка регулярно перевищує TTL, LSN — наступний крок.

**Чому позначка в Redis, а не в пам'яті?** Наступний запит може потрапити на інший інстанс; це була б прихована прив'язка, яку прибрала лаба 2.

**Чому позначка ставиться в `OnStarting`?** Інакше клієнт міг би отримати відповідь і прочитати раніше, ніж позначка з'явиться.

**Redis лежить — що зі Sticky?** Не можна знати, чи писав користувач, тож автентифіковані читання на Primary. Анонімні лишаються на репліці, вони писати не могли.

**Чому TTL 5 с, якщо затримка доходила до 29.5 с?** До насичення максимум 206 мс. Секунди — лише вище насичення, де система вже перевантажена. Довший TTL не покриває 29 с і забирає ще більше читань із репліки. Критичні читання й так на Primary. Це записане обмеження, причину стрибків не встановлено: у двох діагностичних прогонах конфліктів відтворення не було, але й стрибок там не повторився.

**Навіщо монітор, якщо є повтори EF?** Без нього зупинена репліка давала 503 через 8.6–10.6 с, а записи без Primary чекали 13–19 с.

**Чому перевірка монітора без пулу?** Під навантаженням пул зайнятий, перевірка чекала б у черзі, і монітор оголосив би здоровий Primary мертвим у самому піку. Перевірено під навантаженням: 0 хибних спрацювань.

**Що таке `hot_standby_feedback`?** Репліка повідомляє Primary, які рядки ще читає, і він їх не чистить. Без цього довгі читання скасовувалися б через конфлікт із відтворенням WAL. Ціна — трохи більше роздуття таблиць на Primary.

**Навіщо слот і чому межа 1 ГБ?** Слот тримає WAL для зупиненої репліки, тож короткий простій не потребує нового `pg_basebackup`. Межа — щоб довгий простій не заповнив диск Primary; тоді репліку доведеться перестворити.

**Може голос подвоїтися при падінні Primary?** Ні. Клієнт може отримати 503 на закомічений голос, бо він не знає результату обірваної операції. Повтор дасть 409 або 200 через `UNIQUE(poll_id, user_id)`.

**Чому логін не працює без Primary?** Завдання відносить автентифікацію до строгих читань. Наявні JWT лишаються дійсними, вони не потребують БД.

**Чому чистий запис без реплікації швидший, а на 200 VU різниці майже немає?** WAL-sender працює на тому самому CPU Primary: −25 % на 10 VU. На 200 VU вузьке місце вже блокування рядків `vote_count`, і реплікація майже нічого не додає.

**Як довіряти цим числам?** Обмежено: ноутбук, сусідні потоки ділять фізичне ядро, 1–3 прогони, розкид у Single великий. Висновки — лише про великі різниці. Перша серія була неправильна: слот зупиненої репліки сповільнював запис у 1.6 раза. Знайшов, бо реплікація не може прискорювати запис, а цифри це показували.

## 4. Якщо демо зламалось

| Симптом | Що робити |
|---|---|
| `postgres-replica` постійно перезапускається | старий том до лаби 6: `docker compose down -v && docker compose up -d` |
| `stale-read-demo` показує 200 замість 404 | перевірити затримку: `docker compose exec -T postgres-replica psql -U polling -d polling -tAc "SHOW recovery_min_apply_delay"`; скрипт виставляє її сам |
| Після перерваного демо дивні застарілі відповіді | лишилась затримка: `ALTER SYSTEM RESET recovery_min_apply_delay`, потім окремо `SELECT pg_reload_conf()` на репліці |
| Усе 503 після `db-failure-check` | `docker compose start postgres postgres-replica`; скрипт робить це сам у `finally`, якщо його не перервати через закрите вікно |
| `FAIL ... ms` у `db-failure-check` | перевірка часу на завантаженій машині; закрити важкі програми, повторити. Код 503 важливіший за мілісекунди |
| Стек із лімітами після навантаження | `docker compose up -d` |
| Сторінка показує «Увійти» без Primary | очікувано: `/me` відповідає 503; токен лишається, після повернення Primary користувач знову в системі |
| Swagger: 500 на `POST /api/polls` без `options` | відома помилка з лаби 1 у валідаторі, не пов'язана з реплікацією; надсилай заповнене тіло |
