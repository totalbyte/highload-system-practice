# Лабораторна 7, пункт 2.5: решардинг і Consistent Hashing

Рішення — [ADR 0058](../ai/decisions/0058-resharding-model.md). Повторити: `python scripts/resharding-model.py --live`
(≈ 3 с, `--live` потребує піднятого стеку).

## Модель

Є K ключів (id опитувань) і функція `shard(key)`. Кластер росте з N до M шардів. Ключ переїжджає, якщо
`shard_N(key) ≠ shard_M(key)`. Найменше, що можна перенести, — частка даних, яка має опинитися на нових шардах:
**(M − N) / M**. Для 2 → 3 це 1/3.

**Наївний modulo.** Ключ лишається на місці лише тоді, коли `key mod N = key mod M`. Для M = N + 1 це виконується для
N ключів з кожних N·(N + 1) підряд, тож лишається 1/(N + 1), а **переїжджає N/(N + 1)**: 2 → 3 — 67 %, 3 → 4 — 75 %,
4 → 5 — 80 %. Що більший кластер, то ближче до 100 %. Хешування перед `% N` (`hash % N`) рівномірно розкидає ключі,
але не допомагає: переїжджає стільки ж, бо проблема саме в `% N`.

**Consistent Hashing.** Шарди і ключі — точки на одному колі (хеш від 0 до 2⁶⁴). Ключ належить першому шарду за
годинниковою стрілкою. Новий шард стає на коло і забирає ключі лише в сусіда до себе, решта ключів не рухаються. З
однією точкою на шард частки випадкові: одному шарду може дістатися велика дуга. Тому кожен шард ставить багато
**віртуальних вузлів** (тут 100 точок), і дуги усереднюються: переїжджає ≈ 1/M, навантаження рівне.

**Virtual Buckets** (стратегія за замовчуванням у нашому `ShardRouter`). Ключ → `hash(key) % 64` → бакет → шард за
таблицею. Кількість бакетів не змінюється ніколи, тож функція `hash % 64` теж. При розширенні змінюється лише таблиця:
новий шард забирає у старих стільки бакетів, скільки йому належить (64 / M), а переносяться тільки рядки цих бакетів.

## Результати на 100 000 id

Частка ключів, що переїжджають:

| Спосіб | 2 → 3 | 3 → 4 | 2 → 4 | 4 → 5 |
|---|---|---|---|---|
| key % N | 66.7 % | 75.0 % | 50.0 % | 80.0 % |
| hash % N | 66.3 % | 74.7 % | 49.9 % | 80.1 % |
| кільце, 1 віртуальний вузол | 63.6 % | 2.1 % | 65.6 % | 40.3 % |
| кільце, 100 віртуальних вузлів | 36.4 % | 25.2 % | 49.9 % | 18.8 % |
| Virtual Buckets, 64 | 32.6 % | 24.9 % | 50.1 % | 18.6 % |
| ідеал (M − N) / M | 33.3 % | 25.0 % | 50.0 % | 20.0 % |

Рівномірність після 2 → 3 (ідеал — 33.3 % на шард):

| Спосіб | Шард 0 | Шард 1 | Шард 2 | max / avg |
|---|---|---|---|---|
| key % N | 33.3 % | 33.3 % | 33.3 % | 1.00 |
| кільце, 1 віртуальний вузол | 18.8 % | 17.6 % | 63.6 % | 1.91 |
| кільце, 100 віртуальних вузлів | 30.6 % | 33.0 % | 36.4 % | 1.09 |
| Virtual Buckets, 64 | 34.6 % | 32.7 % | 32.6 % | 1.04 |

Modulo розподіляє ідеально, але при кожній зміні N переносить більшість даних. Кільце з однією точкою на шард переносить
випадкову частку (від 2 до 66 %) і дає перекіс: третій шард отримав 64 % ключів. Кільце зі 100 віртуальними вузлами
і бакети переносять майже ідеальну частку й лишаються рівними. Подвоєння 2 → 4 — окремий випадок: тут і modulo
переносить лише половину, бо кожен шард рівно ділиться навпіл.

перехід 2 → 3.

| Спосіб | Опитувань переїде | Рядків переїде |
|---|---|---|
| key % N | 189 (66.1 %) | 8822 (67.1 %) |
| hash % N | 200 (69.9 %) | 8989 (68.4 %) |
| кільце, 1 віртуальний вузол | 190 (66.4 %) | 8078 (61.5 %) |

З бакетами довелося б перенести вдвічі менше рядків, ніж із modulo.

## Як виглядав би решардинг бакетами

Переїзд бакета — це запис на два шарди, тобто той самий Cross-Shard запис з пункту 2.4. Його роблять кроками, як Saga,
щоб у будь-який момент кожне опитування читалося з одного місця:

1. Підняти новий шард (пару Primary + Replica, як Shard B) і застосувати міграції.
2. Для кожного бакета, що переїжджає: скопіювати його опитування з варіантами й голосами на новий шард.
3. Ненадовго заблокувати запис у ці бакети, докопіювати зміни, що з'явилися під час копіювання.
4. Змінити таблицю «бакет → шард» на всіх інстансах backend і зняти блокування.
5. Видалити старі рядки бакета зі старого шарду.

Таблиця бакетів у нашому `ShardRouter` поки задається по колу від кількості шардів; для справжнього решардингу її треба
зберігати явно (у конфігурації або на Shard A), щоб після кроку 4 вона змінювалася без зміни функції. У межах лаби
перенесення не реалізовано: модель вище показує, скільки даних воно зачепило б.
