## Головне рішення (ADR 0054)

- **Що шардуємо:** агрегат «опитування» — `polls` + `options` + `votes`. Це найбільша і найгарячіша частина даних:
  голосів у сотні разів більше, ніж користувачів, і саме вони дають навантаження на запис (лаба 5: вузьке місце —
  блокування рядка `options.vote_count`).
- **Shard Key:** `poll_id`. Голос, результати, деталі, «мій голос», публікація, закриття — кожна операція знає `poll_id`
  і йде рівно на один шард. Унікальність «один голос на опитування» `(poll_id, user_id)` і транзакція «голос + лічильник»
  лишаються локальними, тобто звичайними ACID-транзакціями одного вузла.
- **Не шардуємо:** `users` — мала таблиця, читається при логіні за email. Лежить на Shard A як «глобальна» таблиця.
- **Чому не інші ключі:** `votes.id` (сліпий сурогатний ключ) розкидає голоси одного опитування по всіх шардах —
  результати стають fan-out, а `UNIQUE (poll_id, user_id)` неможливо перевірити одним індексом. `user_id` — те саме для
  результатів, а голосування в гаряче опитування все одно б'є в один рядок лічильника. `creator_id` — низька Cardinality
  (у сіді 20 авторів) і «великий автор» = гарячий шард.

## Етап 1. Аналіз Dataset і Shard Key (2.1) — ✅

- ADR 0054: таблиця «операція → ключ → скільки шардів зачіпає» для `poll_id`, `user_id`, `votes.id`, `creator_id`.
- Що ламається при шардингу і як це обійти: JOIN `polls → users` (ім'я автора у списку) → денормалізоване
  `creator_username`; FK на `users` між вузлами неможливі → прибрати; автоінкремент `polls.id` на кожному шарді дасть
  однакові id → глобальна послідовність `poll_ids` на Shard A.

## Етап 2. Топологія і Shard Router (2.2) — ✅ (ADR 0055)

- Shard A = `postgres` + `postgres-replica` (як у лабі 6, плюс таблиця `users` і послідовність `poll_ids`).
  Shard B = `postgres-shard-b` + `postgres-shard-b-replica` — ті самі скрипти реплікації з параметром хоста.
- `Sharding/ShardRouter`: `poll_id → шард`, стратегії `range | modulo | hash | buckets` (перемикач `SHARD_STRATEGY`),
  `SHARD_COUNT=1` — конфігурація Single Node для порівняння.
- Кожен шард має свій Primary / Replica, `ReadDb` і монітор вузлів з лаби 6 працюють у межах шарду.
- Заголовок `X-Shard` (куди насправді пішов запит), `scripts/shard-routing-check.py`: нові опитування стабільно
  потрапляють на свій шард, у БД іншого шарду їх немає.
- Сід з `Buckets`: Shard A — 18 опитувань / 1937 голосів, Shard B — 32 / 3659. Створення опитування торкається й Shard A
  (послідовність id), тому для опитування з B заголовок `A,B`.
- Лишилось: скрипти лаб 2–6, що читають БД напряму (`kill-test`, `load`, `redis-outage-check`, `replication-check`,
  `db-failure-check`, `series*.sh`), мають питати шард опитування.

## Етап 3. Розподіл даних і Hot Shard (2.3) — ✅ (ADR 0056, звіт [`hot-shard.md`](hot-shard.md))

- `scripts/shard-distribution.py`: Data Distribution Matrix (записи, частка даних, частка записів) для кожної стратегії.
- Hot Shard: стратегія `range` (діапазони id = «часовий інтервал») — усі нові опитування й голоси в них ідуть на
  останній шард. k6-прогін + CPU / пам'ять шардів із `docker stats`: затримки ростуть на одному вузлі, другий простоює.
- Оптимізація: `hash` / `buckets` вирівнюють навантаження; графік до / після.
- Окремо — межа методу: одне вірусне опитування (hot key) не розкласти жодним хешем; що тоді робити (кеш з лаби 4,
  розщеплений лічильник).
- Виміряно: Range — 100 % трафіку на Shard B, CPU B 99 %, A 1–3 %, ≈ 520 RPS; Buckets — 47 / 53 %, ≈ 1000 RPS,
  p95 на 10–50 VU нижчий. Матриця (живі дані): записи 55.6 / 44.4 % за X-Shard і 55.1 / 44.9 % за PostgreSQL.
- Скрипти лаб 2–6 переведено на шарди (`kill-test`, `load`, `redis-outage-check`, `replication-check --shard`,
  `series*.sh`, `env-spec.sh`); у `db-failure-check` крок «обидва вузли лежать» переглянути в етапі 4.

## Етап 4. Cross-Shard запити і транзакції (2.4)

- Scatter-Gather: каталог `GET /api/polls` — паралельний запит до всіх шардів, злиття за `created_at`, сторінка і
  сума `totalCount`. Порівняння з shard-local `GET /api/polls/{id}`: латентність і кількість запитів до БД.
- Cross-shard запис: розбір на прикладі нашого домену (видалення акаунта: голоси на всіх шардах + `users` на Shard A) —
  чому локальна транзакція не допомагає, 2PC проти Saga; голосування перепроєктоване як шард-локальний агрегат.

## Етап 5. Решардинг і Consistent Hashing (2.5)

- `scripts/resharding-model.py`: частка ключів, що переїжджають при 2 → 3 → 4 шардах для `key % N`, кільця з
  віртуальними вузлами і Virtual Buckets; формули в README.
