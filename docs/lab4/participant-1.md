# Лабораторна 4 (Distributed Caching) — Учасник 1: кеш результатів, інвалідація, fallback

> Вимоги: [`docs/labs/Lab4 - Distributed Caching.md`](../labs/Lab4%20-%20Distributed%20Caching.md). У дужках біля
> кожної задачі — пункт методички, який вона закриває.

## Коротко

- **Хто:** лабу 4 за домовленістю учасників виконує **Учасник 1 повністю**, включно з модулем `Results/`, який у
  лабах 1–3 належав Учаснику 2. Учасник 2 — рев'ю PR і питання на захисті про всю систему, як і раніше.
- **Зона:** обґрунтування вибору ендпоінта, схема ключів і TTL, Cache-Aside з інвалідацією без гонки, `X-Cache`,
  cold vs hot latency, fallback на БД при недоступному Redis, документація і сценарій захисту.
- **Що вже є з лаби 2:** Redis у спільній мережі, `ResultsCache` поверх спільного `IConnectionMultiplexer`, Cache-Aside
  для `GET /results` у найпростішому вигляді, інвалідація `DEL` при vote / publish / close / delete (ADR 0026, 0027).
  Лаба 4 доводить це до вимог методички, а не будує з нуля.

## Домовленості

- **Гілка:** `lab4/caching` → PR у `main`, рев'ю — Учасник 2. Перед PR підтягнути свіжий `main`.
- **ADR:** з 0041 поспіль. Зміни рішень лаби 2 — новими ADR зі статусом `Superseded by` / `amended by` у старих.
- **Межі файлів:** один виконавець, тож поділу файлів немає; правила з `CLAUDE.md` і `src/PollingPlatform.Api/CLAUDE.md`
  (тонкі контролери, коментарі українською, транзакції в execution strategy) діють як завжди.

## Межі лаби 4 — чого не робимо

- **Захист від Cache Stampede** (single-flight, розподілений lock, probabilistic early expiration) — **відкладено
  свідомо**, рішення Учасника 1 від 2026-11-02. На захисті пояснюємо теорію і показуємо, де саме stampede виникає в нас
  (кожен голос у гаряче опитування скидає кеш, і всі читачі одночасно йдуть у БД). **Нагадати** перед П1-8 і в П1-9 —
  можливо, все ж додати мінімальний варіант.
- **Кеш on/off для порівняльних прогонів, k6, ramp-up** — лаба 5.
- **Кешування інших ендпоінтів** — ні: критерій оцінювання «кешування лише відповідних read-intensive операцій»;
  чому саме так — у П1-1.
- **Rate limiting у Redis** (з дизайн-документа) — не вимога жодної лаби, не робимо.

## Задачі

### П1-1. Аналіз і вибір об'єкта кешування (2.1) — ≈20–30 хв

- Таблиця кандидатів (`/results`, `GET /polls/{id}`, `GET /polls`, `/auth/me`, а також що не кешується в принципі)
  за критеріями методички: частота читання vs запису, допустима застарілість, вартість запиту, кількість варіантів
  ключа і точок інвалідації.
- Висновок і чесна примітка: сам SQL для `/results` дешевий (денормалізований `vote_count`), головний виграш — не
  забирати з'єднання з пулу під час піку голосування (bottleneck №3) і не конкурувати з транзакціями голосів.

- [x] ADR 0041 (розділ про вибір).

### П1-2. Схема ключів і політика TTL (2.4) — ≈20–30 хв

- Шаблон ключа, вільний від колізій, з урахуванням усіх параметрів відповіді; версія формату значення.
- Механізм інвалідації без гонки «агрегат порахований до коміту, записаний після `DEL`» — покоління (generation) в
  ключі.
- TTL за статусом опитування (active / draft / closed) + jitter проти Cache Avalanche; межа застарілості, якщо
  інвалідація не вдалася.

Готово, коли:

- [x] ADR 0041 (ключі, покоління, TTL);
- [x] Учасник 1 погодив схему (2026-11-02).

### П1-3. Cache-Aside з поколіннями і TTL за статусом (2.3, 2.4, 2.5) — ≈45–60 хв

- `ResultsCache`: читання покоління і значення за один round-trip (Lua-скрипт), запис під поколінням, прочитаним
  **до** звернення до БД; інвалідація — `INCR` покоління (+ `UNLINK` попереднього значення), не `DEL`.
- TTL і jitter за ADR 0041; `ResultsService` нічого не знає про ключі.
- Усі чотири точки інвалідації (vote, publish, close, delete) лишаються; публічний API `ResultsCache` по можливості
  не змінюється, щоб `PollService` / `VoteService` не чіпати.
- ADR 0041 → `Accepted`; ADR 0026 → `amended by 0041`.

Готово, коли:

- [x] MISS → HIT → голос → MISS зі свіжими даними → HIT, через обидва інстанси (однаковий `generatedAt`);
- [x] гонку відтворено «до» і її немає «після» — `scripts/cache-race-check.py`: `DEL` — 2–5 застарілих раундів з 60
  у кожному з 5 прогонів, покоління — 0 з 60 у 5 прогонах;
- [x] `TTL` у `redis-cli`: draft 11 с, closed 3906 с; `concurrency-checks.py`, `cross-instance.sh` 8/8,
  `redis-outage-check.py` зелені.

### П1-4. `X-Cache` і логування (2.6.1) — ≈20–30 хв

- Заголовок `X-Cache: HIT | MISS | BYPASS` (BYPASS — Redis недоступний, П1-5) на `GET /results`.
- Лог інвалідації (який ключ / покоління); HIT / MISS — на рівні `Debug`, щоб не засмічувати лог під навантаженням.
- `capture response header X-Cache` у HAProxy — у `docker compose logs lb` джерело даних видно поруч з інстансом і
  часом відповіді.

Готово, коли:

- [x] заголовок видно в `curl -i` і в лозі HAProxy (`{HIT}` / `{MISS}`); Swagger описує його в `remarks`; ADR 0042.

### П1-5. Fallback на БД при недоступному Redis (2.6.3) — ≈30–45 хв

- Fail-fast клієнта Redis замість ~5 с очікування в backlog (ADR 0027): налаштування з'єднання в `Program.cs`.
- `GetAsync` при недоступному Redis → читання прямо з БД, `X-Cache: BYPASS`, **200** замість 503. Запис і
  інвалідація лишаються best-effort.
- Новий ADR замість 0027 (`Superseded by`); `/health` як і раніше не перевіряє Redis (ADR 0021) — вузли лишаються в
  пулі.
- `scripts/redis-outage-check.py` — під нову поведінку (лаби 2 і 3 захищені, стара поведінка більше не потрібна).

Готово, коли:

- [x] `docker compose stop redis` → `GET /results` 200 з `BYPASS` за 68 мс (було 503 за 5.2 с), голос 201 за 197 мс і
  видно в наступному читанні, publish працює, `/health` 200; `start redis` → MISS (Redis порожній) без рестарту backend;
- [x] межу застарілості після невдалої інвалідації записано в ADR 0043; збереження Redis на диск вимкнене — без цього
  після рестарту повертався застарілий запис (контрольний прогін: HIT з `totalVotes=0`).
