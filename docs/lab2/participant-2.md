## Межі лаби 2 — чого не робимо

Правило проєкту: не робити покращень раніше за лабу, яка їх вимагає.

- **Лаба 3:** Nginx/HAProxy, єдина точка входу, алгоритми балансування. У лабі 2 клієнт сам обирає інстанс за портом.
- **Лаба 4:** схема ключів `domain:entity:id`, обґрунтування TTL, `X-Cache: HIT/MISS`, заміри cold/hot latency,
  fallback на БД при падінні Redis, захист від cache stampede, виправлення гонки інвалідації. У лабі 2 кеш
  переїжджає в Redis «як є»: ключ `results:{pollId}`, TTL 10 с, інвалідація при голосі, publish, close і delete.
- **Лаба 5:** k6, навантажувальні сценарії, заміри пропускної здатності.

### П2-5. Stateless Request Flow для `POST /api/polls/{id}/vote` (2.3) — ≈20–30 хв, можна починати одразу

Методичка вимагає для одного ключового сценарію зафіксувати чотири речі. Наш сценарій — голосування (high-load
сценарій проєкту):

| Вимога 2.3 | Що показуємо |
|---|---|
| Вхідні параметри / context token | `Authorization: Bearer <JWT>` → `userId` з claim `sub` (перевірка підпису, без сховища сесій); `pollId` з маршруту; `{optionId}` з тіла. Запит може прийти на будь-який інстанс |
| Вичитування контексту зі shared storage | PostgreSQL: опитування (статус, `startsAt` / `endsAt`, `allowVoteChange`), належність варіанта до опитування |
| Атомарні зміни у зовнішньому сховищі | одна транзакція PostgreSQL у execution strategy: існуючий голос `FOR UPDATE` → INSERT або зміна голосу → `vote_count ± 1` у порядку id варіантів → COMMIT; після коміту — видалення `results:{pollId}` у Redis |
| Відсутність залишкових мутацій у пам'яті | `VoteService` і `AppDbContext` scoped — знищуються після відповіді; `static`-полів і singleton з даними немає; наступний запит того ж користувача може піти на інший інстанс |

### П2-6. Паралельне голосування на двох інстансах (2.2, 2.5) — ≈20–30 хв

1. багато різних користувачів голосують в одне опитування одночасно → усі 201, жодного 5xx;

### П2-7. Втрата інстансу під час голосування (2.5, §4) — ≈45–70 хв

Методичка: аварійна зупинка (`docker stop/kill`) одного інстансу **під час операцій**, потім довести, що бізнес-стан
цілий, а другий інстанс підхопив обробку.

Скрипт `scripts/kill-test.py` (Python + `ThreadPoolExecutor`, як перевірки з runbook):

1. Створити й опублікувати свіже опитування P з `allowVoteChange: false`; залогінити 200–300 сід-користувачів.
2. Паралельно голосувати, запити по черзі на backend-1 / backend-2.
3. Посеред прогону — `docker compose kill backend-1` (аварійна зупинка; окремо можна показати `docker compose stop`).
4. Клієнт при помилці з'єднання або таймауті з backend-1 повторює той самий запит на backend-2 (у лабі 3 це робитиме
   балансувальник).
5. Після прогону перевірити:
   - кожен користувач отримав 201 або, при повторі, 409 — голос записано рівно один раз;
   - `SELECT count(*) FROM votes WHERE poll_id = P` = кількість користувачів з успішним голосом;
   - запит узгодженості лічильників per option → 0;
   - `GET …/results` через backend-2 збігається з БД.
6. Повернення інстансу: зафіксувати, чи Docker піднімає контейнер сам (`restart: unless-stopped`); якщо ні —
   `docker compose start backend-1`. Далі `/health` = 200 і `GET …/results` через backend-1 дає ті самі числа —
   жодного «прогріву» стану.

Пояснення для захисту: транзакція на вбитому інстансі обривається разом із з'єднанням, і PostgreSQL її відкочує —
голосу без лічильника не буває, бо обидві зміни в одній транзакції (ADR 0014). Якщо коміт встиг, а відповідь
загубилась, повтор на іншому інстансі отримує 409 — подвійного голосу немає завдяки `UNIQUE(poll_id, user_id)`.

## Теорія до захисту

Питають обох і про всю систему.

**Stateless ≠ «без даних».** Даних у системі багато, але між запитами їх немає в пам'яті процесу backend: бізнес-стан
— у PostgreSQL (опитування, голоси, `vote_count`), спільні тимчасові дані — у Redis (кеш результатів, ключі
DataProtection), ідентичність користувача — у JWT на боці клієнта. Тому будь-який інстанс можна вбити, перезапустити
або додати без втрати даних і без «прогріву».

**Ризики прихованої affinity** — коли запит мовчки залежить від конкретного інстансу:

- локальний кеш — інстанси віддають різні дані (наше демо «до», П2-2);
- sticky sessions — маскують локальний стан; при падінні вузла користувач втрачає сесію; навантаження розподіляється
  нерівно;
- різні секрети чи ключі на інстансах (JWT-секрет, ключі DataProtection) — токен або cookie працює лише там, де виданий;
- файли в контейнері (завантаження, ключі, файлові сесії) — зникають разом з контейнером і невидимі іншим;
- лічильники й rate limit у пам'яті — кожен інстанс рахує своє, ліміт фактично множиться на N;
- блокування в процесі (`lock`, `SemaphoreSlim`) не серіалізують запити між інстансами — тому зміни голосу
  серіалізуються в PostgreSQL (`FOR UPDATE`, ADR 0017), а сід — через `pg_advisory_xact_lock`;
- фонові задачі й таймери — виконуються на кожному інстансі (дублювання) або залежать від одного;
- довгі з'єднання (WebSocket/SSE для лайв-дашборду) прив'язані до інстансу — потрібен backplane (наприклад, Redis pub/sub).

**Механізми консистентності в нашій системі:** транзакція PostgreSQL (голос і лічильник разом),
`UNIQUE(poll_id, user_id)` (один голос, навіть якщо повтор прийшов на інший інстанс), `FOR UPDATE` для змін голосу,
інвалідація кешу в Redis після коміту і TTL 10 с як страховка. Відома межа: результат, порахований до коміту голосу,
може потрапити в кеш уже після інвалідації — застарілість до 10 с (тема лаби 4).

## Що знати про частину Учасника 1

- Compose: `redis` + `backend-1` / `backend-2` з одного образу, порти 8080 / 8082, `INSTANCE_ID` (П1-1).
- Чому два інстанси не ламають міграції й сід на чистій БД: результат П1-2 і advisory lock сіду (ADR 0009).
- JWT: чому токен, виданий backend-1, працює на backend-2 — сесій немає, секрет спільний з env (ADR 0006).
- DataProtection: що це, чому ключі у файловій системі контейнера — прихований стан, куди їх винесли (П1-3).
- Бюджет з'єднань: 2 × 30 = 60 ≤ 97 (ADR 0018); що зміниться при 3–4 інстансах у лабі 3.
- C4 Component Diagram (П1-6) і cross-instance ланцюжок (П1-5) — на захисті їх показуватимете обидва.
