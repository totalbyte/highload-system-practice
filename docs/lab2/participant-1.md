**Інфраструктурний контракт (дає П1-1, використовує Учасник 2):**

- Redis — сервіс `redis` у мережі `app-network`, порт 6379; рядок підключення `ConnectionStrings:Redis`
  (у compose — `ConnectionStrings__Redis: redis:6379,abortConnect=false`).
- У DI зареєстровано один `IConnectionMultiplexer` (singleton) — спільний для кешу результатів і ключів DataProtection.
- Інстанси: `backend-1` → http://localhost:8080, `backend-2` → http://localhost:8082 (8081 зайнятий Adminer);
  заголовок `X-Instance-ID: backend-1` / `backend-2`.
- Після П1-1 застосунок **ще не пише в Redis**: кеш результатів лишається в пам'яті процесу, щоб Учасник 2 встиг
  показати проблему «до» (П2-2).

## Межі лаби 2 — чого не робимо

Правило проєкту: не робити покращень раніше за лабу, яка їх вимагає.

- **Лаба 3:** Nginx/HAProxy, єдина точка входу, алгоритми балансування. У лабі 2 клієнт сам обирає інстанс за портом.
- **Лаба 4:** схема ключів `domain:entity:id`, обґрунтування TTL, `X-Cache: HIT/MISS`, заміри cold/hot latency,
  fallback на БД при падінні Redis, захист від cache stampede, виправлення гонки інвалідації. У лабі 2 кеш
  переїжджає в Redis «як є»: ключ `results:{pollId}`, TTL 10 с, інвалідація при голосі, publish, close і delete.
- **Лаба 5:** k6, навантажувальні сценарії, заміри пропускної здатності.

## Задачі Учасника 1

### П1-1. Redis і два інстанси backend (2.4) — гілка `lab2/p1-infra`, ≈30–40 хв

Що зробити:

- `docker-compose.yml`:
  - сервіс `redis`: закріплена версія образу (як pgAdmin, ADR 0020), healthcheck `redis-cli ping`, мережа
    `app-network`, порт на хост `${REDIS_PORT:-6379}` — для `dotnet run` (як Postgres на 5433, ADR 0011);
  - замість одного `backend` — `backend-1` і `backend-2` з **одного образу** й однакової конфігурації (YAML-якір),
    відрізняються лише `INSTANCE_ID` і портом: `backend-1` → `${API_PORT:-8080}`, `backend-2` → `${API2_PORT:-8082}`;
    образ збирається один раз;
  - `depends_on`: `postgres` і `redis` — `service_healthy`;
  - `ConnectionStrings__Redis: redis:6379,abortConnect=false` (backend стартує, навіть якщо Redis ще не готовий).
- `Program.cs`: один `IConnectionMultiplexer` (singleton) з `ConnectionStrings:Redis`, пакет `StackExchange.Redis`;
  у `appsettings.json` — рядок для `localhost`.
- `/health` у лабі 2 Redis **не перевіряє**: інакше в лабі 3 падіння Redis змусить балансувальник вимкнути всі інстанси.
- `.env.example`: `API2_PORT`, `REDIS_PORT`.
- Каркас розділу README «Лабораторна 2» з підрозділами і позначкою власника кожного (аудит — дві частини,
  усунені залежності, Request Flow, мульти-інстансне розгортання, cross-instance перевірка, відмовостійкість), щоб
  далі кожен писав у свій підрозділ без конфліктів.
- ADR: Redis + два інстанси, порти, `/health` без Redis.

Готово, коли:

- [ ] `docker compose down -v && docker compose up -d --build` піднімає postgres, redis і обидва backend **без ручних
      кроків** (обов'язкова вимога курсу);
- [ ] `curl -i localhost:8080/health` → 200 і `X-Instance-ID: backend-1`; `localhost:8082` → `backend-2`;
- [ ] `docker compose exec redis redis-cli ping` → `PONG`;
- [ ] кеш результатів ще в пам'яті процесу (Redis лише підключений) — не випереджаємо П2-3;
- [ ] smoke test з runbook проходить на 8080.

### П1-2. Одночасний старт двох інстансів на чистій БД (2.4) — та сама гілка, ≈20–30 хв (+≈40 хв, якщо потрібен окремий сервіс міграцій)

[ADR 0009](../ai/decisions/0009-startup-migrations-and-seed-locking.md) прямо позначає це як неперевірене: два
інстанси одночасно виконують `MigrateAsync` і сід.

Що зробити:

- 3–5 разів `docker compose down -v && docker compose up -d`, переглянути `docker compose logs backend-1 backend-2`.
- Якщо інстанси конфліктують на міграціях: окремий одноразовий сервіс `migrator` з того самого образу (режим «лише
  міграції й сід, потім вихід»); backend-и стартують після нього (`condition: service_completed_successfully`) з
  `Database__MigrateOnStartup=false` і `Seed__Enabled=false`.
- Результат (є гонка чи ні) — новий ADR; в ADR 0009 змінити лише статус (`Amended by …`), текст не переписувати.

Готово, коли:

- [ ] кожен холодний старт: обидва інстанси healthy, у логах немає помилок міграцій;
- [ ] `SELECT count(*) FROM users` = 500, `SELECT count(*) FROM polls` = 50 — сід виконався рівно один раз;
- [ ] у `__EFMigrationsHistory` немає дублікатів.

### П1-3. Ключі DataProtection — у спільне сховище (2.1 категорія 3, 2.2) — гілка `lab2/p1-platform`, ≈15–20 хв

Зараз кожен контейнер генерує власні ключі DataProtection у своїй файловій системі — це файловий стан, прив'язаний
до інстансу: усе, що захищене ними на одному інстансі (cookie, antiforgery-токени), інший не розшифрує. Ми
DataProtection зараз не використовуємо, але саме такий прихований стан шукає аудит (попередження про ключі видно в
логах, див. runbook).

Що зробити:

- `AddDataProtection().SetApplicationName(...)` з однаковою назвою на всіх інстансах +
  `PersistKeysToStackExchangeRedis(<IConnectionMultiplexer з П1-1>, "DataProtection-Keys")`; пакет
  `Microsoft.AspNetCore.DataProtection.StackExchangeRedis`. Код — окремим блоком у `Program.cs`, не поруч з
  реєстрацією кешу (там працює Учасник 2).
- Альтернатива — PostgreSQL (`PersistKeysToDbContext`, потребує EF-міграції). Вибір і причина — ADR.
- Прибрати рядок про DataProtection з «known quirks» у `docs/ai/runbook.md`.

Готово, коли:

- [ ] у логах обох інстансів немає попередження, що ключі не зберігаються поза контейнером;
- [ ] у Redis є ключ `DataProtection-Keys`, і після рестарту інстансу він не генерує новий.

### П1-4. Аудит стану платформної частини (2.1) — ≈20–30 хв

Пройти `Program.cs`, `Auth/`, `Polls/`, `Data/`, `Common/` (крім `ErrorHandling/`), `Dockerfile`, compose і віднести
кожен елемент до однієї з трьох категорій методички. Орієнтовний перелік — **перевірити по коду**, не переносити
навмання:

| Елемент | Категорія | Чому |
|---|---|---|
| Автентифікація (JWT, `JwtTokenService`) | Shared / Externalized | серверних сесій немає: ідентичність — у підписаному токені на клієнті (ADR 0006), секрет — спільна конфігурація з env |
| `Jwt:Secret` | Shared (конфігурація) | однаковий на всіх інстансах; якби кожен генерував свій, токен з backend-1 давав би 401 на backend-2 — приклад прихованої affinity |
| `PasswordHasher`, `TimeProvider` (singleton) | Ephemeral / Local Safe | не зберігають даних між запитами |
| `InstanceIdentity` | Ephemeral / Local Safe | навмисно різний на кожному інстансі — діагностика |
| Статичний `Topics` у `DataSeeder` | Ephemeral / Local Safe | незмінні константи |
| Сід під `pg_advisory_xact_lock` | Shared | блокування в PostgreSQL, а не в процесі (не application-level lock) |
| Життєвий цикл опитувань (`PollService`) | Shared | стан у PostgreSQL, переходи — умовні UPDATE/DELETE (ADR 0004) |
| Пул з'єднань Npgsql | Ephemeral / Local Safe | інфраструктура процесу; бюджет 2 × 30 = 60 ≤ 97 (ADR 0018) |
| Логи (stdout контейнера) | Ephemeral / Local Safe | діагностика, не бізнес-стан |
| Ключі DataProtection у файловій системі контейнера | Critical | усунено в П1-3 |

Окремо довести, що сесій немає: логін на `backend-1`, той самий токен на `backend-2` → `GET /api/auth/me` = 200.

Готово, коли:

- [ ] рядки внесено в підрозділ «Аудит стану — платформа» README;
- [ ] для кожного `static` / singleton у своїх модулях є пояснення, чому він безпечний (знадобиться в С-4).

### П1-5. Cross-Instance Consistency (2.5, §3) — ≈40–50 хв

Методичка: послідовний ланцюжок «POST → Instance 1, GET → Instance 2, PUT → Instance 2, GET → Instance 1» з
підтвердженням актуальності даних **без sticky sessions**. PUT у нашому API немає — його роль виконують `PATCH
…/publish` і `PATCH …/close`. Ланцюжок покриває і опитування, і голоси з результатами — кожен крок друкує
`X-Instance-ID` і ключове поле відповіді:

| # | Запит | Інстанс | Очікування |
|---|---|---|---|
| 1 | `POST /api/auth/login` | backend-1 | 200, токен |
| 2 | `POST /api/polls` (`allowVoteChange: true`) | backend-1 | 201, `draft`, id = P |
| 3 | `GET /api/polls/{P}` (той самий токен) | backend-2 | 200, `draft` — токен від іншого інстансу прийнято |
| 4 | `PATCH /api/polls/{P}/publish` | backend-2 | 200, `active` |
| 5 | `GET /api/polls/{P}` | backend-1 | `active` — свіжі дані |
| 6 | `GET /api/polls/{P}/results` | backend-1 і backend-2 | `totalVotes = 0` на обох (навмисно «прогріває» кеш обох) |
| 7 | `POST /api/polls/{P}/vote` (варіант 1) | backend-1 | 201 |
| 8 | `GET /api/polls/{P}/results` | backend-2, потім backend-1 | одразу `totalVotes = 1` на обох |
| 9 | `POST /api/polls/{P}/vote` (варіант 2) | backend-2 | 200 — голос змінено |
| 10 | `GET /api/polls/{P}/results` | backend-1 | голос уже на варіанті 2 |
| 11 | `PATCH /api/polls/{P}/close` → `GET …/results` | backend-1 → backend-2 | `closed` |
| 12 | нова чернетка: `POST` → `DELETE` → `GET` | backend-2 → backend-1 → backend-2 | 201 → 204 → 404 |
| 13 | опитування з `allowVoteChange: false`: голос → повтор | backend-1 → backend-2 | 201 → 409: дубль ловить БД, а не пам'ять інстансу |

Клієнт не надсилає cookies і сам обирає інстанс — sticky sessions немає.

Результат:

- `requests/cross-instance.http` (змінні `@i1 = http://localhost:8080`, `@i2 = http://localhost:8082`) — для
  REST Client / Rider / Postman;
- `scripts/cross-instance.sh` (curl, Git Bash): перевіряє очікування і виходить з ненульовим кодом при розбіжності;
  токен очищати від `\r` (див. runbook).

Готово, коли:

- [ ] скрипт проходить на холодному старті **після мерджу П2-3**. До нього кроки 8 і 10 падають протягом 10 с — це
      очікувано: саме цю проблему виправляє Учасник 2;
- [ ] приклад виводу з `X-Instance-ID` — у README.

### П1-6. Архітектурна схема та інструкція розгортання (2.6, §3) — ≈25–35 хв

- **C4 Component Diagram** — методичка вимагає саме рівень компонентів. Два однакові контейнери
  `backend-1` / `backend-2`, усередині — компоненти: контролери Auth / Polls / Votes / Results → сервіси →
  `ResultsCache` (клієнт Redis), `AppDbContext` (пул Npgsql), валідація JWT, DataProtection. Зовнішні сховища:
  PostgreSQL (користувачі, опитування, варіанти з `vote_count`, голоси) і Redis (кеш результатів, ключі
  DataProtection). Підписати, що в інстансах немає стану між запитами і що клієнт звертається до інстансу напряму за
  портом. Mermaid, як решта схем README; компоненти голосування й результатів погодити з Учасником 2.
- README «Мульти-інстансне розгортання»: запуск, порти інстансів, як звернутися до конкретного інстансу, як побачити
  `X-Instance-ID`, як зупинити, вбити і повернути інстанс, як заглянути в Redis (`redis-cli`).
- README: оновити «Швидкий старт», RACI (рядки лаби 2), структуру репозиторію (`scripts/`, `docs/lab2/`).
- `docs/ai/runbook.md` (запуск двох інстансів, Redis) і `docs/ai/contracts.md` (інстанси, порти, Redis).

## Теорія до захисту

Питають обох і про всю систему.

**Stateless ≠ «без даних».** Даних у системі багато, але між запитами їх немає в пам'яті процесу backend: бізнес-стан
— у PostgreSQL (опитування, голоси, `vote_count`), спільні тимчасові дані — у Redis (кеш результатів, ключі
DataProtection), ідентичність користувача — у JWT на боці клієнта. Тому будь-який інстанс можна вбити, перезапустити
або додати без втрати даних і без «прогріву».

**Ризики прихованої affinity** — коли запит мовчки залежить від конкретного інстансу:

- локальний кеш — інстанси віддають різні дані (наше демо «до», П2-2);
- sticky sessions — маскують локальний стан; при падінні вузла користувач втрачає сесію; навантаження розподіляється
  нерівно;
- різні секрети чи ключі на інстансах (JWT-секрет, ключі DataProtection) — токен або cookie працює лише там, де виданий;
- файли в контейнері (завантаження, ключі, файлові сесії) — зникають разом з контейнером і невидимі іншим;
- лічильники й rate limit у пам'яті — кожен інстанс рахує своє, ліміт фактично множиться на N;
- блокування в процесі (`lock`, `SemaphoreSlim`) не серіалізують запити між інстансами — тому зміни голосу
  серіалізуються в PostgreSQL (`FOR UPDATE`, ADR 0017), а сід — через `pg_advisory_xact_lock`;
- фонові задачі й таймери — виконуються на кожному інстансі (дублювання) або залежать від одного;
- довгі з'єднання (WebSocket/SSE для лайв-дашборду) прив'язані до інстансу — потрібен backplane (наприклад, Redis pub/sub).

**Механізми консистентності в нашій системі:** транзакція PostgreSQL (голос і лічильник разом),
`UNIQUE(poll_id, user_id)` (один голос, навіть якщо повтор прийшов на інший інстанс), `FOR UPDATE` для змін голосу,
інвалідація кешу в Redis після коміту і TTL 10 с як страховка. Відома межа: результат, порахований до коміту голосу,
може потрапити в кеш уже після інвалідації — застарілість до 10 с (тема лаби 4).

## Що знати про частину Учасника 2

- Кеш результатів: був `IMemoryCache` у кожному процесі → став Redis (П2-3); ключ `results:{pollId}`, TTL 10 с,
  ключ видаляється після коміту голосу і при publish / close / delete.
- Голос: одна транзакція PostgreSQL — існуючий голос `FOR UPDATE` → INSERT або зміна голосу → `vote_count ± 1`
  у порядку id варіантів (ADR 0014, 0017). Вміти пройти Request Flow `POST /vote` по кроках (П2-5).
- Тест втрати інстансу (П2-7): чому не буває «половинчастого» стану (голос без лічильника) і подвійних голосів.
- Redis недоступний → що відповідає API (ADR Учасника 2, П2-4); повний fallback на БД — лаба 4.
