## 0. Шпаргалка за одну хвилину

- **Інструмент:** k6 1.3.0 у Docker, усередині мережі стеку, на 8 окремих ядрах; кожен компонент системи — на своїх
  ядрах з лімітами (ADR 0045). Кожен прогін — з чистої БД (ADR 0047).
- **Сценарії:** A — читання (результати, деталі, каталог), B — голосування в гаряче опитування, C — наскрізний
  сценарій (каталог → деталі → голос → результати, іноді повний цикл опитування).
- **Профіль:** warm-up 20 с → 10 → 25 → 50 → 100 → 200 VU по 40 с.
- **Насичення:** A ≈ 50 VU (≈ 3.7k RPS), B ≈ 10 VU (≈ 470 RPS, далі RPS **падає**), C ≈ 400 VU (≈ 1.5k RPS).
- **Вузьке місце:** блокування рядків `options.vote_count` гарячого опитування при записі (до 70 сесій у `Lock`);
  для читання — CPU backend-ів, далі CPU PostgreSQL.
- **Scale-out:** читання E(2) = 0.86, E(3) = 0.72; запис — від'ємне масштабування (365 → 276 → 229 RPS).
- **Кеш:** вимкнений кеш = +55 % транзакцій PostgreSQL, −28 % RPS, p95 +58 %.
- **Помилок 0** на всіх ступенях: перевантаження видно в затримках. Відкрита модель на 1 200 запитів/с — 75 %
  запланованих запитів навіть не відправлено.

## 1. Сценарій захисту (процедура методички — 4 пункти)

Команди — з кореня репозиторію, у Git Bash. Перед захистом: Docker Desktop запущений, немає
`docker-compose.override.yml`.

```bash
export MSYS_NO_PATHCONV=1
C="-f docker-compose.yml -f load-tests/docker-compose.loadtest.yml"
docker compose down -v && docker compose $C up -d --build     # ≈ 30 с; стек з лімітами й закріпленими ядрами
bash load-tests/env-spec.sh                                   # показати конфігурацію середовища
```

### Крок 1. Запуск тесту зі ступеневим нарощуванням — п. 1 процедури (≈ 5 хв)

```bash
bash load-tests/run.sh scenario-b-write demo        # або коротше: ... demo LEVELS=10,50,200 STEP=20
```

Поки йде тест — відкрити http://localhost:8404/stats (запити по вузлах) і показати, що k6 пише ступені. Наприкінці
k6 друкує таблицю «ступінь → RPS, avg, p50, p95, p99, max, помилки» — рівно формат таблиці з методички.

**Сказати:** warm-up не входить у вимірювання (там найгірший `max` — JIT і порожні пули); кожен ступінь — окреме
плато з паузою, тому метрики не змішуються; логін — у `setup()`, бо він навмисно CPU-важкий і не є частиною сценарію.

### Крок 2. Аналіз результатів — п. 2 процедури

Показати в README таблиці й графіки A і B.

**Сказати:**
- **p50 vs p99:** у B на 200 VU медіана 0.6 с, а p99 3.1 с, max 7 с. Середнє (0.7 с) ховає тих, хто чекає секунди.
  Хвіст — це черга на блокування рядка: хто прийшов, коли перед ним 30 транзакцій на той самий рядок, чекає всіх.

  але десятки сесій PostgreSQL у `Lock`.

### Крок 3. Порівняльні режими — п. 3 процедури

Показати таблиці README «Scale-out» і «Кеш». Наживо (≈ 5 хв кожне, якщо попросять):

```bash
docker compose $C stop backend-2 && bash load-tests/run.sh scenario-a-read one LEVELS=50 STEP=20     # 1 інстанс
docker compose $C start backend-2 && bash load-tests/run.sh scenario-a-read two LEVELS=50 STEP=20    # 2 інстанси
RESULTS_CACHE_ENABLED=false docker compose $C up -d backend-1 backend-2                              # кеш вимкнено

docker compose $C up -d backend-1 backend-2                                                          # кеш назад
```

**Сказати:** читання масштабується майже лінійно (E ≈ 0.86 на 2 інстансах), бо інстанси нічого не ділять;
запис — навпаки, гіршає від інстансів: кожен інстанс додає 30 з'єднань, тобто ще більше транзакцій у черзі на ті
самі 4 рядки. Кеш знімає третину транзакцій з PostgreSQL.

## 2. Питання на захист

**Що таке Saturation Point?** Рівень навантаження, після якого додаткові користувачі не дають додаткової
пропускної здатності: RPS виходить на плато (або падає), а затримка і черги ростуть. За законом Літтла
`паралельність = RPS × latency`: якщо RPS стоїть, а VU подвоюються, latency теж подвоюється — саме це видно в
сценарії A після 50 VU. Помилки при цьому можуть і не з'явитися (у нас 0 %) — система просто стає повільнішою.

**Чому RPS у B не тримається, а падає (retrograde scaling)?** Блокування рядків серіалізує транзакції на гарячі
рядки. Що більше транзакцій одночасно чекає, то більше накладних витрат: черга блокувань, перемикання контексту,
утримання з'єднань і рядка голосу `FOR UPDATE` довше. Корисна робота стоїть, а накладні ростуть — тому 10 VU дають
більше голосів за секунду, ніж 200.

**Чому середнє — погана метрика?** Розподіл затримок має довгий правий хвіст. Середнє змішує 99 швидких запитів з
одним дуже повільним і не показує ні того, ні іншого. p50 — «типовий» користувач, p95 / p99 — ті, хто страждає;
у системі, де користувач робить 10 запитів за сесію, p99 бачить ≈ кожен десятий користувач.

**Що таке Coordinated Omission?** Помилка вимірювання в закритій моделі: генератор чекає відповіді перед наступним
запитом, тож коли система гальмує, він сам «домовляється» з нею і шле менше. Запити, які реальні користувачі
надіслали б у цей час, не відбуваються, і їхня затримка (з урахуванням очікування в черзі) у перцентилі не
потрапляє — p99 виглядає кращим, ніж є. Ліки — відкрита модель (constant arrival rate), як у
`load-tests/open-model.js`: на 1 200 запитів/с система пропустила ≈ 300 / с, k6 не відправив 75 % запланованих
запитів (`dropped_iterations`), p50 — 1.2 с.

**Як GC і JIT впливають на перцентилі?**
- **JIT:** .NET компілює метод при першому виклику і доперекомпільовує гарячі методи (tiered compilation) — перші
  секунди повільніші. Тому warm-up перед вимірюванням: у ньому найгірший `max` кожного прогону (A 344 мс, B 750 мс).
- **GC:** збирання сміття ненадовго зупиняє потоки (у gen 2 — помітно). На медіану це майже не впливає, але дає
  поодинокі сплески — `max` і p99.9. Тому хвіст треба міряти на довгому плато, а не на кількох секундах.
- Те саме з пулами з'єднань, DNS-кешем і кешем Redis — усе «холодне» на старті.

**Навіщо ізолювати генератор?** Якщо k6 ділить CPU з системою, під навантаженням він сам гальмує: шле менше
запитів і додає власну затримку — міряємо генератор, а не систему (у лабі 3 Python-генератор упирався в 1.8k RPS).
У нас k6 на окремих 8 ядрах, система — на своїх.

**Чому перед кожним прогоном чиста БД?** Сценарій C за прогін створює тисячі опитувань, B — сотні тисяч оновлень.
Без скидання наступний прогін міряє іншу базу: у першій серії через це 3 інстанси «вийшли» гіршими за 2 (ADR 0047).

**Як прибрати вузьке місце запису?** Шардований лічильник (N рядків на варіант, голос оновлює випадковий, результат —
сума), пакетне / асинхронне оновлення `vote_count` через чергу, або рахувати результати з `votes` (`COUNT … GROUP BY`)
і кешувати. Додавати інстанси backend — не допоможе (виміряно: гірше).

**Чому кеш дав лише −28 % RPS, а не в рази?** База мала (50 опитувань) і вся в пам'яті PostgreSQL, агрегат
результатів — сума кількох рядків. Кеш тут перш за все знімає навантаження з БД (+55 % транзакцій без нього) і
відсуває її насичення; на великих даних виграш у latency більший.

## 3. Якщо щось пішло не так

| Симптом | Що робити |
|---|---|
| `k6` не стартує: «network … not found» | стек не піднятий з оверлеєм: `docker compose $C up -d` |
| Числа вдвічі нижчі, ніж у README | хост зайнятий іншим (браузер, IDE, Docker Desktop UI); закрити зайве. Порівнювати лише прогони однієї серії |
| На 3 інстансах читання гірше, ніж на 2 | прогони йшли на одній базі — підняти чистий стек (`down -v`) перед кожним (ADR 0047) |
| `X-Cache: DISABLED` після демо | кеш лишився вимкненим: `docker compose $C up -d backend-1 backend-2` без змінної |
| Помилки 409 у B | два VU голосували тим самим користувачем одночасно — у поточному скрипті користувачі розділені між VU |
