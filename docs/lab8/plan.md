# Лабораторна 8 (Resilience Engineering) — план за етапами

> Вимоги: [`docs/labs/Lab8 - Resilience Engineering.md`](../labs/Lab8%20-%20Resilience%20Engineering.md).
> Лабу виконує Учасник 1 сам (за згодою обох учасників). Гілка `lab8/resilience` від `main` (лаби 6 і 7 уже там).
> ADR лаби 8 — з 0060 поспіль. Робимо лише те, що вимагає методичка, і мінімум, щоб це показати.

## Що вже є з лаби 4

- Cache-Aside для `GET /api/polls/{id}/results` з поколіннями (ADR 0041): голос не видаляє ключ, а збільшує покоління.
- Single-flight на інстансі (ADR 0044): одночасні промахи одного інстансу чекають одне читання з БД. На двох
  інстансах — ≈ 2 звернення до БД на інвалідацію (`scripts/cache-stampede-check.py`).
- TTL jitter `TTL × (1 + 0…0.2)`, без перемикача.

Чого бракує: режиму «без захисту» для порівняння, рівно одного звернення до БД на весь кластер (пункт захисту 2),
Avalanche-експерименту, Negative Caching, k6 на 500+ VU, матриці, Failure Modes і Resilience Profile.

## Етап 1. Об'єкт кешування (2.1) — ✅

- `GET /api/polls/{id}/results` гарячого опитування: найчастіше читання (лайв-дашборд), кожен голос інвалідує ключ,
  а промах конкурує за пул БД (30 з'єднань на інстанс) з транзакціями голосів.
- Обґрунтування — README «Лабораторна 8 → Об'єкт». Агрегат дешевий (1–2 мс), тож важкий агрегат імітує
  `RESULTS_LOAD_DELAY_MS` (`pg_sleep`, за замовчуванням 0, ADR 0060).

## Етап 2. Stampede без захисту (2.2) — ✅ (ADR 0060)

- Перемикач `RESULTS_STAMPEDE_PROTECTION=none | single-flight | lock` (за аналогією з `RESULTS_CACHE_ENABLED`, лаба 5).
- k6-сценарій на 500+ VU: скидає ключ (INCR покоління в Redis) і одразу читає.
- Звернення до БД рахує PostgreSQL: `pg_stat_statements` (міграція `EnablePgStatStatements`), запит агрегату з тегом
  `results-load`. `load-tests/stampede.sh <None|SingleFlight> [burst|sustained]`.
- Виміряно (500 VU): агрегат + 50 мс, burst — None 434 звернення на інвалідацію (з 500), p95 1.7 с; SingleFlight 2.0,
  p95 0.56 с. Справжній агрегат: None 21 (142 після холодного старту), SingleFlight 2.2. RPS і p95 — див. серію етапу 6.

## Етап 3. Distributed lock (2.4) — ✅ (ADR 0061)

- Single-flight з лаби 4 дає по одному зверненню на інстанс; щоб їх було рівно 1 — lock у Redis.
- `SET lock NX PX <lease>` з випадковим токеном, ключ містить покоління (гарантія ADR 0041 не ламається); звільнення —
  лише свого токена (Lua). Single-flight лишається перед lock: у Redis іде один запит з інстансу.
- Хто не отримав lock — перечитує кеш до обмеженого часу очікування, потім читає з БД сам: без deadlock, lease
  обмежений у часі (критерій оцінювання). Redis недоступний — BYPASS, як у ADR 0043.
- Перевірка: власника lock зупинено — решта відповідають після спливу lease.
- Виміряно: 1.0 звернення до БД на інвалідацію (500 VU, burst і sustained); у серії етапу 6 Lock за RPS не швидший
  за single-flight (3420 проти 3765), p95 нижчий.
  `scripts/lock-check.py` (мертвий власник): усі 200 через ≈ 1 с, 1 звернення; читання 1.5 с при lease 1 с — 2 звернення,
  0 помилок. `Lock` — режим за замовчуванням.

## Етап 4. Avalanche і TTL Jitter (2.3, 2.5) — ✅ (ADR 0062)

- Перемикач jitter; формула `Base_TTL ± Random_Jitter`.
- k6 читає всі опитування сіду: без jitter ключі спливають разом — сплески звернень до БД і затримок; з jitter —
  розмазані.

- `load-tests/avalanche.sh` на стеку з `SEED_POLLS=1000` (832 ключі), 300 VU, 60 с. Виміряно (агрегат + 50 мс): без
  розкиду — хвилі кожні 10 с до 269 звернень/с, 26 сесій, p95 у хвилі 370 мс проти 245; ±20 % — пік 162, з третього
  циклу рівно 30–120/с.

## Етап 5. Negative Caching (2.6) — ✅ (ADR 0063)

- Маркер «не існує» з коротким TTL у Redis.
- Створення опитування збільшує покоління свого id — інакше маркер на кілька секунд сховав би нове опитування.
- Потік запитів до неіснуючих id: звернення до БД без захисту і з захистом.

- `scripts/negative-cache-check.py`, `load-tests/penetration.sh`. Виміряно (200 VU, 30 с): 100 неіснуючих id — у БД 53.8 % →
  0.39 % запитів, RPS 744 → 1468; новий id на кожен запит — 100 % в обох режимах, Redis +1 ключ на запит (межа методу).

## Етап 6. Матриця і Failure Modes (2.7) — ✅ (ADR 0064, [`resilience-profile.md`](resilience-profile.md))

- Матриця з методички: `none` / `single-flight` / `lock` — звернення до БД, RPS, p95, p99, % помилок.
- Ризики: deadlock, сплив lease, пам'ять під negative cache, застарілість при SWR (SWR не реалізуємо — ADR 0044).
- Resilience Profile: таблиця «відмова → поведінка → механізм → виміряно» за лаби 2–8.

- `load-tests/series-lab8.sh`, кожен режим × 3. Агрегат + 50 мс: None 124 звернення / 1075 RPS → SingleFlight 2.2 / 3765
  → Lock 1.0 / 3420; справжній агрегат: захист +50 % RPS; penetration 100 % → 0.15 %; сценарій A −7 % на 50 VU.
  Висновки одиночних прогонів про RPS виправлено (ADR 0064).
