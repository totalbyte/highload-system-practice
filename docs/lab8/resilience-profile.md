# Лаба 8: Failure Modes захисту кешу і Resilience Profile системи

> Пункти 2.7 і §3 методички. Рішення — ADR [0060](../ai/decisions/0060-stampede-experiment.md)–[0064](../ai/decisions/0064-lab8-comparison-series.md),
> порівняльна матриця — README «Лабораторна 8 → Матриця (2.7)».

## Failure Modes: нові ризики самих механізмів захисту

Кожен захисний механізм додає свою точку відмови. Нижче — що може піти не так, що з цього виходить і чим це обмежено
або перевірено.

### Distributed lock (ADR 0061)

| Ризик | Що відбувається | Чим обмежено / як перевірено |
|---|---|---|
| **Deadlock** — lock ніхто не звільнить | неможливий за побудовою: lock — це ключ із lease 1 с (`SET … NX PX 1000`), Redis видаляє його сам; чекач не чекає довше 2 с, далі читає БД сам | `scripts/lock-check.py`: «мертвий» lock із чужим token — усі 50 / 200 читачів отримали 200 через 1.01–1.02 с, одне звернення до БД |
| **Lock Expiration Timeout** — читання довше за lease | lease спливає посеред читання, lock бере наступний і теж читає БД: замість 1 звернення — по одному на кожен lease. Помилок немає, обидва пишуть той самий агрегат під тим самим поколінням | `RESULTS_LOAD_DELAY_MS=1500` при lease 1 с: 2.0 звернення на інвалідацію, 0 % помилок, Warning «lease expired» у лозі. Lease (1 с) у 500 разів довший за справжнє читання (1–2 мс) |
| **Чужий lock знято** — власник після спливу lease робить `DEL` | інший інстанс уже тримає lock — простий `DEL` зняв би його, і пішов би третій запит у БД | звільнення лише свого: Lua `if GET == token then DEL`. У прогоні з 1500 мс жоден чужий lock не знято |
| **Застарілий власник пише в кеш** (класична проблема без fencing token) | запис ідемпотентний і прив'язаний до покоління: старий власник пише той самий агрегат того самого покоління; новішого покоління він не торкається | fencing token не потрібен (ADR 0061) |
| **Redis недоступний** | lock не взяти — читання БД без lock, як BYPASS (ADR 0043): stampede знову обмежений лише single-flight на інстансі | `redis-outage-check.py`: 200 з `X-Cache: BYPASS`; клієнт Redis fail-fast, без очікування таймаутів |
| **Redis падає посеред lock** | `TryLockAsync` / `GetEntryAsync` бачать недоступність і читають БД самі | обробка в коді; окремим тестом не перевірено |
| **Один вузол Redis — не Redlock** | при failover на репліку Redis (якби вона була) lock міг би загубитися — зайве читання БД, не помилка | у нас один Redis без реплікації; Redlock (5 незалежних вузлів, більшість) — теорія |
| **Ціна в нормальному режимі** | на промах 2–4 звернення до Redis замість 1; чекачі опитують Redis кожні 10–20 мс (по одному запиту з інстансу на ключ) | серія (ADR 0064): −9 % RPS проти single-flight на двох інстансах; сценарій A лаби 5 — −7 % RPS на 50 VU, 0 на 200 VU |

### Single-flight (ADR 0044)

| Ризик | Що відбувається | Чим обмежено |
|---|---|---|
| Межа інстансу | на N інстансах N звернень до БД на інвалідацію | закрито lock-ом (режим `Lock`) |
| Клієнт, що почав читання, відключився | спільне читання не скасовується: свій DI-scope і `CancellationToken.None` | кожен чекач перестає чекати за своїм токеном |
| Помилка БД у спільному читанні | усі чекачі отримують ту саму помилку (503 / 404) | наступний запит починає нове читання |

### Negative Caching (ADR 0063)

| Ризик | Що відбувається | Чим обмежено / як перевірено |
|---|---|---|
| **Пам'ять під негативний кеш** | один ключ (~106 байт) на кожен різний неіснуючий id; пам'ять ≈ частота різних id × TTL | виміряно: 465 запитів/с з унікальними id → 14 тис. ключів ≈ 1.5 МіБ за 30 с; при 10 тис. запитів/с ≈ 32 МіБ. `maxmemory` у Redis не задано — обмежує лише TTL 30 с |
| **Унікальні id** | кожен id новий — маркер ніколи не спрацьовує, у БД так само 100 % | межа методу; Bloom filter (або для наших послідовних id — `id > last_value` послідовності `poll_ids`) і rate limiting — теорія |
| **Нове опитування з id, для якого вже закешовано «немає»** | без інвалідації воно 30 с віддавало б 404 | створення збільшує покоління id; `negative-cache-check.py`: після створення автор одразу отримує 200 |
| **Збій Redis саме в момент створення** | інвалідація best-effort (не ламає успішний запис), тож негативний запис може вціліти — нове опитування до 36 с віддає 404 | лише при короткому збої з'єднання без рестарту Redis (після рестарту кеш порожній, збереження на диск вимкнене) |
| Маркер із репліки | репліка могла ще не мати щойно створеного опитування | «немає» кешується лише з відповіді Primary |

### TTL Jitter (ADR 0062)

| Ризик | Що відбувається | Чим обмежено |
|---|---|---|
| Холодний кеш (рестарт Redis, flush) | усі ключі зникають разом незалежно від TTL — перша хвиля промахів | на ключ — одне звернення (lock); розкид розтягує вже наступні цикли |
| ±20 % від 10 с — лише 4 с розкиду | перша хвиля після одночасного запису лишається | з третього циклу навантаження рівне (виміряно) |
| Максимальна застарілість при втраченій інвалідації | TTL активного опитування тепер 8–12 с (раніше 10–12) | TTL — страховка, свіжість дає інвалідація (ADR 0041) |

### Stale-While-Revalidate — свідомо не реалізовано

SWR віддає старе значення, поки один запит оновлює кеш у фоні. Stampede зникає повністю, але **рівень застарілості
дорівнює часу оновлення плюс вік старого значення**, і він не обмежений інвалідацією: виборець після свого 201 бачив би
результати без свого голосу. Це ламає гарантію «читання після мутації бачить мутацію» (ADR 0041, 0044), тому SWR —
лише теорія. Для закритих опитувань (дані вже не змінюються) він був би безпечним, але там і stampede немає: TTL 1 год,
інвалідацій немає.

### Діагностичні перемикачі

`RESULTS_LOAD_DELAY_MS` (імітація важкого агрегату) і `RESULTS_TTL_JITTER=0` існують лише для експериментів і за
замовчуванням вимкнені. `pg_stat_statements` додає невеликі накладні витрати на кожен запит на Primary; у прогонах
непомітно.

## Resilience Profile системи (лаби 2–8)

Що відбувається з системою при кожній відмові чи аномальному навантаженні, яким механізмом це закрито і чим доведено.

| Відмова / навантаження | Поведінка системи | Механізм (лаба, ADR) | Доказ |
|---|---|---|---|
| Падіння одного backend-інстансу | запити йдуть на живий, сесії не губляться | stateless JWT, ключі DataProtection у Redis (лаба 2, ADR 0006, 0023); HAProxy health checks, `be_vote` з власними перевірками (лаба 3, ADR 0033, 0037) | `kill-test.py`: 0 помилок клієнта, вузол DOWN за ≈ 1 с; `lb-failover.py`: 0 non-2xx |
| Повільний інстанс | трафік відходить на швидкий | Least Connections (лаба 3, ADR 0034) | p95 209 → 23–28 мс проти Round Robin |
| Падіння балансувальника | **сервіс недоступний — SPOF** | один HAProxy; Keepalived / VRRP — лише схема (лаба 3) | відома межа |
| Redis недоступний | результати читаються з БД (`X-Cache: BYPASS`), голоси приймаються, lock не використовується | fallback і fail-fast клієнт (лаба 4, ADR 0043) | `redis-outage-check.py`: 200 за 68 мс замість 503 за 5.2 с |
| Гонка «прочитав до коміту, записав після інвалідації» | старий агрегат не потрапляє в кеш | покоління в ключі (лаба 4, ADR 0041) | `cache-race-check.py`: 0 з 60 |
| Тимчасові помилки БД | повтор EF, далі 503, а не 500 | retry strategy (ADR 0008), 503 для transient (ADR 0016) | смоук: рестарт Postgres → 200 |
| Одночасні зміни голосу | без deadlock і розбіжності лічильників | `FOR UPDATE`, оновлення рядків у порядку id (ADR 0017) | `concurrency-checks.py`, лічильники по варіантах — 0 розбіжностей |
| Падіння репліки | читання переходять на Primary | Primary Fallback (лаба 6, ADR 0052) | `db-failure-check.py`: 0 помилок читання |
| Падіння Primary | читання з репліки, записи — 503 `Read-Only Mode` за мілісекунди; **автоматичного failover немає** | `DbNodeMonitor` (лаба 6, ADR 0052) | записи відхилено за 9–104 мс, 0 помилок читання |
| Відставання репліки | автор бачить свою зміну, інші — із затримкою | Session Sticky 5 с (лаба 6, ADR 0051) | `stale-read-demo.py` |
| Падіння цілого шарду | каталог без опитувань цього шарду (`X-Shard-Unavailable`), його опитування — 503, решта працює; **логін залежить від Shard A** (`users`) | fail-fast на мертвий шард (лаба 7, ADR 0057) | `cross-shard-check.py`: каталог 200 за 16 мс, опитування B — 503 за 6 мс |
| Гарячий шард | рівномірний розподіл опитувань | Virtual Buckets (лаба 7, ADR 0055, 0056) | Range 100 % на одному шарді → Buckets 47 / 53 % |
| **Cache Stampede** (сотні промахів одного ключа) | одне звернення до БД на весь кластер | single-flight + distributed lock (лаба 8, ADR 0061) | 500 VU, агрегат + 50 мс: burst 486 → 1.0 звернення на інвалідацію; під потоком інвалідацій 124 → 1.0, RPS 1075 → 3420 (ADR 0064) |
| **Cache Avalanche** (одночасне спливання багатьох ключів) | спливання розподілене в часі | TTL ± 20 % (лаба 8, ADR 0062) | 832 ключі: пік 269 → 162 звернень/с, з третього циклу рівно |
| **Cache Penetration** (неіснуючі id) | 404 з кешу, БД — ≈ раз на id за 30 с | Negative Caching (лаба 8, ADR 0063) | 100 id: 100 % → 0.15 % запитів до БД, RPS 953 → 3217 (ADR 0064); **унікальні id — не захищено** |

**Відомі межі, що лишаються:** один балансувальник і один Redis без реплікації (SPOF), немає автоматичного failover
Primary, `users` лише на Shard A, `maxmemory` у Redis не задано, потік унікальних неіснуючих id не фільтрується
(потрібен Bloom filter / rate limiting).
