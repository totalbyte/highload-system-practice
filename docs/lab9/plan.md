# Лабораторна 9 (Performance Profiling) — план за етапами

> Артефакти профілювання — у [`/profiling`](../../profiling/) (вимога §3).

## Етап 1. Симптом і гіпотези (2.1) — ✅

**Симптом** (лаба 7, ADR 0059): каталог `GET /api/polls` на двох шардах насичується вже на 10 VU при ≈ 410 RPS, обидві
репліки — на 98–101 % свого ядра, p95 на 200 VU — 853 мс, а другий шард дав лише ×1.1. При цьому в таблиці `polls` лише
десятки рядків на шард: стільки CPU на такий запит — підозріло.

**Гіпотези:**

- **H1 — неефективний план:** повне сканування `polls` і сортування замість індексу (Full Table Scan, Sort).
- **H2 — N+1 у SQL:** кількість варіантів рахується корельованим підзапитом окремо для кожного рядка сторінки.
- **H3 — планування на кожен запит:** EF / Npgsql не готують запити (prepared statements), тож PostgreSQL заново
  розбирає і планує кожен запит каталогу; на маленьких даних планування дорожче за виконання.
- **H4 — пул з'єднань:** churn (нові з'єднання з SCRAM-автентифікацією, fork процесу) або очікування вільного з'єднання.
- **H5 — backend:** CPU або GC самого backend (серіалізація JSON, компіляція EF-запитів, злиття сторінок fan-out).

Розвідка (2026-11-18, 50 VU, `pg_stat_statements` з `track_planning`): на репліці A планування 12.8 с проти 9.1 с
виконання за 33 с прогону; EXPLAIN ANALYZE сторінки — Planning 2.95 мс / Execution 0.54 мс, індекс використовується;
сесій 60 стабільно. Тобто H3 — головний кандидат, H1 і H4 — ймовірно спростовані; підтвердити інструментами етапу 3.

## Етап 2. Інструменти — ✅

- `pg_stat_statements` на всіх чотирьох вузлах (у лабі 8 — лише на Primary) і `track_planning` — час планування окремо.
- OpenTelemetry у backend (ASP.NET Core, Npgsql, Redis) → Jaeger у профілі `tracing`; вимикач, щоб не впливати на заміри.
- `dotnet-trace`, `dotnet-counters`, `dotnet-gcdump` в образі backend: CPU-профіль (flame graph), алокації і GC, знімки купи.
- Скрипт, що знімає все одним прогоном під тим самим навантаженням.

## Етап 3. Докази (2.2) — ✅ H3 — Root Cause

- CPU: flame graph backend під навантаженням каталогу — де гарячі шляхи; чи backend взагалі вузьке місце (H5).
- Пам'ять: темп алокацій, частота GC і пауз (`dotnet-counters`), два знімки купи з інтервалом — чи є витік.
- БД: EXPLAIN ANALYZE обох запитів каталогу, `pg_stat_statements` (планування / виконання / `DISCARD ALL`), сесії й очікування пулу (H1, H2, H3, H4).
- Трасування: розклад одного запиту каталогу на backend, два паралельні запити до шардів, час у БД.
- Висновок: які гіпотези спростовані, Root Cause з доказами.

## Етап 4. Точкова оптимізація (2.3) — ✅ `Max Auto Prepare=20`

- Те, що усуває підтверджену причину; для H3 — автоматична підготовка запитів Npgsql (`Max Auto Prepare`) з вимикачем для A/B.

## Етап 5. A/B і регресія (2.4) — ✅ каталог +41…+58 % RPS, p95 −17…−35 %
