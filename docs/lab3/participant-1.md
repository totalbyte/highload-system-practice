## Коротко

- **Зона:** балансувальник (Nginx) як єдина точка входу, інкапсуляція backend-ів, пул з 2–3 інстансів і бюджет
  з'єднань, пасивні health checks і виключення вузла, конфіги алгоритмів і їх live-перемикання, статистика
  розподілу, архітектурна схема, інструкція розгортання, SPOF балансувальника.
- **Час у чаті з ШІ:** своя частина ≈ 3–4.5 год, спільна ≈ 1.5–2 год.
- **Перший PR (`lab3/p1-lb`) розблоковує Учасника 2** — робимо й мерджимо його першим, бажано протягом першої години.

**Інфраструктурний контракт (дає П1-1, використовує Учасник 2):**

- Назовні відкритий лише сервіс `lb`: http://localhost:8080. `backend-1`, `backend-2`, `backend-3` — без `ports`,
  доступні тільки всередині `app-network` як `backend-N:8080`.
- `backend-3` — у профілі `scale` (`docker compose --profile scale up -d`), щоб звичайний старт лишався з двома
  інстансами. Як Nginx стартує, коли `backend-3` не запущений (`zone` + `resolve` в `upstream` — є в open source
  Nginx з 1.27.3, або окремі файли upstream), — вирішує Учасник 1 в ADR.
- `X-Instance-ID` ставить backend, балансувальник передає його клієнту без змін. В access-лог Nginx пише
  `$upstream_addr`, `$upstream_status`, `$upstream_response_time`, `$request_time` — це дані для експериментів П2.
- Алгоритм перемикається **без перезбирання образу**: окремі файли upstream або `include` + `docker compose exec lb
  nginx -s reload`. Механізм обирає Учасник 1, точна команда — у runbook (її показують на захисті).
- Прямий доступ до конкретного інстансу (налагодження, старі демо лаби 2) — лише окремим файлом
  `docker-compose.debug.yml` з портами 8091 / 8092 / 8093, **не** в стандартному стеку (інакше порушено 2.2).
- Бюджет з'єднань з БД: 3 × 30 = 90 ≤ 97 (ADR 0018). Для 4+ інстансів — П1-2.

## Межі лаби 3 — чого не робимо

Правило проєкту: не робити покращень раніше за лабу, яка їх вимагає.

- **Лаба 4:** fallback на БД при падінні Redis, `X-Cache: HIT/MISS`, схема ключів, TTL, захист від cache stampede.
  Під час замірів кеш результатів працює як у лабі 2 (ключ `results:{pollId}`, TTL 10 с) — пам'ятати, що
  `GET /results` здебільшого влучає в кеш.
- **Лаба 5:** k6 / Locust, ramp-up до 200 VU, формальний baseline p95 / p99, saturation point. У лабі 3 заміри —
  простим Python-скриптом (`ThreadPoolExecutor`, як решта `scripts/`) з фіксованою кількістю потоків. Числа
  порівнюємо **між конфігураціями**, а не як абсолютну продуктивність системи.
- Keepalived / VRRP руками не піднімаємо — лише теорія (п. 4 захисту) і, за бажанням, схема.
- Redis до `/health` не додаємо (ADR 0021): інакше падіння Redis змусить балансувальник вимкнути всі інстанси.

## Задачі Учасника 1

### П1-1. Nginx як єдина точка входу і пул backend (2.1, 2.2) — гілка `lab3/p1-lb`, ≈40–60 хв

Що зробити:

- `nginx/nginx.conf` (і `nginx/conf.d/`, якщо алгоритми будуть окремими файлами — див. П1-4):
  - `upstream backend_pool` з `backend-1:8080`, `backend-2:8080`, `backend-3:8080` і `zone` (спільні лічильники між
    воркерами — потрібні для `least_conn` і пасивних перевірок);
  - `proxy_pass http://backend_pool`, заголовки `Host`, `X-Forwarded-For`, `X-Forwarded-Proto`;
  - keepalive до upstream (`keepalive`, `proxy_http_version 1.1`, `proxy_set_header Connection ""`) — без нього
    Nginx відкриває нове TCP-з'єднання на кожен запит; пояснити в ADR;
  - access-лог з `$upstream_addr`, `$upstream_status`, `$upstream_response_time`, `$request_time` (контракт для П2).
- `docker-compose.yml`:
  - сервіс `lb`: закріплена версія образу, порт `${LB_PORT:-8080}:80`, конфіг монтується read-only, мережа
    `app-network`;
  - у `backend-1` / `backend-2` прибрати `ports`; додати `backend-3` з того самого якоря `*backend`, у профілі
    `scale`, `INSTANCE_ID: backend-3`;
  - як Nginx переживає відсутній `backend-3` (`resolve` в upstream або окремі файли) — перевірити і записати в ADR.
- `.env.example`: `LB_PORT`; прибрати `API2_PORT`.
- Каркас розділу README «Лабораторна 3» з підрозділами і позначкою власника кожного (балансувальник і
  інкапсуляція, алгоритми і розподіл, асиметричне навантаження, health checks, відмова вузла — читання і запис,
  scale-out, bottleneck, SPOF), щоб далі кожен писав у свій підрозділ без конфліктів.
- ADR: вибір Nginx (або HAProxy), порт 8080 за балансувальником, `backend-3` у профілі.

Готово, коли:

- [ ] `docker compose down -v && docker compose up -d --build` піднімає postgres, redis, `lb` і два backend **без
      ручних кроків**;
- [ ] кілька `curl -i localhost:8080/health` поспіль → `X-Instance-ID` чергується `backend-1` / `backend-2`;
- [ ] `curl localhost:8082` → connection refused; у `docker compose ps` backend-и без опублікованих портів;
- [ ] `docker compose --profile scale up -d` → у ротації з'являється `backend-3` (з `nginx -s reload` чи без — як
      записано в ADR);
- [ ] smoke test з runbook проходить на 8080.

### П1-2. Три інстанси і бюджет з'єднань (2.1, 2.5) — та сама гілка, ≈15–25 хв

- [ADR 0018](../ai/decisions/0018-connection-pool-budget.md): 3 × 30 = 90 ≤ 97 — трьом інстансам вистачає. Для 4+
  потрібно або менший `DB_MAX_POOL_SIZE`, або `max_connections` (`command: postgres -c max_connections=…`). Що
  обрали — новий ADR, в ADR 0018 змінити лише статус (`Amended by …`).
- 3 рази одночасний холодний старт **трьох** інстансів (як П1-2 лаби 2, ADR 0022).

Готово, коли:

- [ ] кожен холодний старт з `--profile scale`: усі три healthy, у логах немає помилок міграцій, сід — рівно один
      раз (`users` = 500, `polls` = 50);
- [ ] після навантажувального прогону Учасника 2 на трьох інстансах `SELECT count(*) FROM pg_stat_activity` ≤ 90 +
      адмін-з'єднання, `psql` підключається.

### П1-3. Health checks і автоматичне виключення вузла (2.4.1, 2.4.2, 2.4.3) — гілка `lab3/p1-platform`, ≈30–45 хв

- `/health` уже є (ADR 0012, 0019): `SELECT 1` до PostgreSQL з таймаутом 2 с, 200 / 503. Перевірити по коду, що це
  відповідає вимозі «статус готовності», і пояснити в README, чому Redis туди навмисно не входить (ADR 0021).
- Пасивні перевірки Nginx: `max_fails` / `fail_timeout` на кожному `server`, `proxy_connect_timeout` 1–2 с (за
  замовчуванням 60 с — клієнт хвилину чекатиме мертвий вузол), `proxy_next_upstream error timeout` +
  `proxy_next_upstream_tries`. Чи вважати відмовою `http_502` / `http_503` — **узгодити з Учасником 2 (П2-4)**: наш
  API чесно віддає 503 при недоступній БД або Redis, і `http_503` у списку може вимкнути весь пул.
- Активні перевірки: в open source Nginx їх немає — пояснити в ADR. Якщо на С-1 обрали HAProxy:
  `option httpchk GET /health`, `inter 2s fall 2 rise 2`, `timeout check 3s` (більше за 2 с з ADR 0019).
- Демо для захисту: серія `GET` через балансувальник → `docker compose stop backend-2` (і окремо `kill`) → запити
  йдуть лише на `backend-1`, клієнт не бачить 5xx → `docker compose start backend-2` → вузол повертається в ротацію
  сам. Запис під час відмови — П2-4.

Готово, коли:

- [ ] stop і kill вузла під потоком `GET` → нуль 5xx у клієнта;
- [ ] після `start` вузол повертається без перезапуску `lb`; час виявлення і повернення записано в README;
- [ ] ADR: які перевірки, які коди вважаються відмовою і чому.

### П1-4. Алгоритми балансування і статистика розподілу (2.3.1, 2.3.2, §4 п. 1–2) — ≈30–45 хв

- Конфіги: Round Robin (за замовчуванням), `least_conn`, Weighted (`weight=3` / `weight=1`), `ip_hash`.
- Live-перемикання без перезбирання образу (див. контракт) і точна команда в runbook — на захисті її запускають
  наживо.
- `scripts/lb-distribution.sh` (curl, як `cross-instance.sh`) або `.py`: N запитів (наприклад, 300) через
  балансувальник → підрахунок `X-Instance-ID` → таблиця «інстанс — кількість — %».
- Прогнати для кожного алгоритму. Очікування: RR ≈ 50 / 50, Weighted ≈ 75 / 25, `ip_hash` — усе на один інстанс
  (пояснення — у «Теорії»), Least Connections при коротких однакових запитах — майже як RR (різницю показує П2-3).

Готово, коли:

- [ ] таблиця розподілу для всіх алгоритмів — у README;
- [ ] перемикання RR → Least Connections займає одну команду і не дає помилок у клієнта.

### П1-6. Архітектурна схема, інструкція розгортання, SPOF (§3, §4 п. 4) — ≈30–40 хв

- Схема (Mermaid, як решта README): клієнт → `lb:8080` → upstream-пул `backend-1..3` → PostgreSQL і Redis; межа
  приватної мережі `app-network` (назовні лише `lb`); підписати алгоритм і health checks. Компоненти голосування й
  результатів — як на C4 з лаби 2, погодити з Учасником 2.
- README «Розгортання з балансувальником»: запуск з 1 / 2 / 3 інстансами, перемикання алгоритму, зупинка й
  повернення вузла, де дивитися access-лог Nginx.
- README «Балансувальник як SPOF»: чому один Nginx — точка відмови, Keepalived / VRRP, DNS Round Robin, хмарні LB
  (див. «Теорію»); за бажанням — схема з двома LB і VIP.
- README: «Швидкий старт», RACI (рядки лаби 3), структура репозиторію (`nginx/`, `docs/lab3/`).
- `docs/ai/runbook.md` і `docs/ai/contracts.md`: балансувальник, порти, профіль `scale`, команда перемикання.

Готово, коли:

- [ ] людина без контексту за README піднімає стек, бачить розподіл по інстансах і перемикає алгоритм.

## Теорія до захисту

Питають обох і про всю систему.

**Чому масштабування взагалі працює.** Після лаби 2 backend stateless: будь-який інстанс обробляє будь-який запит
(JWT замість сесій, дані — у PostgreSQL, кеш і ключі — у Redis). Тому балансувальнику не потрібна sticky-прив'язка,
а вузол можна додати чи вбити без втрати даних.

**Алгоритми і для чого кожен:**

- **Round Robin** — по черзі. Добре, коли запити однакові й короткі, а вузли однакові. Не бачить, що вузол
  повільний: шле йому ту саму частку, і p99 системи дорівнює латентності найгіршого вузла.
- **Weighted Round Robin** — по черзі з вагами. Для вузлів різної потужності, але ваги задаються руками і не
  реагують на раптову деградацію.
- **Least Connections** — туди, де найменше активних з'єднань. Повільний вузол довше тримає з'єднання, тож отримує
  менше нових запитів — реагує на деградацію сам. У Nginx лічильники спільні між воркерами лише з `zone` в upstream.
- **IP Hash** — один клієнтський IP завжди на той самий вузол (affinity на мережевому рівні). Нам не потрібна, бо
  стану в інстансах немає, і навіть шкідлива: за NAT чи проксі всі клієнти — «один IP», і все йде на один вузол.
  У Nginx `ip_hash` бере лише перші три октети IPv4, тому всі запити з хоста через Docker-мережу потрапляють на
  один інстанс.

**Health checks.** Пасивні — балансувальник помічає відмову на живих запитах (помилка з'єднання, таймаут) і на
`fail_timeout` виключає вузол; перший запит до мертвого вузла все одно «платить» — його треба повторити на іншому
вузлі (`proxy_next_upstream`). Активні — балансувальник сам періодично питає `/health` і виключає вузол до того, як
на нього прийде клієнт. Таймаут перевірки має бути більший за 2 с, з якими відповідає наш `/health` при
недоступній БД (ADR 0019).

**Повтори та ідемпотентність.** Повторити запит на інший вузол безпечно, лише якщо повтор не задвоїть зміну. GET —
завжди. Наш `POST /vote` захищений `UNIQUE(poll_id, user_id)` і транзакцією: повтор після коміту дає 409, а не другий
голос. `POST /api/polls` — ні: повтор створить друге опитування. Тому Nginx за замовчуванням не повторює POST/PATCH,
якщо запит уже пішов на upstream (опція `non_idempotent`).

**`/health` без Redis.** Якби `/health` перевіряв Redis, падіння одного спільного Redis зробило б «хворими» всі
інстанси одночасно, і балансувальник віддав би 502 на все — навіть на запити, яким Redis не потрібен (ADR 0021).

**Single Point of Failure — сам балансувальник.** Один Nginx: якщо він упав, система недоступна при живих
backend-ах. Шляхи:

- два балансувальники + **Keepalived / VRRP**: спільна віртуальна IP-адреса, активний вузол шле heartbeat, при його
  падінні резервний забирає VIP за 1–3 с (active-passive);
- **DNS Round Robin**: кілька A-записів на різні балансувальники; дешево, але DNS кешується (TTL), клієнт не знає,
  що адреса мертва, health check-ів немає;
- керований хмарний балансувальник у кількох зонах доступності, anycast.

У нас один Nginx у compose — свідомо, для навчального стенду.

**Масштабування compute не масштабує сховище.** Інстанси backend додаються легко, а PostgreSQL один: кожен новий
інстанс — ще 30 з'єднань (ADR 0018), а гарячий рядок `options.vote_count` однаково змінюється по одному
(рядкове блокування). Тому після 2–3 інстансів запис упирається в БД — це і є висновок 2.5.2, а шляхи далі —
кеш читань (лаба 4), черга / пакетне оновлення лічильників, шардування лічильника.

## Що знати про частину Учасника 2

- Затримка на одному інстансі: middleware `Common/Diagnostics`, вмикається змінною `Diagnostics__ArtificialDelayMs`
  лише на одному інстансі; чому middleware, а не мережева затримка (П2-1).
- RR vs Least Connections при повільному вузлі: частка запитів на повільний вузол, p99 системи, чому Least
  Connections сам «обходить» повільний вузол (П2-3).
- Відмова вузла під час запису: чому Nginx за замовчуванням не повторює `POST`, чому повтор `POST /vote` безпечний
  (транзакція + `UNIQUE` → 409), а `POST /api/polls` — ні; пастка з 503 і `proxy_next_upstream http_503` (П2-4).
- Scale-out 1 / 2 / 3: що росло, що ні і чому; який компонент став наступним обмеженням (П2-5, П2-6).
- Генератор навантаження: що він міряє і чому це ще не лаба 5 (П2-2).
