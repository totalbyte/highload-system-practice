# **ЛАБОРАТОРНА РОБОТА № 2 Тема: Архітектура без стану (Stateless Application Architecture) та винесення стану системи** 

#### **1. Мета роботи** 

На основі базового прототипу (Лабораторна робота № 1) підготувати backend-рівень (Application Layer) до горизонтального масштабування. Усунути залежність бізнес-логіки від локального стану конкретного екземпляра сервісу (instance) та забезпечити коректну, узгоджену роботу системи при паралельному запуску декількох backend-процесів. По завершенню роботи студенти повинні вміти: 

- проводити аудит та класифікацію стану застосунку (Application State); 

- виявляти та рефакторити прихований локальний стан (In-Memory Collections, Sticky Sessions, Singleton State); 

- інтегрувати зовнішні розподілені сховища (Distributed Caching / Centralized Session Stores); 

- забезпечувати детерміновану консистентність даних при обробці послідовних запитів різними екземплярами сервісу; 

- гарантувати відсутності втрати бізнес-стану при раптовій зупинці або перезапуску окремих вузлів (Fault Tolerance). 

## **2. Завдання та етапи виконання** 

### **2.1. Аудит та класифікація стану (State Audit)** 

Проаналізувати поточну реалізацію backend-застосунку та формалізувати класифікацію стану за трьома категоріями: 

1. **Ephemeral / Local Safe:** Тимчасові обчислення, локальні діагностичні метрики та логи. 

2. **Shared / Externalized:** Основний бізнес-стан, сесії, транзакційні дані (мають бути винесені в external storage). 

3. **Critical Stateful Dependencies (підлягають вилученню):** Static state, in-memory колекції, локальні кеші, локальні блокування (application-level locks), локальні лічильники та файлові сесії. 

### **2.2. Рефакторинг та декомпозиція локального стану** 

Переробити архітектуру backend-сервісу за принципами _Stateless_ : 

- Усунути будь-яку прив'язку бізнес-логіки до пам'яті конкретного процесу. 

- Перенести сесійний стан та спільні дані у зовнішній загальний шар (Primary DB або Redis/Key-Value Store). 

- Гарантувати, що будь-який екземпляр сервісу є взаємозамінним (Interchangeable Worker) і здатен обробити довільний HTTP-запит. 

### **2.3. Специфікація Stateless Request Flow** 

Для одного з ключових бізнес-сценаріїв побудувати та реалізувати сквозний потік виконання запиту (Request Flow), зафіксувавши: 

- Вхідні параметри запиту (request parameters / context token); 

- Операції вичитування необхідного контексту зі shared storage; 

- Атомарні зміни стану у зовнішньому сховищі; 

- Відсутність залишкових мутацій у пам'яті Node.js/JVM/Python-процесу після завершення запиту. 

### **2.4. Мульти-екземплярне розгортання та ідентифікація** 

1. Запустити щонайменше **два паралельні екземпляри** backend-застосунку на основі єдиної кодової бази/контейнера. 

2. Впровадити сервісний механізм ідентифікації node (наприклад, через заголовок відповіді X-Instance-ID або container hostname), що дозволяє чітко відстежувати, який саме instance обробив конкретний запит. 

### **2.5. Моделювання збоїв та тестування консистентності (Resilience Testing)** 

Реалізувати та експериментально підтвердити наступні сценарії: 

- **Cross-Instance Consistency:** Виконання послідовного ланцюжка запитів (наприклад: POST → Instance 1, GET → Instance 2, PUT → Instance 2, GET → Instance 1) з підтвердженням актуальності даних без використання Sticky Sessions. 

- **Restart / Instance Loss Scenario:** Симуляція збою (аварійна зупинка `docker stop/kill` одного з instances) під час виконання операцій з подальшим підтвердженням збереження цілісності бізнес-стану та здатності другого instance підхопити обробку. 

### **2.6. Оновлення архітектурної документації** 

Актуалізувати архітектурну схему системи (C4 Component Diagram), відобразивши декомпозицію сервісного шару на декілька stateless instances та їхню взаємодію із централізованими сховищами даних. 

## **3. Вимоги до Git-репозиторію та документації** 

У репозиторії проєкту (файл README.md) мають бути додані: 

- Звіт про аудит стану (таблиця класифікації та перелік усунених in-memory залежностей); 

- Оновлена архітектурна схема; 

- Інструкція з локального розгортання мульти-інстансного середовища та приклади запитів для перевірки cross-instance консистентності (cURL / Postman collection). 

## **4. Порядок захисту та критерії оцінювання** 

### **Процедура захисту:** 

1. **Аудит коду:** Демонстрація усунення stateful-конструкцій у коді. 

2. **Live-демонстрація збійних сценаріїв:** 

   - Виконання серії запитів через різні instances з демонстрацією заголовка X- Instance-ID; 

   - Аварійна зупинка одного з екземплярів під час виконання бізнес-сценарію та доведення відсутності втрати даних. 

3. **Теоретичне опитування:** Обґрунтування різниці між stateless-архітектурою та відсутністю даних взагалі; аналіз ризиків прихованої affinity. 

### **Критерії оцінювання:** 

- **Повнота декомпозиції стану:** Відсутність прихованого пам'ять-залежного стану в коді. 

- **Відзольованість instances:** Повна взаємозамінність сервісних вузлів. 

- **Обізнаність у механізмах консистентності:** Глибоке розуміння розподіленого збереження стану.
