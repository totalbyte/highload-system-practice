# **ЛАБОРАТОРНА РОБОТА № 6**

## **Тема: Реплікація баз даних (Database Replication) та розділення потоків читання і запису (Read/Write Separation)**

#### **1. Мета роботи**

На основі розподіленої системи (Лабораторні роботи № 1–5) реалізувати топологію реплікації СУБД (Primary/Replica) та організувати маршрутизацію запитів на рівні шару доступу до даних (Data Access Layer). Опрацювати особливості асинхронної реплікації, дослідити явище затримки синхронізації (Replication Lag), реалізувати стратегії забезпечення консистентності читання після запису (Read-After-Write Consistency) та опрацювати сценарії деградації шарду (Failover / Degradation Modes).

По завершенню роботи студенти повинні вміти:

- проєктувати та конфігурувати топологію реплікації СУБД (Primary / Read Replicas);
- реалізовувати паттерн Read/Write Separation на рівні ORM/Data Access Layer або Connection Pooling Middleware;
- класифікувати бізнес-сценарії за вимогами до консистентності даних (Eventual vs Strong Consistency);
- вимірювати та демонструвати затримку реплікації (Replication Lag) та проблему застарілого читання (Stale Reads);
- розробляти механізми забезпечення Read-After-Write Consistency (Sticky Routing, Primary Fallback, Versioning);
- налаштовувати поведінку системи при відмові окремих вузлів СУБД (Primary / Replica Fault Tolerance).

## **2. Завдання та етапи виконання**

### **2.1. Конфігурація топології реплікації СУБД (Primary / Replica Topology)**

Розгорнути топологію СУБД у складі щонайменше двох вузлів:

- **Primary Node (Master):** вузол, що приймає мутуючі транзакції (INSERT, UPDATE, DELETE, DDL).
- **Replica Node (Slave/Read-Replica):** вузол у режимі Read-Only, який підключається до Primary та асинхронно/напівсинхронно відтворює журнал транзакцій (WAL / Binary Log).

Продемонструвати автореплікацію даних шляхом виконання мутацій на Primary та перевірки їхньої наявності на Replica.

### **2.2. Реалізація паттерну Read/Write Separation**

- Розділити маршрутизацію запитів у застосунку:
  - Усі модифікуючі операції (Write Operations) підряджаються виключно на Primary Node.
  - Запити читання (Read Operations), що допускають узгодженість у кінцевому підсумку (Eventual Consistency), маршрутизуються на Replica Node.
- Маршрутизація має бути реалізована програмно (через Dynamic DataSource Routing / Multi-Pool Manager) або інфраструктурно (Database Proxy / Middleware типу MaxScale / PgBouncer).

### **2.3. Класифікація читальних сценаріїв та аналіз Replication Lag**

- Сформулювати перелік бізнес-операцій із чітким розділенням:
  - **Eventual Consistent Reads:** перегляд загального каталогу, публічних списків, аналітичних звітів (маршрутизуються на Replica).
  - **Strictly Consistent Reads:** перегляд стану балансу, підтвердження транзакцій, автентифікація (маршрутизуються на Primary).
- Зафіксувати або синтетично відтворити затримку синхронізації (Replication Lag) між Primary та Replica. Продемонструвати феномен Stale Read (повернення застарілих даних з Replica відразу після запису на Primary).

### **2.4. Реалізація паттерну Read-After-Write Consistency**

Для сценаріїв, де користувач повинен гарантовано бачити свої щойно внесені зміни, впровадити та продемонструвати один із механізмів захисту від Stale Read:

- **Session Sticky Routing:** маршрутизація всіх запитів користувача на Primary протягом визначеного TTL після виконання операції запису.
- **Read-Your-Own-Writes Verification:** звірка LSN (Log Sequence Number) / Transaction ID між Primary та Replica перед виконанням читання.
- **Explicit Primary Routing:** примусове читання критичних об'єктів з Primary Node.

### **2.5. Моделювання збоїв та сценарії відмовостійкості (Fault Tolerance)**

Продемонструвати та зафіксувати поведінку системи у двох збійних ситуаціях:

| Сценарій збою | Очікувана поведінка та Graceful Degradation |
|---|---|
| Втрата Replica Node (`docker stop database_replica`) | Система автоматично перенаправляє read-трафік на Primary (Primary Fallback) або повертає контрольовану помилку без падіння backend-сервісів. |
| Втрата Primary Node (`docker stop database_primary`) | Мутуючі операції блокуються з відповідною помилкою (Read-Only Mode), читання з Replica залишається доступним для некритичних сценаріїв. |

### **2.6. Порівняльний аналіз продуктивності (Read Scaling Impact)**

За допомогою скриптів з Лабораторної роботи № 5 провести навантажувальне тестування для двох конфігурацій:

- **Single Primary Topology:** читання та запис виконуються на єдиному вузлі.
- **Primary + Replica Topology:** read-трафік винесений на Replica Node.

Зафіксувати та порівняти Throughput (RPS), Latency p95/p99 та точку насичення (Saturation Point).

## **4. Порядок захисту та критерії оцінювання**

### **Процедура захисту:**

1. **Демонстрація реплікації:** Виконання запису на Primary та перевірка транзакційного логу / стану Replica Node.
2. **Live-демонстрація Stale Read & Read-After-Write Consistency:**
   - Фіксація розбіжності даних при затримці реплікації;
   - Демонстрація роботи захисного механізму (наприклад, Sticky Routing), що запобігає показу застарілих даних користувачу.
3. **Симуляція аварійних ситуацій:** Послідовне вимкнення Replica та Primary вузлів із показником реакції системи (Graceful Degradation).
4. **Теоретичний захист:** Пояснення різниці між синхронною, асинхронною та напівсинхронною реплікацією; поняття Split-Brain, CAP-теореми, PACELC-теореми та механізмів вибору нового лідера (Consensus algorithm / Raft).

### **Критерії оцінювання:**

- **Архітектурна коректність Read/Write Separation:** Прозорість маршрутизації на рівні коду чи middleware.
- **Обґрунтованість механізмів консистентності:** Захист від Stale Reads у критичних бізнес-сценаріях.
- **Глибина аналізу продуктивності:** Кількісне доведення ефекту від масштабування читання.
