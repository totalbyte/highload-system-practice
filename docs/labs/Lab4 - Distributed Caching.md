# **ЛАБОРАТОРНА РОБОТА № 4 Тема: Розподілене кешування (Distributed Caching) та паттерни узгодженості даних** 

#### **1. Мета роботи** 

На основі масштабованої системи (Лабораторна робота № 3) розробити та інтегрувати розподілений кешувальний шар для розвантаження основної бази даних, оптимізації readintensive операцій та зменшення затримок (latency). Опрацювати паттерни взаємодії з кешем, стратегії інвалідації та підтримки консистентності даних у розподіленому середовищі. 

По завершенню роботи студенти повинні вміти: 

- проводити профільний аналіз навантаження та виділяти ресурсоємні read-intensive сценарії для кешування; 

- інтегрувати та налаштовувати централізоване Key-Value сховище (Redis / Memcached) для використання декількома instances; 

- реалізовувати паттерн **Cache-Aside (Lazy Loading)** ; 

- проєктувати детерміновану схему ключів кешування (Cache Key Design) з урахуванням усіх просторів параметрів; 

- налаштовувати політики TTL (Time-To-Live) та реалізовувати ясну інвалідацію кешу при модифікуючих операціях; 

- розробляти механізми відмовостійкості (Fallback Mechanisms) на випадок деградації або недоступності сервера кешування. 

## **2. Завдання та етапи виконання** 

### **2.1. Аналіз та вибір об'єктів кешування** 

Обґрунтувати доцільність кешування для обраного Read-Intensive сценарію. Провести декомпозицію за критеріями: частота читання vs частота запису, допустимий поріг застарівання даних (Stale Data), об'єм обчислень чи складність SQL/NoSQL запиту. 

### **2.2. Інтеграція розподіленого Cache Storage** 

Розгорнути зовнішнє кешувальне сховище (рекомендовано **Redis** ) як окремий контейнер у спільній мережі. Забезпечити рівноправний доступ до цього сховища для всіх запущених backend-instances. 

### **2.3. Реалізація паттерну Cache-Aside** 

Для обраного сценарію читання реалізувати алгоритм: 

1. Запит до кешу за сформованим ключем (Key Lookup). 

2. **Cache Hit:** Повернення закешованого об'єкта без звернення до БД. 

3. **Cache Miss:** Зчитування даних із primary БД, збереження об'єкта в кеші з визначеним TTL та повернення відповіді клієнту. 

### **2.4. Схема ключів (Cache Key Design) та Політика TTL** 

1. Розробити чіткий шаблон ключів (наприклад, domain:entity:id:params_hash), що виключає колізії. 

2. Сформулювати та налаштувати регламент **Time-To-Live (TTL)** з огляду на вимоги бізнес-логіки до актуальності даних. 

### **2.5. Механізми інвалідації кешу (Cache Invalidation)** 

Реалізувати алгоритм примусового скидання або оновлення кешу при виконанні операцій запису/зміни/видалення (POST, PUT, DELETE), що впливають на кешовану сутність. Наступний read-запит після мутації повинен гарантовано повертати свіжі дані. 

### **2.6. Демонстрація метрик продуктивності та збоїв** 

1. **Метрики Hit / Miss / Invalidation:** Додати заголовки відповіді (наприклад, X-Cache: HIT / X-Cache: MISS) або логування операцій для чіткої фіксації джерела даних під час демонстрації. 

2. **Продуктивність:** Порівняти latency відповіді для холодного (Cache Miss) та гарячого (Cache Hit) запитів. 

3. **Fallback testing:** Імітувати відмову Redis (`docker stop redis`). Перевірити, що backend-сервіси переходять у режим прямої роботи з БД (Graceful Degradation), а система залишається функціональною.

## **4. Порядок захисту та критерії оцінювання** 

### **Процедура захисту:** 

1. **Демонстрація Cache Hit / Miss:** Первинний запит (MISS, звернення до БД), повторний запит (HIT, повернення з Redis). 

2. **Демонстрація інвалідації:** Модифікація об'єкта через API, наступне читання (MISS, оновлення кешу). 

3. **Демонстрація Fallback:** Аварійна зупинка Redis-сервера та демонстрація збереження працездатності системи за рахунок прямої роботи з базой даних. 

4. **Теоретичний захист:** Пояснення проблем Cache Stampede / Thundering Herd, Cache Avalanche, стратегій Eviction (LRU, LFU) та різниці між Expiration і Invalidation. 

### **Критерії оцінювання:** 

- **Обґрунтованість кешування:** Кешування лише відповідних read-intensive операцій. 

- ● **Узгодженість даних:** Коректність інвалідації при мутаціях. 

- **Відмовостійкість:** Здатність системи обробляти запити при відмові кешувального шару.
