# **ЛАБОРАТОРНА РОБОТА № 7**

## **Тема: Масштабування даних (Data Scaling): Шардинг (Sharding) та Партиційнування (Partitioning)**

#### **1. Мета роботи**

На основі відмовостійкої розподіленої системи (Лабораторні роботи № 1–6) розробити та реалізувати архітектуру масштабування шару даних шляхом фізичного або логічного партиціювання/шардингу набору даних (Dataset). Дослідити вплив вибору ключа шардингу (Shard Key) на рівномірність розподілу навантаження, опрацювати проблему «гарячого шарду» (Hot Shard), паттерни виконання міжшардових запитів (Cross-Shard Queries/Transactions) та механізми перерозподілу даних (Resharding & Consistent Hashing).

По завершенню роботи студенти повинні вміти:

- проводити доменний аналіз та здійснювати селекцію наборам даних (Datasets), що підлягають горизонтальному шардингу;
- вибирати та обґрунтовувати ключ шардингу (Shard Key) з урахуванням потужності множини (Cardinality), локальності запитів (Query Locality) та рівномірності запису;
- реалізовувати маршрутизацію запитів (Routing Logic) на рівні застосунку (Application-Level Sharding) або інфраструктурного проксі (Database Proxy / Router);
- моделювати та усувати деградації продуктивності, викликані дисбалансом трафіку (Hot Shard / Write Contention);
- проєктувати алгоритми виконання Cross-Shard Queries (Scatter-Gather / Fan-out) та оцінювати їхній оверхед;
- опрацьовувати розподілені транзакції (Cross-Shard Transactions) та аналізувати обмеження локальних ACID-гарантій;
- застосовувати алгоритми Consistent Hashing та Virtual Buckets для мінімізації міграції даних при зміні топології кластера.

## **2. Завдання та етапи виконання**

### **2.1. Селекція Dataset та обґрунтування Shard Key**

- Виділити в предметній області ресурсоємну сутність або агрегат (наприклад, orders, transactions, events, messages), що потребує горизонтального розщеплення.
- Обґрунтувати вибір Shard Key (наприклад, tenant_id, user_id, account_id). Довести недоцільність використання виключно засліплених ключів (наприклад, сурогатного автоінкрементного Primary Key без урахування контексту запитів).

### **2.2. Архітектурне розгортання та Routing Logic**

- Розгорнути щонайменше **два незалежні шарди** (Shard A, Shard B) — фізично або логічно ізольовані вузли СУБД. За наявності реплікації з ЛР № 6 кожен шард може являти собою топологію Primary + Replica.
- Реалізувати детермінований **Shard Router** (програмно в Data Access Layer або через Middleware), який за Shard Key обчислює цільовий вузол для виконання CRUD-операцій.

### **2.3. Аналіз розподілу даних та моделювання Hot Shard**

Згенерувати тестовий масив даних та скласти підсумкову таблицю фактичного розподілу записів по шардах (Dataset Distribution Baseline):

| Шард / Вузол | Кількість записів | Частка даних (%) | Частка Write Operations (%) |
|---|---|---|---|
| Shard A | — | — | — |
| Shard B | — | — | — |

- **Hot Shard Scenario:** Створити синтетичний сценарій асиметричного навантаження (наприклад, монополізація трафіку одним великим тенентом чи часовим інтервалом при низькій Cardinality ключа). Зафіксувати деградацію затримок (Latency spikes) та утилізації CPU/Memory перевантаженого шарду.
- **Оптимізація стратегії:** Перейти від примітивного modulo-маршрутизування (key % N) до хешування (hash(key) % N), складених ключів (Composite Keys) або концепції **Virtual Buckets**. Продемонструвати вирівнювання навантаження.

### **2.4. Cross-Shard Операції та Розподілені Транзакції**

- **Cross-Shard Query (Fan-out / Scatter-Gather):** Реалізувати аналітичний або пошуковий запит, що вимагає звернення до всіх шардированих вузлів. Порівняти час виконання (Latency) та ресурсоємність Shard-Local запиту проти Cross-Shard запиту.
- **Cross-Shard Write / Transaction:** Розглянути сценарій мутації, що охоплює декілька шардів (наприклад, переказ коштів між рахунками на різних шардах). Пояснити неспроможність локальних ACID-транзакцій та запропонувати двофазну фіксацію (2PC / Two-Phase Commit), Saga Pattern або шард-локальний перепроєктований агрегат.

### **2.5. Модель решардингу (Resharding) та Consistent Hashing**

- Сформулювати математичну або алгоритмічну модель розширення кластера (наприклад, зміна конфігурації з 2 до 3 або 4 шардів).
- Продемонструвати проблеми «наївного» шардингу (key % N), при якому зміна N вимагає суцільної міграції майже 100% даних.
- Обґрунтувати використання **Consistent Hashing / Virtual Nodes**, що мінімізує обсяг переміщуваних даних пропорційно до 1/N.

### **2.6. Порівняльний аналіз продуктивності (Performance Benchmark)**

Із використанням навантажувальних скриптів із Лабораторної роботи № 5 провести вимірювання продуктивності для:

- Single Database Node Topology;
- Sharded Architecture Topology (для Shard-Local запитів та Cross-Shard Fan-out запитів).

Зафіксувати метрики Throughput (RPS), Latency p95/p99, Error Rate та межу насичення (Saturation Point).

- Оновлена архітектурна схема із відображенням Shard Router, вузлів Shard A / Shard B та супутньої реплікації.

## **4. Порядок захисту та критерії оцінювання**

### **Процедура захисту:**

1. **Аргументація Shard Key:** Обґрунтування вибору ключа з огляду на Cardinality, Query Locality та захист від колізій.
2. **Live-демонстрація маршрутизації та розподілу даних:**
   - Створення нових об'єктів та демонстрація їхнього детермінованого потрапляння на відповідні фізичні шарди;
   - Відтворення Hot Shard та показати роботу оптимізованої функції хешування / Virtual Buckets.
3. **Демонстрація Cross-Shard запитів:** Виконання та аналіз оверхеду для Fan-out запитів у порівнянні з Shard-Local операціями.
4. **Теоретичний захист:** Пояснення різниці між партиціюванням, шардингом та реплікацією; аналіз проблем distributed JOINs, unique constraints, 2PC, Saga pattern та алгоритмів Consistent Hashing.

### **Критерії оцінювання:**

- **Обґрунтованість архітектурних рішень:** Доцільність вибору Shard Key під профіль навантаження.
- **Якість реалізації Shard Router:** Детермінованість та ізольованість маршрутизації.
- **Глибина системного аналізу:** Розуміння ціни Cross-Shard операцій та проблем розподіленої консистентності.
