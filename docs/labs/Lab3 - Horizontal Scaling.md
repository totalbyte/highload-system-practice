# **ЛАБОРАТОРНА РОБОТА № 3 Тема: Горизонтальне масштабування (Horizontal Scaling) та Балансування навантаження (Load Balancing)** 

#### **1. Мета роботи** 

На основі stateless-архітектури (Лабораторна робота № 2) реалізувати горизонтальне масштабування сервісного шару шляхом розгортання пулу backend-екземплярів та побудови єдиної точки входу (Reverse Proxy / Load Balancer). Дослідити алгоритми розподілу трафіку, поведінку системи при нерівномірному навантаженні та механізми забезпечення високої доступності (High Availability). По завершенню роботи студенти повинні вміти: 

- проєктувати та налаштовувати Reverse Proxy / Load Balancer (Nginx, HAProxy, Traefik); 

- конфігурувати пули серверів (Upstream Pools) та застосовувати різні алгоритми балансування (Round Robin, Least Connections, IP Hash); 

- впроваджувати активні та пасивні механізми Health Checking для виявлення відмов сервісів; 

- аналізувати поведінку балансувальника при деградації продуктивності окремих вузлів; 

- ідентифікувати нові вузькі місця (Bottlenecks), що виникають після масштабування compute-шару. 

## **2. Завдання та етапи виконання** 

### **2.1. Конфігурація пулу backend-сервісів** 

Сформувати підкладку з щонайменше **двох реплік backend-застосунку** , які працюють із спільними сховищами даних, мають ізольовані життєві цикли та повертають свій унікальний Instance-ID. 

### **2.2. Побудова єдиної точки входу (Single Entry Point)** 

Інтегрувати перед пулом backend-сервісів балансувальник навантаження (наприклад, Nginx або HAProxy). Забезпечити повну інкапсуляцію внутрішньої мережі: клієнтський застосунок повинен взаємодіяти виключно з єдиною зовнішньою IP-адресою/портом Load Balancer і не мати доступу до приватних адрес instances. 

### **2.3. Дослідження та порівняльний аналіз алгоритмів балансування** 

1. Сконфігурувати базовий алгоритм **Round Robin** . Виконати серію запитів та зафіксувати статистику розподілу. 

2. Налаштувати та протестувати щонайменше один альтернативний алгоритм: 

   - **Least Connections:** для оптимізації розподілу тривалих запитів; 

   - **Weighted Round Robin:** симуляція гетерогенної інфраструктури з різною потужністю вузлів; 

   - **IP Hash:** забезпечення сесійної прив'язки на рівні мережевого протоколу. 

3. **Експеримент з асиметричним навантаженням:** Створити синтетичне затримання (latency delay) на одному з backend-інстансів. Порівняти ефективність Round Robin та Least Connections у контексті утилізації ресурсів та системного p99 latency. 

### **2.4. Реалізація механізмів Health Check та Fault Tolerance** 

1. Реалізувати спеціалізований інспекційний endpoint GET /health, який повертає статус готовності сервісу (проверка з'єднання з БД, доступність ресурсів). 

2. Налаштувати в балансувальнику автоматичне виключення недоступних або degraded-вузлів з Upstream-пулу (Passive/Active Health Checks). 

3. Продемонструвати поведінку системи при зупинці одного з backend-контейнерів: переспрямування трафіку на працездатні вузли без видачі помилок 5xx клієнту. 

### **2.5. Scale-out Експеримент та системний аналіз** 

1. Провести серію тестових прогонів для конфігурацій: 1, 2 та 3+ instances. Зафіксувати зміни пропускної спроможності. 

2. **Аналіз повносистемних Bottlenecks:** Сформулювати аналітичний висновок про те, який компонент системи (Database connection pool, Network I/O, CPU Load Balancer, Shared Storage Locks) стає наступним обмеженням продуктивності після масштабування backend-шару. 

## **3. Вимоги до Git-репозиторію та документації** 

Репозиторій повинен містити: 

- Конфігураційні файли балансувальника (наприклад, nginx.conf / haproxy.cfg); 

- Оновлену архітектурну схему із зазначенням клієнтського трафіку, балансувальника та upstream-пулу; 

- Звіт у README.md із порівняльним аналізом випробуваних алгоритмів балансування та результатами експерименту з відмовою вузла. 

## **4. Порядок захисту та критерії оцінювання** 

### **Процедура захисту:** 

1. **Демонстрація балансування:** Запуск серії запитів через балансувальник та показ реального розподілу по Instance ID. 

2. **Live-переключення алгоритму:** Зміна конфігурації (наприклад, з Round Robin на Least Connections) та пояснення різниці у поведінці. 

3. **Симуляція аварії:** Зупинка вузла в реальному часі та перевірка відсутності втрат запитів за рахунок Health Check. 

4. **Архітектурна дискусія:** Пояснення поняття Single Point of Failure стосовно самого балансувальника та шляхів його усунення (Keepalived / VRRP, DNS Round Robin). 

### **Критерії оцінювання:** 

- **Коректність конфігурації Reverse Proxy:** Дотримання принципів інкапсуляції інфраструктури. 

- **Глибина аналізу алгоритмів:** Обґрунтованість вибору алгоритму під конкретний профіль навантаження. 

- **Працездатність Health Check:** Автоматичне відновлення та деградація пулу без збоїв для користувача.
