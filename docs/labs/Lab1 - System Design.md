# **ЛАБОРАТОРНА РОБОТА № 1** 

## **Тема: Проєктування архітектури (System Design) та реалізація базового прототипу розподіленої/модульної системи** 

#### **1. Мета роботи** 

Засвоїти принципи системного проєктування (System Design) та сформувати базовий працездатний каркас (MVP / Architectural Baseline) програмного комплексу для його подальшого розширення та масштабування. 

По завершенню роботи студенти повинні вміти: 

- здійснювати доменний аналіз предметної області та формалізувати модель даних; 

- проєктувати та документувати початкову архітектуру системи; 

- реалізовувати шар персистентності (Persistence Layer) та RESTful API / gRPC; 

- забезпечувати детерміноване та відтворюване середовище розгортання; 

- проводити умоглядний аналіз потенційних вузьких місць (Bottleneck Analysis). 

## **2. Завдання та етапи виконання** 

### **2.1. Доменний аналіз та специфікація API** 

Для обраної предметної області необхідно: 

1. **Сформулювати сутності предметної області** та зв'язки між ними (мінімум 3 інтегровані сутності). 

2. **Розробить специфікацію API** (мінімум 5 бізнес-орієнтованих кінцевих точок / endpoints, які реалізують CRUD-операції та специфічну бізнес-логіку). API має відповідати RESTful-принципам або gRPC-стандартам, підтримувати коректну обробку помилок та статус-коди HTTP. 

3. **Визначити піковий сценарій навантаження (High-Load Scenario)** — специфікувати операцію або послідовність запитів, що генерують найбільше ресурсоємних обчислень чи I/O-операцій. 

### **2.2. Архітектурне проєктування** 

Створити актуальну **архітектурну схему** (C4 Model: Component/Container level або розширена UML Component Diagram), яка відображає: 

- Backend-застосунок (сервісний шар); 

- Первинне сховище даних (реляційну або NoSQL СУБД); 

- Зовнішні інтеграції та черги повідомлень (за наявності); 

- Мережеву взаємодію, протоколи та напрямки потоків даних між компонентами. 

### **2.3. Реалізація сервісного шару та персистентності** 

1. **Backend-сервіс:** Реалізувати бізнес-логіку обробки запитів, валідацію вхідних даних (Input Validation) та обробку виняткових ситуацій (Exception Handling). 

2. **Persistence Layer:** 

- Розгорнути повноцінну СУБД (збереження даних у пам'яті застосунку / inmemory без скидання на диск заборонено). 

- Реалізувати схему бази даних (міграції або скрипти ініціалізації DDL). 

- Забезпечити збереження та консистентність даних при перезапуску сервісів (data persistence). 

### **2.4. Контейнеризація та відтворюваність середовища** 

Створити конфігураційні файли декларативного розгортання (наприклад, dockercompose.yml або Helm-чарти): 

- Забезпечити автоматичне підняття всього стеку (сервіси + БД) єдиною командою без додаткового ручного втручання; 

- Налаштувати мережеву взаємодію між контейнерами (networks) та монтування об'ємів даних (volumes) для СУБД. 

### **2.5. Аналіз потенційних вузьких місць (Bottleneck Analysis)** 

На основі спроєктованої архітектури провести теоретичний аналіз продуктивності та визначити **не менше ніж 3 потенційні точки деградації системи** під високим навантаженням. 

Для кожного вузького місця подати аналітичний опис за формою: 

1. **Компонент / Операція / Запит:** Чітко вказана точка відмови/уповільнення. 

2. **Причина (Root Cause):** Фізичні або програмні обмеження (I/O Wait, CPU Throttling, Lock Contention, N+1 problem, відсутність індексів тощо). 

3. **Симптоматика та прояв:** Як саме деградація позначається на системних метриках (Latencies p99, Throughput/RPS, Memory Leak, Connection Pool Exhaustion). 

## **3. Вимоги до Git-репозиторію та командної розробки** 

Проєкт розробляється в єдиному Git-репозиторії команди. Репозиторій повинен містити: 

- **Вихідний код** проєкту із дотриманням принципів Clean Code та кодових стандартів обраної мови розробки. 

- **Скрипти міграції** бази даних та конфігураційні файли розгортання. 

- **Файл README.md** , який містить: 

   - Інструкцію з детермінованого запуску системи; 

   - Архітектурну схему та опис API (або посилання на Swagger/OpenAPI специфікацію); 

   - Таблицю/матрицю розподілу відповідальності (RACI-матриця або перелік модулів, розроблених кожним учасником); 

   - Результати аналізу вузьких місць (Bottleneck Analysis). 

## **4. Порядок захисту та критерії оцінювання** 

### **Процедура захисту:** 

1. **Демонстрація запуску та функціональності:** 

   - Холодне розгортання системи з репозиторію; 

   - Демонстрація виконання мінімум 5 API-endpoints через HTTP-клієнт (Postman, 

curl, Bruno, Swagger); 

- Перевірка зберігання даних шляхом перезапуску контейнера БД. 

- 2. **Архітектурний захист:** Обґрунтування вибраного архітектурного стилю, структури даних та рішень щодо масштабованості. 

3. **Індивідуальне опитування:** Кожен член команди повинен вільно орієнтуватися в загальній архітектурі та виснажливо відповісти на питання щодо реалізованого ним модуля/компонента. 

### **Основні критерії оцінювання:** 

- **Архітектурна якість:** Доцільність декомпозиції, дотримання REST/gRPC стандартів. 

- **Відтворюваність:** Запуск системи «із коробки» без помилок середовища. 

- ● **Глибина системного аналізу:** Обґрунтованість сформульованих потенційних bottlenecks. 

- **Командна обізнаність:** Розуміння кожним учасником принципів функціонування усієї системи, а не лише власного блоку.
