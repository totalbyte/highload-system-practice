# Лабораторна робота № 5 — Навантажувальне тестування і Performance Baseline

**Платформа опитувань** · k6 1.3.0 · ASP.NET Core 10 · PostgreSQL 17 · Redis 8 · HAProxy 3.4 · Docker Compose.
Скрипти — [`load-tests/`](../../load-tests/README.md), повний звіт з усіма таблицями й графіками —
[README, розділ «Лабораторна 5»](../../README.md#лабораторна-5-навантажувальне-тестування-і-performance-baseline).

---

## 1. Результат одним абзацом

Три сценарії (читання, запис, наскрізний workflow) прогнано k6 зі ступеневим навантаженням 10 → 200 VU після
warm-up, на ізольованому середовищі з фіксованими ресурсами. Знайдено точки насичення: читання ≈ 50 VU (≈ 3.7k RPS),
запис ≈ 10 VU (≈ 470 RPS, далі пропускна здатність падає), workflow ≈ 400 VU (≈ 1.5k RPS). **Первинне вузьке місце —
блокування рядків лічильників голосів гарячого опитування в PostgreSQL**: його не лікують ні кеш, ні додаткові
інстанси (з ними запис гіршає), тоді як читання масштабується з коефіцієнтом 0.86 на 2 інстансах.

## 2. Середовище (2.2)

| Компонент | Ядра (`cpuset`) | CPU / RAM |
|---|---|---|
| HAProxy | 0–1 | 2 / 256 МБ |
| backend × 2 (× 3 для scale-out) | 2–3, 4–5, 6–7 | по 2 / 1 ГБ, пул 30 з'єднань |
| PostgreSQL 17 | 8–11 | 4 / 2 ГБ, `max_connections` 100 |
| Redis 8 | 12 | 1 / 256 МБ |
| **k6 — генератор** | **16–23** | 8 / 2 ГБ, ізольований від системи |

k6 працює всередині мережі Docker і б'є в балансувальник напряму. Кожен прогін — на чистій БД з тим самим сідом
(500 користувачів, 50 опитувань).

## 3. Сценарії і профіль (2.1, 2.3)

| Сценарій | Що робить | Що навантажує |
|---|---|---|
| **A — Read-Intensive** | 60 % результати опитування, 25 % деталі, 15 % каталог | кеш Redis, PostgreSQL, CPU backend |
| **B — Write-Intensive** | голоси / зміни голосу, 70 % — гаряче опитування | транзакції, рядкові блокування |
| **C — Complex Workflow** | каталог → деталі → голос → результати; у 20 % — створення, публікація, закриття опитування | усе разом |

Профіль: **warm-up 20 с**, далі плато по 40 с на **10 → 25 → 50 → 100 → 200 VU**.

## 5. Точка насичення і вузьке місце (2.5)

| Сценарій | Saturation point | Що обмежує (доказ — ресурси по ступенях) |
|---|---|---|
| A — читання | ≈ 50 VU, ≈ 3.7k RPS | CPU backend-ів на межі ліміту; на 3 інстансах — CPU PostgreSQL 4 / 4 ядра |
| B — запис | ≈ 10 VU, ≈ 470 RPS; далі RPS **падає** | **блокування рядків** `options.vote_count`: 14–45 сесій у `Lock`, CPU не вичерпано |
| C — workflow | ≈ 400 VU, ≈ 1.5k RPS | CPU backend-ів і PostgreSQL одночасно |

## 6. Порівняння (2.6)

**Масштабування**, 200 VU, коефіцієнт `E(N) = RPS(N) / (N × RPS(1))`:

| | 1 інстанс | 2 інстанси | 3 інстанси |
|---|---|---|---|
| A — читання, RPS | 2 444 | 4 213 (**E = 0.86**) | 5 243 (**E = 0.72**) |
| B — запис, RPS | 365 | 276 (E = 0.38) | 229 (E = 0.21) — гіршає |

Читання масштабується: інстанси нічого не ділять. Запис — ні: кожен інстанс додає 30 з'єднань, і більше транзакцій
стоїть у черзі на ті самі рядки.

**Кеш** (сценарій A, 200 VU):

| | Кеш увімкнено | Кеш вимкнено |
|---|---|---|
| RPS | 4 213 | 3 054 (−28 %) |
| p95 / p99 | 84 / 121 мс | 133 / 171 мс |
| Транзакцій PostgreSQL за секунду | 4 831 | 7 464 (**+55 %**) |
| CPU PostgreSQL | 246 % | 370 % з 400 |

## 7. Coordinated Omission — відкрита модель

| Частота прибуття голосів | Відправлено | Не відправлено | p50 | p99 |
|---|---|---|---|---|
| 300 / с | 300 / с | 0 | 15 мс | 56 мс |
| 1 200 / с | 309 / с | **75 %** | 1.2 с | 3.7 с |

Закрита модель (VU) сама шле менше, коли система гальмує, і ховає частину затримки; відкрита — показує справжню.

## 8. System Performance Baseline (2.7)

```text
=== SYSTEM PERFORMANCE BASELINE ===
Environment Config:  24 vCPU host; HAProxy 2 CPU; 2 × backend 2 CPU / 1 GB, pool 30; PostgreSQL 17 4 CPU / 2 GB;
                     Redis 1 CPU, cache on; k6 on 8 isolated cores
Stable Throughput:   read 3.7k RPS · write 470 RPS · workflow 1.3k RPS
Saturation Point:    read ≈ 50 VUs · write ≈ 10 VUs · workflow ≈ 400 VUs
p95 / p99 Latency:   read 24 / 31 ms · write 39 / 54 ms · workflow 47 / 77 ms
Error Rate:          0 % up to 200 VUs (overload → latency, not errors)
Critical Scenario:   B — Write-Intensive (voting into the hot poll)
Primary Bottleneck:  row-lock contention on options.vote_count (PostgreSQL Lock waits)
```
