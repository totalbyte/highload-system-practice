## 1. Результат

Три сценарії — читання, запис і наскрізний workflow — прогнано k6 зі ступеневим навантаженням 10 → 200 VU після
розігріву, на середовищі з фіксованими ресурсами, де генератор ізольовано від системи. Точки насичення: читання
≈ 50 VU (≈ 3.7k RPS), запис ≈ 10 VU (≈ 470 RPS, далі пропускна здатність падає), workflow ≈ 400 VU (≈ 1.6k RPS).
**Первинне вузьке місце — блокування рядків лічильників голосів гарячого опитування в PostgreSQL**: його не
усувають ні кеш, ні додаткові інстанси (з ними запис гіршає), тоді як читання масштабується з коефіцієнтом 0.86 на
2 інстансах.

## 2. Середовище тестування (2.2)

| Компонент | Ядра (`cpuset`) | CPU / RAM | Конфігурація |
|---|---|---|---|
| HAProxy | 0–1 | 2 / 256 МБ | `roundrobin`, health checks |
| backend × 2 (× 3 для scale-out) | 2–3, 4–5, 6–7 | по 2 / 1 ГБ | ASP.NET Core 10, пул 30 з'єднань на інстанс |
| PostgreSQL 17 | 8–11 | 4 / 2 ГБ | `max_connections` 100 |
| Redis 8 | 12 | 1 / 256 МБ | кеш результатів, без збереження на диск |
| **k6 — генератор** | **16–23** | 8 / 2 ГБ | ядра, яких система не використовує |

k6 працює всередині мережі Docker і звертається до балансувальника напряму. Кожен прогін — на щойно піднятому стеку з
тим самим сідом (500 користувачів, 50 опитувань): без цього прогони впливали один на одного.

**Де в репозиторії:** ядра й ліміти, сервіс k6 — [`load-tests/docker-compose.loadtest.yml`](../../load-tests/docker-compose.loadtest.yml#L18);

чистий стек перед кожним прогоном — [`load-tests/series.sh`](../../load-tests/series.sh#L23) (функція `fresh`);
README «Середовище тестування».

## 3. Сценарії і профіль навантаження (2.1, 2.3)

| Сценарій | Що робить | Що навантажує |
|---|---|---|
| **A — Read-Intensive** | 60 % результати опитування (половина — гаряче #1), 25 % деталі, 15 % каталог | кеш Redis, PostgreSQL, CPU backend |
| **B — Write-Intensive** | голоси і зміни голосу 500 користувачів, 70 % — у гаряче опитування #1 | транзакції, рядкові блокування |
| **C — Complex Workflow** | каталог → деталі → голос → результати; у 20 % ітерацій — створення, публікація і закриття опитування; паузи 100–300 мс між кроками | усе разом |

Профіль: **розігрів 20 с** (пули з'єднань, JIT, кеш — у вимірювання не входить), далі плато по 40 с на
**10 → 25 → 50 → 100 → 200 VU** з паузою між ступенями. Кожен ступінь — окремий k6-scenario, тому метрики окремо по
кожному. Логін користувачів — у `setup()`, не вимірюється.

**Де в репозиторії:**
- ступені й розігрів — [`load-tests/lib.js`](../../load-tests/lib.js#L19) (`steppedScenarios`), логін — [`loginUsers`](../../load-tests/lib.js#L65);
- сценарій A — [`scenario-a-read.js`](../../load-tests/scenario-a-read.js#L25);
- сценарій B — [`scenario-b-write.js`](../../load-tests/scenario-b-write.js#L41), розподіл користувачів між VU — [`userToken`](../../load-tests/scenario-b-write.js#L35);
- сценарій C — [`scenario-c-workflow.js`](../../load-tests/scenario-c-workflow.js#L41).

|---|---|---|---|---|
| 10 | 2 310 · 3.5 · 8.5 · 11.3 | 469 · 18.5 · 39.2 · 53.8 | 67 · 7.9 · 40.3 · 48.1 | 0 % |
| 25 | 3 138 · 7.1 · 14.4 · 19.0 | 432 · 19.9 · 264.7 · 515.2 | 170 · 7.5 · 28.3 · 47.5 | 0 % |
| 50 | 3 695 · 12.5 · 24.0 · 30.7 | 320 · 23.4 · 893.1 · 1 769.5 | 346 · 7.3 · 19.3 · 40.4 | 0 % |
| 100 | 3 934 · 23.9 · 44.5 · 57.0 | 289 · 231.7 · 1 277.1 · 2 643.7 | 687 · 8.3 · 22.3 · 32.8 | 0 % |

**Середнє проти хвоста.** У сценарії B на 200 VU середнє — 732 мс, медіана — 614 мс, а p99 — 3.1 с і максимум 7 с.

## 5. Точка насичення і первинне вузьке місце (2.5)

| Сценарій | Saturation point | Ознаки | Що обмежує (ресурси по ступенях) |
|---|---|---|---|
| A — читання | ≈ 50 VU, ≈ 3.7k RPS | RPS +6 % на подвоєння VU, затримка ×2 | CPU backend-ів на межі ліміту; на 3 інстансах — CPU PostgreSQL 4 / 4 ядра |
| B — запис | ≈ 10 VU, ≈ 470 RPS | RPS **падає**, p99 0.05 → 3.1 с | **блокування рядків** `options.vote_count`: 14–45 сесій PostgreSQL у черзі `Lock`, CPU не вичерпано |
| C — workflow | ≈ 400 VU, ≈ 1.6k RPS | +25 % RPS при p95 ×5.3, далі не росте | CPU backend-ів і PostgreSQL одночасно |

Усі голоси гарячого опитування змінюють ті самі 4 рядки лічильників; PostgreSQL виконує такі транзакції по черзі.
Що більше одночасних транзакцій, то довша черга і більші накладні витрати — тому пропускна здатність запису не
тримається, а зменшується.

**Де в репозиторії:** ресурси по ступенях (CPU контейнерів, сесії й транзакції PostgreSQL кожні 5 с) знімає
[`load-tests/run.sh`](../../load-tests/run.sh); транзакція голосу з блокуваннями —
[`Votes/VoteService.cs`](../../src/PollingPlatform.Api/Votes/VoteService.cs); README «Точка насичення і первинний bottleneck».

## 6. Порівняння: масштабування (2.6)

Коефіцієнт масштабованості `E(N) = RPS(N) / (N × RPS(1))`, 200 VU:

| | 1 інстанс | 2 інстанси | 3 інстанси |
|---|---|---|---|
| A — читання, RPS | 2 444 | 4 213 (**E = 0.86**) | 5 243 (**E = 0.72**) |
| B — запис, RPS | 365 | 276 (E = 0.38) | 229 (E = 0.21) |

Читання масштабується: інстанси нічого не ділять. Запис гіршає: кожен інстанс додає 30 з'єднань до БД, і більше
транзакцій стоїть у черзі на ті самі рядки (до 70 сесій у `Lock` на 3 інстансах).

**Де в репозиторії:** прогони 1 / 3 інстанси — [`load-tests/series.sh`](../../load-tests/series.sh) (мітки `1-inst`,
`3-inst`); порівняльні таблиці — `report.py --compare`; README «Scale-out: 1 vs 2 vs 3 інстанси».

## 7. Порівняння: кеш (2.6)

Сценарій A, 200 VU; кеш вимикається змінною `RESULTS_CACHE_ENABLED=false` (кожне читання результатів — запит до
БД, відповідь `X-Cache: DISABLED`):

| | Кеш увімкнено | Кеш вимкнено |
|---|---|---|
| RPS | 4 213 | 3 054 (−28 %) |
| p95 / p99 | 84 / 121 мс | 133 / 171 мс |
| Транзакцій PostgreSQL за секунду | 4 831 | 7 464 (**+55 %**) |
| CPU PostgreSQL | 246 % | 370 % з 400 |

Кеш знімає з PostgreSQL третину транзакцій сценарію і тримає БД нижче насичення. Холодний проти гарячого запиту на
одному читанні — у лабі 4: MISS ≈ 4.1 мс, HIT ≈ 1.9 мс (p50).

**Де в репозиторії:** перемикач — [`ResultsService.cs`](../../src/PollingPlatform.Api/Results/ResultsService.cs#L18)
(`cache.Enabled`), налаштування — [`ResultsCache.Enabled`](../../src/PollingPlatform.Api/Results/ResultsCache.cs#L30),
змінна в [`docker-compose.yml`](../../docker-compose.yml#L20); прогін — [`series.sh`](../../load-tests/series.sh#L55);
README «Кеш: вимкнено vs увімкнено».

## 8. Coordinated Omission — відкрита модель (§4)

Таблиці вище — закрита модель: віртуальний користувач надсилає наступний запит лише після відповіді на попередній, тож
коли система гальмує, генератор сам шле менше, і частина затримки не потрапляє в статистику. Відкрита модель
надсилає голоси з фіксованою частотою прибуття:

| Частота прибуття голосів | Відправлено | Не відправлено | p50 | p99 |
|---|---|---|---|---|
| 300 / с | 300 / с | 0 | 15 мс | 42 мс |
| 1 200 / с | 295 / с | **75 %** | 0.5 с | 3.0 с |

**Де в репозиторії:** [`load-tests/open-model.js`](../../load-tests/open-model.js#L20) (`constant-arrival-rate`);
README «Відкрита модель і coordinated omission».

## 9. System Performance Baseline (2.7)

```text
=== SYSTEM PERFORMANCE BASELINE ===
Environment Config:  24 vCPU host; HAProxy 2 CPU; 2 × backend 2 CPU / 1 GB, pool 30; PostgreSQL 17 4 CPU / 2 GB;
                     Redis 1 CPU, cache on; k6 on 8 isolated cores
Stable Throughput:   read 3.7k RPS · write 470 RPS · workflow 1.3k RPS
Saturation Point:    read ≈ 50 VUs · write ≈ 10 VUs · workflow ≈ 400 VUs
p95 / p99 Latency:   read 24 / 31 ms · write 39 / 54 ms · workflow 47 / 77 ms
Error Rate:          0 % up to 200 VUs (overload → latency, not errors)
Critical Scenario:   B — Write-Intensive (voting into the hot poll)
Primary Bottleneck:  row-lock contention on options.vote_count (PostgreSQL Lock waits)
```

Обмеження: усе на одній машині — ядра розділені, а пам'ять, диск і хост-ОС спільні; порівнюються лише прогони однієї
серії.

**Де в репозиторії:** README «System Performance Baseline».
