# Лабораторна 6 (Database Replication) — план за етапами

> Вимоги: [`docs/labs/Lab6 - Database Replication.md`](../labs/Lab6%20-%20Database%20Replication.md).
> Лабу виконує Учасник 1 самостійно (за домовленістю учасників), гілка `lab6/replication`. ADR лаби 6 — з 0049 поспіль.
> Вимірювання — на машині Учасника 1 (8 потоків): лабу 5 міряв Учасник 2 на 24 vCPU, тому її абсолютні числа не
> порівнюються, а базова конфігурація міряється заново в одній серії з Primary + Replica.

## Етап 1. Топологія (2.1) — ✅

- Сервіс `postgres` лишається Primary (на цю назву спираються скрипти), новий сервіс `postgres-replica` — асинхронна
  потокова репліка, яка на порожньому томі сама робить `pg_basebackup`; роль `replicator` і фізичний слот `replica_1`.
- [`scripts/replication-check.py`](../../scripts/replication-check.py): топологія, міграції й сід на обох вузлах,
  INSERT / UPDATE / DELETE через API доходять до Replica, запис у Replica відхиляється. ADR 0049.

## Етап 2. Read/Write Separation і класифікація (2.2, 2.3) — ✅

- Два пули: Primary за замовчуванням, на Replica лише читання через `ReadDb.Eventual`; заголовок `X-DB-Node`; перемикач
  `READ_REPLICA_ENABLED` для конфігурації Single Primary. ADR 0050.
- Replica: каталог, деталі опитування, результати при вимкненому кеші.
- Primary: логін, реєстрація, `/me`, «мій голос», перевірки перед записом, відповідь після запису, промах кешу результатів.
- Промах кешу результатів читається з Primary: інакше старий агрегат потрапить у кеш під новим поколінням (ADR 0041).
- Перевірка: [`scripts/rw-routing-check.py`](../../scripts/rw-routing-check.py) і всі регресії кешу та голосування.

## Етап 3. Stale Read і Read-After-Write (2.3, 2.4) — ⏳

- Керована затримка через `recovery_min_apply_delay`; демо Stale Read: автор створює опитування, інший користувач
  отримує 404, поки Replica не наздожене.
- Session Sticky у Redis (ключ на користувача з TTL ≈ 5 с, бо backend-ів кілька); Redis недоступний — автентифіковані
  читання йдуть на Primary. Демо-скрипт із вимкненим і ввімкненим захистом.

## Етап 4. Відмови (2.5) — ⏳

- `/health` повертає 503 лише тоді, коли недоступні обидва вузли БД, інакше Primary down виключить увесь пул HAProxy.
- Primary Fallback при втраті Replica; Read-Only 503 при втраті Primary, читання каталогу лишається.
- Спершу заміряти поведінку механізмів Npgsql; монітор вузлів — лише якщо час реакції неприйнятний.

## Етап 5. Навантаження (2.6) — ⏳

- Конфігурація ядер для 8 потоків (окремий overlay), збір даних про Replica і затримку реплікації.
- Серія в однакових умовах, свіжий стек на прогін (ADR 0047): Single Primary проти Primary + Replica, сценарії A, B, C.
- Сценарій A ще й з вимкненим кешем: за даними лаби 5 з кешем вузьке місце — CPU backend-ів, і репліка може майже не
  додати RPS; з вимкненим кешем навантаження впирається в PostgreSQL.
