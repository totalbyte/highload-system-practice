# Профілювання (лабораторна 9)

Цикл Symptom → Hypotheses → Instrumentation → Evidence → Root Cause → Optimization → Regression Verification для одного
симптому. Рішення — ADR [0065](../docs/ai/decisions/0065-lab9-symptom-and-db-instrumentation.md)–[0070](../docs/ai/decisions/0070-migration-advisory-lock.md),
порівняння до / після — [`ab-report.md`](ab-report.md), сирі результати A/B — [`ab-results/`](ab-results/).

## 1. Симптом

У лабі 7 каталог `GET /api/polls` на двох шардах насичувався вже на 10 VU при ≈ 410 RPS. Обидві репліки працювали на
98–101 % свого ядра, p95 на 200 VU сягав 853 мс, а другий шард дав лише ×1.1. При цьому на кожному шарді лише кілька
десятків опитувань. За `docker stats` це ≈ 2.3 мс CPU репліки на один запит каталогу — забагато для таких маленьких запитів.

## 2. Гіпотези

| | Гіпотеза | Чим перевіряю |
|---|---|---|
| H1 | неефективний план: повне сканування `polls` і сортування | EXPLAIN ANALYZE |
| H2 | N+1 у SQL: кількість варіантів рахується підзапитом для кожного рядка | EXPLAIN ANALYZE (loops) |
| H3 | кожен запит заново розбирається й планується, бо Npgsql не готує запити | `pg_stat_statements` з `track_planning`, Npgsql `prepared_ratio`, `pgbench` simple / extended / prepared |
| H4 | пул з'єднань: churn нових з'єднань або очікування вільного | лічильники пулу Npgsql, `pg_stat_database.sessions`, `pg_stat_activity` |
| H5 | сам backend: CPU, GC, серіалізація, злиття fan-out | flame graph, `dotnet-counters`, два знімки купи, траси Jaeger |

## 4. Докази

**H1 — спростовано.** EXPLAIN ANALYZE сторінки каталогу ([`baseline/explain-page.txt`](baseline/explain-page.txt)):
`Index Scan Backward using ix_polls_status_created_at`, сортування лише інкрементне за вже відсортованим індексом,
виконання 0.50 мс. Повного сканування `polls` немає.

**H2 — є, але дешево.** У тому ж плані `SubPlan 1` виконується `loops=13` разів (по разу на рядок сторінки) — це N+1
усередині SQL, але кожен прохід 0.017–0.020 мс. На такому обсязі даних це не причина; з тисячами варіантів на шард він був би
наступним кандидатом.

**H3 — підтверджено.** `pg_stat_statements` обох реплік за вікно прогону «до» ([`baseline/pg-stat-statements-postgres-replica.txt`](baseline/pg-stat-statements-postgres-replica.txt),
[`…-postgres-shard-b-replica.txt`](baseline/pg-stat-statements-postgres-shard-b-replica.txt)), на один виклик:

| Запит | Репліка | Планування, мс | Виконання, мс | Частка планування |
|---|---|---|---|---|
| сторінка каталогу | A | 0.378 | 0.407 | 48 % |
| сторінка каталогу | B | 0.438 | 1.818 | 19 % |
| підрахунок | A | 0.146 | 0.095 | 61 % |
| підрахунок | B | 0.131 | 0.103 | 56 % |

Час планування на обох репліках однаковий (0.38–0.44 мс на сторінку), а частка на B менша, бо виконання сторінки там
дорожче — чому, розібрано нижче. Плюс один `DISCARD ALL` на кожне повернення з'єднання в пул. Npgsql `prepared_ratio` = 0 % на
обох пулах реплік ([`baseline/summary.md`](baseline/summary.md)).

Окремий контрольний експеримент — `pgbench` на репліці кожного шарду з тими самими двома запитами, одне ядро, по 3 прогони
кожного режиму через один ([`pgbench/results.txt`](pgbench/results.txt), 2026-11-23):

| Протокол | Репліка A, запитів каталогу / с (min–max) | Репліка B |
|---|---|---|
| simple | 4337 (4269–4368) | 3326 (3076–3425) |
| extended — так працює Npgsql без підготовки | 3749 (3608–3797) | 3055 (2954–3100) |
| prepared | **9194** (9054–9205) | **6443** (6295–6552) |
| prepared / extended | **×2.45** | **×2.1** |

Та сама база на тому самому ядрі обслуговує у 2.1–2.5 раза більше, якщо запит не треба щоразу розбирати й планувати; розкид
між повторами — 1–5 %. Перший, одиночний прогін 2026-11-18 дав 717 / 1723 (той самий ×2.4), але в 5 разів менші абсолютні
числа: того дня вся машина працювала повільніше (див. розділ 8), тому порівнювати можна лише числа одного дня.

**H4 — наслідок, а не причина.** Пул однієї репліки тримає ≈ 24 з 30 з'єднань зайнятими, бо репліка відповідає повільно;
нових сесій — лише від монітора вузлів (≈ 2–3 на секунду, `pg_stat_database.sessions` = 256 за прогін); черга пулу
потоків — 0.2.

**H5 — спростовано.** `dotnet-counters`: GC-паузи 0.94 % часу, 42 МБ/с алокацій, купа живих об'єктів 10.2 → 10.7 МБ за
вікно (витоку немає). Лише 10.9 % часу потоків — виконання керованого коду (`CPU_TIME`), решта — очікування на БД;
[flame graph](baseline/flamegraph-cpu.svg) показує, що й цей CPU — звичайний шлях запиту (Kestrel → контролер →
`PollService.ListAsync` → EF → Npgsql). Траси Jaeger (розділ 5) дають те саме з іншого боку: під навантаженням 98 % часу
запиту каталогу — SQL.

### Чому Shard B дорожчий

У baseline сторінка каталогу на репліці B виконувалась 1.82 мс за виклик проти 0.41 мс на A, і після оптимізації різниця
лишилась (0.92 проти 0.42). Причина — у даних і в тому, що B першою виходить на стелю свого ядра:

| | Shard A | Shard B |
|---|---|---|
| активних публічних опитувань (рядків у сторінці, з 20) | 12 | 20 |
| варіантів (`options`) | 62 | 115 |
| виконання сторінки на простої, EXPLAIN | 0.087 мс | 0.110 мс |
| `pgbench`, запитів каталогу / с (extended / prepared) | 3749 / 9194 | 3055 / 6443 |
| CPU репліки під навантаженням (baseline) | 90 % | 101 % |
| один SQL-оператор під навантаженням, траса (до / після) | 1.6 / 1.1 мс | 16.4 / 11.1 мс |

Запит каталогу на B у 1.2–1.4 раза дорожчий: на A активних опитувань лише 12, тож сторінка неповна, а на B — повна з
20 рядків, і підзапит кількості варіантів виконується 20 разів, а не 12. Тому за однакової кількості запитів B першою
доходить до 100 % ядра. Далі `pg_stat_statements` і траса міряють не лише роботу оператора, а й чекання на процесор: на B
оператор стоїть у черзі, на A — майже ні (на простої різниця лише 0.11 проти 0.087 мс). Каталог чекає повільніший шард, тож
саме B визначає швидкість усього каталогу. Частка планування на B менша з тієї ж причини: виконання там «роздуте» чергою.

Траси Jaeger, стенд з одним ядром на вузол БД, 2026-11-23, медіана ([`baseline/traces-catalog-load.md`](baseline/traces-catalog-load.md),
[`optimized/traces-catalog-load.md`](optimized/traces-catalog-load.md), приклади трас — `*/trace-*.json`):

| Запит | Частина | До | Після |
|---|---|---|---|
| каталог, без навантаження | весь запит / SQL / backend | 3.94 / 2.22 / 1.69 мс | 3.52 / 1.81 / 1.60 мс |
| каталог, під навантаженням 50 VU | весь запит / SQL / backend | 34.9 / 34.3 / 0.7 мс | 23.3 / 22.7 / 0.6 мс |
| каталог, під навантаженням | один оператор на репліці A / B | 1.6 / 16.4 мс | 1.1 / 11.1 мс |
| результати опитування (кеш), без навантаження | весь запит / Redis / SQL | 0.79 / 0.36 / 0.00 мс | 0.86 / 0.37 / 0.00 мс |

Під навантаженням майже весь час запиту каталогу — SQL, а backend поза ним — 0.6–0.7 мс. Каталог Redis не використовує, тому
складову кешу видно на запиті результатів (Cache-Aside з лаби 4): Redis ≈ 0.4 мс, а більшість запитів (HIT) до БД не доходить.
Траса показує, **де** витрачається час (у SQL на репліці B), але не **на що всередині** оператора: SQL-спан охоплює весь
обмін з базою — відправку, розбір, планування, виконання і відповідь. Розділити планування й виконання може лише сама база —
це робить `pg_stat_statements`.

## 6. Чому причину видно в `pg_stat_statements`, а не у flame graph

Flame graph — профіль процесу **backend** (`dotnet-trace` семплює його потоки). Розбір і планування SQL відбуваються в
іншому процесі — у **PostgreSQL** на репліці, тож у профілі backend вони виглядають лише як потік, що чекає на мережу
(`UNMANAGED_CODE_TIME`). Тому flame graph тут доводить одне: backend не вузьке місце (H5 спростовано). Причину треба шукати
інструментом тієї сторони, де витрачається процесор, — статистикою самої БД.

Ще одна відмінність — спосіб вимірювання. `dotnet-trace` — **sampling**: ~100 разів на секунду записує стеки потоків; накладні
витрати малі, але це статистика, а не точний облік. `pg_stat_statements` і траси OpenTelemetry — **instrumentation**: вимір
на вході й виході кожного оператора або кожної операції; точні значення для кожного виклику. Відомий артефакт sampling у нас —
кадр `PollGC` на ≈ 25 % вибірок `CPU_TIME`: вибірка часу потоків приписує до CPU потоки, що стоять у безпечній точці на
збирання сміття, тоді як лічильник GC-пауз показує < 1 %. Вимірюванням тут є лічильник, кадр лише відзначено.

## 7. Root Cause і оптимізація

Кожен запит каталогу на кожному шарді — два оператори, які PostgreSQL щоразу заново розбирає і планує, бо Npgsql надсилає їх
без підготовки, а після кожного повернення з'єднання в пул `DISCARD ALL` скидає стан сесії. На маленьких даних планування
коштує стільки ж, скільки виконання, і разом із розбором з'їдає ядро репліки.

Оптимізація — один параметр у чотирьох рядках підключення, `docker-compose.yml`, рядки 10–23 (ADR [0068](../docs/ai/decisions/0068-auto-prepare-root-cause.md)):

```diff
-    ConnectionStrings__PostgresReplica: "Host=postgres-replica;…;Maximum Pool Size=${DB_MAX_POOL_SIZE:-30}"
+    ConnectionStrings__PostgresReplica: "Host=postgres-replica;…;Maximum Pool Size=${DB_MAX_POOL_SIZE:-30};Max Auto Prepare=${DB_MAX_AUTO_PREPARE:-20}"
```

і так само для `Postgres`, `ShardB`, `ShardBReplica`. Npgsql сам готує найчастіші запити кожного з'єднання і зберігає їх між
поверненнями в пул. Вимикач для A/B — `DB_MAX_AUTO_PREPARE=0`. Код застосунку не змінювався.

Після неї (той самий прогін, [`optimized/summary.md`](optimized/summary.md)): `prepared_ratio` 100 %, планування сторінки
0.378 → 0.001 мс на виклик на репліці A, 0.438 → 0.000 мс на B, `DISCARD ALL` зник.

## 8. Повторний експеримент (A/B)

Ті самі умови, що й у лабі 7: одне ядро на вузол БД, чистий стек на кожен прогін, каталог 3 рази «до» і 3 рази «після» через
один, плюс по одному прогону запису й читання для перевірки регресії (`profiling/ab-series.sh`, ADR [0069](../docs/ai/decisions/0069-lab9-ab-verification.md)).
Повні таблиці по ступенях — [`ab-report.md`](ab-report.md), сирі зведення k6 і заміри ресурсів кожного прогону — [`ab-results/`](ab-results/).

Каталог, 3 повтори, середнє і розкид (2026-11-18):

| VUs | RPS до (min–max) | RPS після (min–max) | Δ RPS | Δ RPS, найгірший … найкращий випадок повторів | Δ p95 | Δ p99 |
|---|---|---|---|---|---|---|
| 10 | 391 (386–400) | 553 (538–568) | +41 % | +35 … +47 % | −31 % | −31 % |
| 25 | 395 (389–398) | 556 (539–571) | +41 % | +35 … +47 % | −30 % | −33 % |
| 50 | 362 (307–389) | 570 (548–596) | +58 % | +41 … +94 % | −35 % | −36 % |
| 100 | 404 (395–410) | 569 (557–581) | +41 % | +36 … +47 % | −30 % | −29 % |
| 200 | 405 (400–412) | 580 (565–593) | +43 % | +37 … +48 % | −17 % | −17 % |

Помилок 0 у кожному прогоні. Ефект — **≈ +41 % RPS**, і навіть у найгіршому поєднанні повторів (найслабший «після» проти
найкращого «до») не менше +35 %, тобто більший за розкид. Значення +58 % на 50 VU роздуте одним слабким прогоном «до»
(307 RPS), тож за підсумок беру ≈ +41 %. Точка насичення каталогу лишилася на 10 VU, але на ≈ 553 RPS замість ≈ 391: каталог і
далі fan-out, просто кожен його запит дешевший для реплік.

Таблиця методички (каталог, 100 VU — ступінь із найменшим розкидом серед насичених):

| Метрика / Показник | До оптимізації (Baseline) | Після оптимізації (Optimized) | Дельта (Зміна %) |
|---|---|---|---|
| Throughput (RPS) | 404 (395–410) | 569 (557–581) | +40.9 % |
| p95 Latency | 391.9 мс | 275.4 мс | −29.7 % |
| p99 Latency | 458.4 мс | 323.6 мс | −29.4 % |
| Error Rate (%) | 0.00 | 0.00 | — |

| CPU / пам'ять backend | 115 % (з 200) / 156 МіБ | 139 % / 156 МіБ | CPU росте з RPS, пам'ять та сама |

CPU — з `docker stats`, а один його замір з усіма контейнерами триває ≈ 13 с, тож на 30-секундний ступінь припадає 1–3 заміри.
CPU показує, чи вузол на стелі, але не точний відсоток; на ступенях, де замір влучив у паузу між ступенями, він занижений.

**Регресія** (по одному прогону на конфігурацію, тож менш надійно, ніж каталог). Запис голосів: RPS +31 … +81 %, p95
−11 … −42 %. Деталі опитування: RPS +44 … +136 %, p95 −35 … −63 %. Гірше не стало ніде, бо підготовка допомагає кожному
повторюваному запиту. Побічний ефект: на деталях опитування backend-и після зміни доходять до ≈ 200 % своїх двох ядер — вузьке
місце цього шляху перемістилося з реплік на backend.

**Інший день, інший рівень.** 2026-11-23 той самий каталог «до» дав ≈ 1300–1400 RPS замість ≈ 400: ліміти контейнерів ті самі,
але того дня машина працювала в 3–5 разів швидше (той самий `pgbench`: 3749 проти 717). Ефект оптимізації в той день той самий:
+49…+53 % ([`stats-check.md`](stats-check.md)). Там же перевірено, чи не пояснює симптом відсутність статистики планувальника на
свіжому стеку: ні, вона дає лише 6–9 %.

**Компроміси (trade-offs).** Скидання з'єднання при поверненні в пул тепер чотири легкі команди замість одного
`DISCARD ALL`; кожен процес PostgreSQL тримає до 20 підготовлених операторів з планами (трохи більше пам'яті); generic plan
однаковий для всіх значень параметра (ризик для сильно нерівномірних даних); підготовлені запити несумісні з PgBouncer у
transaction mode (його в нас немає). Деталі — ADR [0068](../docs/ai/decisions/0068-auto-prepare-root-cause.md).
