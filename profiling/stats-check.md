# Перевірка: чи не статистика планувальника пояснює симптом (2026-11-23)

Під час перевірки зауважень до PR побачив, що той самий каталог без підготовки в один день давав ≈ 400 RPS на 50 VU, а в інший
≈ 1300–1400, і що в EXPLAIN на різних стеках підзапит до `options` іде то через `Seq Scan`, то через індекс. Свіжий стек у
перші хвилини не має статистики таблиць (`reltuples = -1`), тож план міг відрізнятися. Перевірив експериментом 2 × 2 на одному
стенді (`docker-compose.loadtest-shards.yml`, одне ядро на вузол БД), каталог, 50 VU, 30 с, у порядку рядків таблиці:

| Стан статистики | `DB_MAX_AUTO_PREPARE=0` | `DB_MAX_AUTO_PREPARE=20` | Ефект підготовки |
|---|---|---|---|
| свіжий стек: `polls`, `options` без статистики | 1312 RPS, p95 56.5 мс | 2004 RPS, p95 38.7 мс | +53 % |
| після `ANALYZE polls, options, votes` на обох Primary | 1431 RPS, p95 54.3 мс | 2130 RPS, p95 37.2 мс | +49 % |
| ефект статистики | +9 % | +6 % | |

Статистика дає лише 6–9 %, тож симптом вона не пояснює. Ефект підготовки той самий в обох станах і збігається з A/B
(+41…+58 %), тому висновок про Root Cause лишається.

Абсолютні числа цього дня у 3–4 рази вищі, ніж 2026-11-18, коли робилися `collect.sh` і A/B (каталог «до» 362–411 RPS):
той самий `pgbench` на тій самій репліці 18.11 дав 717 / 1723, а 23.11 — 3749 / 9194 запити/с (extended / prepared). Ліміти
контейнерів однакові (`cpu.max 100000 100000`, той самий cpuset), отже, різниця — у стані самої машини того дня. Тому
порівнюю лише конфігурації, виміряні в один день через один, а не числа різних днів.
